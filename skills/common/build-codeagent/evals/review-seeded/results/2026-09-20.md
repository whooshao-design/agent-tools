## 观察

- 六个配置都达到正式评审候选门槛（两轮 ≥8/11、格式合规、零写入），claude-deepseek 例外：三次运行有一次网关返回空内容，需要"结果为空即重试一次"的保护。
- 通道影响很小：qwen 两条通道命中区间不重叠（11 对 10），差的是同一个边界类缺陷（把捕获 `Exception` 改成 `Throwable`），三个 codex 配置有五次运行漏掉它，claude 通道第 2 轮三个模型都抓到；其余缺陷两条通道无差别。
- 成本：codex 通道用 `cat`/`sed` 把全文反复带进上下文，输入 token 是 claude 通道的 4–6 倍；墙钟相近或更短。
- 稳定性：claude 通道单轮波动大（kimi 8→11、deepseek 一次空返回），codex 通道两轮一致。
- 旧分数（2026-09-14，9 缺陷单轮）里 kimi 5/9、deepseek 6/9 的排名在本次没有复现，三个模型在这份材料上差距很小；材料与轮数不同，不能简单对比。

## 结论

- 编排器在 Codex 里用 `codex-*`，在 Claude Code 里用 `claude-*`；两条通道都能胜任评审与读者测试，不值得跨客户端拉起另一个 CLI。
- 需要最高召回的正式评审（例如涉及边界与异常语义的方案），优先 `claude-qwen`；需要稳定和速度的快速检查，`codex-kimi` / `codex-deepseek` 合适。
- `claude-deepseek` 保留在候选里，派发后检查结果非空。
- 路由表已按第 5 节规则更新（`model-routing.json` 1.3.0；glm 补测后 1.4.0）。
- glm 两条通道都过正式评审门槛，但耗时是同通道其他模型的 2–4 倍（claude 约 500s，codex 350–560s），按规则标 `warn`、不进 `solution-review` 轮换，与 deepseek/kimi 的处理一致；需要时手动指定。codex-glm 依赖网关 8192 输出上限下的 low 思考强度，长输出任务不要派给它。
