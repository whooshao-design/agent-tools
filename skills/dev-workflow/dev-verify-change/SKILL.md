# dev-verify-change

## 定位

用于在代码改动后，以最小有效成本确认这次变更是否成立。

它是验证阶段的主入口：围绕本次改动优先做最小必要验证，先看结果是否通过、失败点在哪里、是否需要补充覆盖率或回归；不内置特定技术栈的重型实现细节。

## 默认产物目录

如需把测试验证结果落盘，默认放到 `/home/joney/docs/requirements-development/<requirement-name>/test-verification/`，建议文件名使用 `verification.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中汇报验证结论时，可不创建文件

## When to Use

适合以下场景：
- 代码已完成改动，需要判断本次变更是否可接受
- 需要执行与本次改动最相关的测试、构建或检查
- 需要先确认失败是否由本次变更引起，再决定是否扩大验证范围
- 需要给出明确验证结论，而不是只罗列命令输出

不适合以下场景：
- 当前还在理解代码或继续修改代码，此时先回到 `dev-build-change`
- 需求或方案尚未稳定，验证范围无法界定
- 需要做专项深挖但尚未完成基础验证结论

## Workflow

### 1. 明确验证边界与审批状态
至少确认：
- 本次改动了什么
- 哪些模块、接口、页面或行为受到影响
- 最小可证明“改动成立”的验证方式是什么
- 当前需求版本、已评审方案版本、场景版本、实现开始前冻结的代码基线 `B`，以及待验证的 `change_revision` / 代码快照

检查交接材料和默认产物目录。若存在测试场景清单，固定场景审批元组 `T = (R,S,C,B)`、对应审批记录和独立的待验 `change_revision`：

- 只有 `dev-review-test-cases` 对该 `T` 给出“通过”，`R/S/C` 仍与当前产物匹配、`B` 未因外部合并/变基/非本任务改动变化、送审后场景正文未变化，元组才有效；任务自身 `change_revision` 不改写 `B`
- 有效时必须把全部本次范围内的场景作为验证依据，不得选择性忽略
- 需求或方案版本陈旧时停止验证；当前方案已评审通过则依次回 `dev-derive-test-cases`、`dev-review-test-cases`，否则先回方案设计/评审阶段
- 场景版本、正文或评审结论不匹配时停止验证；需改场景先回 `dev-derive-test-cases`，只缺有效评审则回 `dev-review-test-cases`

确实没有已通过场景清单时，记录“无场景审批元组”及依据，按当前需求、方案和仓库门禁界定范围；若所属流程本应先评审场景，则停止并依次转 `dev-derive-test-cases`、`dev-review-test-cases`。

### 2. 先做最小有效验证
优先执行与本次改动最相关的检查，例如：
- 直接受影响模块的测试
- 最小必要的构建或编译检查
- 最贴近变更路径的手工或自动验证

原则是先小后大，先验证核心路径，再决定是否扩展。

在真正执行命令前，先识别仓库级测试约束：
- 对 Maven / TestNG 仓库，先检查 `pom.xml`、Surefire 配置和仓库文档，确认是否强依赖 `suiteXmlFile`、固定 suite XML、profile 或额外 JVM 参数
- 若仓库已要求 `suiteXmlFile`，优先复用仓库已有 suite，或显式传入 `-DsuiteXmlFile=...`，不要为了让临时命令跑通就先建议修改 `pom`
- 新增、修改或迁移单测时，以仓库文档、测试发现配置或实际执行结果作为布局证据；仅存在 `mock` 目录不构成强制规则，只有 suite/门禁确实只发现 `mock.*` 时才据此判定
- 若用户级说明、仓库 `AGENTS.md` 或模块文档已经给了推荐测试命令，优先沿用并在验证结果里写清楚具体命令，避免重复踩同一类运行方式问题

覆盖率按当前任务与仓库事实处理：

- 先读取用户/任务验收条件、CI/质量门禁配置和仓库文档，确定覆盖率是否适用及阈值；通用入口不自设统一百分比
- 适用且工具支持时，优先收集新增/修改可执行行的覆盖率证据，不用全仓百分比掩盖改动行缺口
- Java / Maven 改动在任务或仓库要求覆盖率、需要改动行证据、跨模块聚合或报告可信度诊断时调用 `verify-java-coverage`
- 没有覆盖率框架且仓库/任务也无此门禁时，记录“不适用”，用定向测试、静态检查或人工检查等替代证据支撑受限结论，不反复尝试安装工具
- 门禁明确要求覆盖率却因环境、依赖或权限无法生成时，不能宣称该门禁通过；列出替代证据、限制和下一条可执行命令。能生成数据但找不到阈值事实源时，只报告观测值，不判定达标

### 3. 解释结果并收敛结论
拿到结果后明确区分：
- 通过：哪些关键路径已被验证
- 失败：失败发生在哪里、是否明显与本次改动相关
- 未覆盖：哪些风险点尚未被验证到

存在有效审批元组时，逐条输出“场景 ID → 自动测试或人工检查 → 结果与证据/未覆盖原因”，范围内场景不得遗漏。失败不能默认判定为代码问题：对照当前需求和已评审方案区分实现缺陷、场景错误和方案缺口，不能为变绿而扭曲代码或放宽断言。

一旦确认场景错误，立即把原审批元组标记为失效并停止给出通过结论：恢复路径是 `dev-derive-test-cases` 修正并递增版本，再由 `dev-review-test-cases` 获取新审批；新元组生效后，若修正影响实现则从 `dev-build-change` 恢复，否则从本 skill 重新验证。单独执行本 skill 时按该路径交接；处于 `dev-auto-loop` 时停止为 `awaiting_human` 并报告恢复点，不擅自跨段回跳。若根因是方案缺口，同样先停止并从方案阶段恢复，之后重新推导、评审受影响场景。

### 4. 按需增强
只追加当前门禁、风险或失败定位需要的覆盖率、相邻回归和专项验收。证据不足时给出受限结论和具体缺口；相同前提下重复命令不会产生新证据时停止重试。

## 验证原则

- 围绕本次改动做最小有效验证，不默认扩大成全量检查
- 先遵循仓库级测试入口约束，再决定怎么执行验证命令
- 测试布局结论必须有文档、发现配置或实际执行证据，不能从目录名称推断
- 覆盖率是否适用、阈值多少以任务和仓库门禁为事实源；适用时说明报告位置、覆盖范围和未覆盖风险
- 先定位失败，再决定修复还是扩测
- 有有效场景审批元组时覆盖全部范围内场景；场景错误会使审批失效，修正并复审后才能继续
- 验证结论必须能支撑下一步决策
- 回归检查是按需增强，不是默认重流程
- 保持与项目现有测试和验证方式一致

## 输出物

默认输出一份轻量验证结果，至少包括：
- 前提状态：`R/S/C/B`、审批记录、待验 `change_revision` / 代码快照，或无有效元组的依据
- 验证范围：本次验证覆盖了哪些改动点
- 执行结果：哪些检查通过、哪些失败、哪些未执行
- 场景映射：每个范围内场景 ID 的测试/人工检查、结果证据或未覆盖原因；无有效清单时写“不适用”及原因
- 单测布局：实际发现规则及其证据
- 覆盖率结果：适用性和阈值来源、报告位置、改动行或可用范围、关键缺口和门禁结论
- 失败分析：失败是否与本次改动直接相关
- 验证结论：`通过`（必需证据与门禁均满足）、`受限通过`（仅缺非必需证据且限制已记录；继续推进还需用户明确接受限制）、`需修复后重验`（实现缺陷）或 `阻塞`（审批、材料、环境或必需门禁无法满足）；场景审批失效时不能通过
- 后续建议：是否需要补充覆盖率、回归或专项验收

## 结果要求

一份合格的验证结果应满足：
- 能说明验证是围绕本次改动展开，而不是泛泛跑一遍
- 能明确测试是否通过，以及通过结论建立在哪些证据上
- 存在有效审批元组时，每个范围内场景都有结果或未覆盖原因；元组陈旧或失效时没有继续给出通过结论
- 能以实际发现证据说明单测布局是否符合仓库约束
- 能说明覆盖率是否适用、阈值来自哪里；要求覆盖率却缺证据时不把未知当作门禁通过
- 保持轻量，不内嵌 Maven、JaCoCo、浏览器自动化等重实现正文

## 可选增强

- Java / Maven 改动满足仓库/任务覆盖率门禁，或需要改动行、跨模块、报告可信度深挖时，调用 `verify-java-coverage`
- 如需要做浏览器、页面或交互验收，可调用 `verify-browser-qa`
- 如验证显示问题仍在代码实现本身，回到 `dev-build-change`

## 交接建议

- `通过` → 携带 `T`、`change_revision` 和证据进入 `dev-review-change`
- `受限通过` → 只有用户明确接受当前限制后才进入 `dev-review-change`，否则等待风险决策
- `需修复后重验` → 回 `dev-build-change`；修复后必须重新验证
- `阻塞` → 停止并报告阻塞类型、已有替代证据和恢复条件，不原地重复相同命令
