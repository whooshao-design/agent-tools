# dev-verify-change

## 定位

用于在代码改动后，以最小有效成本确认这次变更是否成立。

它是验证阶段的主入口：围绕本次改动优先做最小必要验证，先看结果是否通过、失败点在哪里、是否需要补充覆盖率或回归；不内置特定技术栈的重型实现细节。

## 默认产物目录

如需把测试验证结果落盘，默认放到 `/home/joney/docs/requirements-development/<requirement-name>/test-verification/verification.md`，使用 `references/verification-template.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中汇报验证结论时，可不创建文件
- 第 2 轮及以后验证前，将上一轮报告归档到 `test-verification/rounds/verification-round-<上一轮次号>.md`

## When to Use

适合以下场景：
- 代码已完成改动，需要判断本次变更是否可接受
- 需要执行与本次改动最相关的测试、构建或检查
- 需要先确认失败是否由本次变更引起，再决定是否扩大验证范围
- 需要给出明确验证结论，而不是只罗列命令输出

不适合以下场景：
- 当前还在理解代码或继续修改代码，此时先回到 `dev-build-change`
- 需求或方案尚未稳定，验证范围无法界定
- 需要做专项深挖但尚未完成基础验证结论

## Workflow

### 1. 明确验证边界与交付模式
至少确认：
- 本次改动了什么
- 哪些模块、接口、页面或行为受到影响
- 最小可证明“改动成立”的验证方式是什么
- 按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md` 生成的 `gate_context G` 和待验证 `change_revision`
- `change_revision` 中各 `DEV-*` 的来源、最终状态、实际写集和执行证据

按 `G.mode` 检查交接材料：

- `approved`：方案/测试清单的 `approval-record-v1`、`T=(R,S,C,B)` 与当前指纹必须匹配，并覆盖全部范围内检查项；陈旧时停止并回最早受影响阶段
- `direct`：执行验证前重读 `G.D={ref,fingerprint}` 指向的 `direct-record-v1`，复算外部指纹并校验 schema、完成标准、范围和 `B`；不要求不存在的方案/清单审批，也不把缺失审批写成“已豁免”
- `waived`：执行验证前重读 `G.W={ref,fingerprint}` 指向的 `waiver-record-v1`，复算外部指纹并校验 schema、用户授权、门禁枚举/依赖闭包、绑定产物、当前 `B` 和条件；未跳过的适用门禁仍须有匹配 `approval-record-v1`，并逐项验证替代证据与残余风险

缺少与所选模式匹配的上下文时停止，不静默切换模式。

验证前确认所有范围内 DEV 均为 `Done` 或具有充分“无需代码”依据的 `Skipped`，且实际写集能归属到 DEV。存在
`Planned` / `InProgress` 时回 `dev-build-change`；`Blocked` 按其恢复条件归类为实现、材料、环境或人工阻塞，
不得用测试通过掩盖未完成开发项。

### 2. 先做最小有效验证
优先执行与本次改动最相关的检查，例如：
- 直接受影响模块的测试
- 最小必要的构建或编译检查
- 最贴近变更路径的手工或自动验证

原则是先小后大，先验证核心路径，再决定是否扩展。

执行前先读取 `references/test-execution-routing.md`：仅在仓库实际使用 Maven/TestNG、存在覆盖率要求或需要诊断测试发现规则时，消费其中相应小节。仓库文档和真实配置优先于通用建议。

### 3. 解释结果并收敛结论
拿到结果后明确区分：
- 通过：哪些关键路径已被验证
- 失败：失败发生在哪里、是否明显与本次改动相关
- 未覆盖：哪些风险点尚未被验证到

approved 逐条输出“检查项 ID (`TC-*`) → 对应 `DEV-*`/实现位置 → 自动测试或人工检查 → 结果与证据/未覆盖原因”；direct 逐条映射 `D` 的完成标准与 DEV；waived 逐项验证替代证据、DEV 和仍适用门禁。失败不能默认判定为代码问题：应区分实现缺陷、检查项错误和方案缺口，不能为变绿而扭曲代码或放宽断言。

若仅缺非必需证据而考虑 `受限通过`，必须为每项限制分配稳定 ID（如 `VL-001`）和内容指纹，并记录缺失证据、关联检查项/门禁、影响、接受条件、当前 `G` 与 `change_revision`。限制内容、绑定对象或条件变化后旧授权失效；用户仅说“继续”不构成风险授权。

一旦确认测试清单错误，立即把 `G.mode=approved` 中的原 `T` 标记为失效并停止给出通过结论：恢复路径是 `dev-derive-test-cases` 修正并递增版本，再由 `dev-review-test-cases` 获取新审批；新 `G` 生效后，若修正影响实现则从 `dev-build-change` 恢复，否则从本 skill 重新验证。单独执行本 skill 时按该路径交接；处于 `dev-auto-loop` 时停止为 `awaiting_human` 并报告恢复点，不擅自跨段回跳。若根因是方案缺口，同样先停止并从方案阶段恢复，之后重新编写、复核受影响检查项。

### 4. 按需增强
只追加当前门禁、风险或失败定位需要的覆盖率、相邻回归和专项验收。证据不足时给出受限结论和具体缺口；相同前提下重复命令不会产生新证据时停止重试。

## 常见借口与反驳

| 借口 | 反驳 |
|---|---|
| “跑了几个关键测试都过了，剩下的先不跑” | approved 必须覆盖 `T` 中全部范围内检查项；未执行项逐条记为未覆盖，结论最多是需用户逐项授权的 `受限通过` |
| “测试全绿，改动就没问题” | 测试只证明检查项覆盖到的行为；未映射到 DEV 的写集、`Planned/InProgress` 的开发项不能被绿灯掩盖 |
| “直接跑全量套件更保险” | 先围绕本次改动做最小验证再按失败或门禁扩展；全量不是默认，也不能替代检查项映射 |
| “失败的是老测试，与本次无关” | 先定位失败是否由本次改动引起并写明依据；不能为变绿改断言或跳过用例 |
| “用户说了继续，就算授权” | 只有对精确 `VL-*` 指纹、`G` 和 `change_revision` 的明确授权才算；“继续”不是风险授权 |

## 验证原则

- 围绕本次改动做最小有效验证，不默认扩大成全量检查
- 先遵循仓库级测试入口约束，再决定怎么执行验证命令
- 测试布局结论必须有文档、发现配置或实际执行证据，不能从目录名称推断
- 覆盖率是否适用、阈值多少以任务和仓库门禁为事实源；适用时说明报告位置、覆盖范围和未覆盖风险
- 先定位失败，再决定修复还是扩测
- approved 覆盖 `T` 中全部范围内检查项；检查项错误会使审批失效，修正并复审后才能继续
- 验证结论必须能支撑下一步决策
- 回归检查是按需增强，不是默认重流程
- 保持与项目现有测试和验证方式一致

## 输出物

默认输出一份轻量验证结果；正式落盘时使用 `references/verification-template.md`。至少包括：
- 前提状态：`gate_context G`、审批/任务/waiver 记录、待验 `change_revision`
- 开发项状态：范围内 `DEV-*` 的 Done/Skipped 依据、实际写集和异常状态
- 验证范围：本次验证覆盖了哪些改动点
- 执行结果：哪些检查通过、哪些失败、哪些未执行
- 映射：approved 列每个范围内检查项；direct 列完成标准；waived 列跳过门禁、仍适用门禁及替代验证
- 单测布局：实际发现规则及其证据
- 覆盖率结果：适用性和阈值来源、报告位置、改动行或可用范围、关键缺口和门禁结论
- 失败分析：失败是否与本次改动直接相关
- 限制项：每个 `VL-*` 的内容指纹、缺失证据、影响范围、接受条件和匹配用户授权；没有则写“无”
- 验证结论：`通过`（当前模式的必需证据与门禁均满足）、`受限通过`（仅缺非必需证据且限制已记录；继续推进还需用户明确接受限制）、`需修复后重验`（实现缺陷）或 `阻塞`（审批、材料、环境或必需门禁无法满足）；测试清单审批失效时不能通过
- 后续建议：是否需要补充覆盖率、回归或专项验收

## 结果要求

一份合格的验证结果应满足：
- 能说明验证是围绕本次改动展开，而不是泛泛跑一遍
- 能确认不存在被测试结果掩盖的未完成 DEV，且实际写集均有开发项归属
- 能明确测试是否通过，以及通过结论建立在哪些证据上
- approved 的每个范围内检查项、direct 的每条完成标准、waived 的每项替代验证都有结果或未覆盖原因；`G` 陈旧或失效时没有继续给出通过结论
- 能以实际发现证据说明单测布局是否符合仓库约束
- 能说明覆盖率是否适用、阈值来自哪里；要求覆盖率却缺证据时不把未知当作门禁通过
- `受限通过` 的每项限制都能由稳定 ID/指纹精确授权，且不会跨 `G` 或代码修订复用
- 保持轻量，不内嵌 Maven、JaCoCo、浏览器自动化等重实现正文

## 可选增强

- Java / Maven 改动满足仓库/任务覆盖率门禁，或需要改动行、跨模块、报告可信度深挖时，调用 `verify-java-coverage`
- 如需要做浏览器、页面或交互验收，可调用 `verify-browser-qa`
- 如验证显示问题仍在代码实现本身，回到 `dev-build-change`

## 交接建议

- `通过` → approved 进入 `dev-review-change`；direct 重读并校验 `G.D={ref,fingerprint}` 指向的 `direct-record-v1`，在其中 `code_review_required=true`、风险较高或用户要求时进入独立代码评审，否则可直接进入 `dev-finish-branch` 并记录依据；waived 重读 `G.W` 指向的记录，按未豁免门禁和任务风险决定
- `受限通过` → 只有用户对每个 `VL-*` 的当前指纹、`G`、`change_revision` 和条件作出明确授权后才进入 `dev-review-change`，否则等待风险决策
- `需修复后重验` → 回 `dev-build-change`；修复后必须重新验证
- `阻塞` → 停止并报告阻塞类型、已有替代证据和恢复条件，不原地重复相同命令
