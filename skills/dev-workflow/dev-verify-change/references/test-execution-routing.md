# 测试执行与覆盖率路由

仅在当前仓库或任务涉及对应技术时读取相关小节。用户说明、仓库 `AGENTS.md`、构建配置和 CI 门禁是事实源；本文不设统一阈值。

## 测试入口与发现规则

- 优先使用仓库文档或 CI 已验证的命令，并在报告中记录完整命令
- 新增、修改或迁移测试时，以测试发现配置或实际执行结果判断目录与命名；不能只凭目录名称推断规则
- 临时命令失败时先确认入口参数和 profile，不先修改业务构建配置来迎合命令

## Maven 与 TestNG

- 检查 `pom.xml`、Surefire/Failsafe 配置和仓库文档，确认是否依赖 `suiteXmlFile`、固定 suite XML、profile 或 JVM 参数
- 仓库要求 suite 时优先复用已有 suite，或显式传入 `-DsuiteXmlFile=...`
- 仅存在 `mock` 目录不代表 suite 必然只发现 `mock.*`；需要配置或执行证据

## 覆盖率

- 从任务验收条件、CI/质量门禁和仓库文档确认是否适用及阈值；找不到阈值时只报告观测值，不判定达标
- 适用时优先给出新增/修改可执行行的证据，不用全仓百分比掩盖改动行缺口
- Java/Maven 需要改动行、跨模块聚合或报告可信度诊断时调用 `verify-java-coverage`
- 仓库没有覆盖率框架且任务无覆盖率要求时记录“不适用”；定向测试、静态检查或人工检查已满足本次必需证据时可给出“通过”。覆盖率不适用本身不产生 `VL-*`、受限通过或额外风险授权。
- 门禁要求覆盖率但因环境、依赖或权限无法生成时，不宣称通过；记录限制、替代证据和下一条可执行命令

## 前端验证

- 先跑仓库已有的 lint、type-check、test 脚本；没有时（如 `web_mihawk_oa`）至少对改动的 `.vue` 做模板编译、对脚本做语法检查，并在报告中写明“仓库无 lint/test 脚本”
- 资源允许时（启动工具的资源门禁通过），本地 dev server 编译通过是必需证据；门禁不通过时记录原因，退回模板编译与语法检查并在结论里写明证据限制：米霍克 OA 前端用 `start-local-frontend`（`doctor` → `start` → 等 webpack 明确报告编译完成），只看端口监听不算
- 能在本地页面复现的交互用浏览器自动化截图留证，按 `verify-browser-qa`；截图写明页面 URL、操作和对应检查项
- 依赖真实后端数据或登录态的交互，先判断 agent 能否拿到对应环境的登录态；拿不到时按下文“环境联调”的登录态规则处理，把该项列为用户验收项，写清入口 URL、前置数据、操作步骤和预期结果，结论中标为未由 agent 覆盖
- 前后端一起改时，后端行为按“环境联调”绕开页面直接验证，页面只验证展示与交互

## 环境联调

- 先确认被测实例确实是本次部署的版本（实例名/版本号、部署时间），再开始调用
- 后端行为优先绕开页面直接验证：Dubbo/FSOF 接口用 `test-dubbo-api`（扁鹊）直调目标实例，结果用 `query-mysql-data` 只读核对；需要证明“源数据未被修改”时，在调用前后各取一次内容指纹（如 `MD5(GROUP_CONCAT(...))`）比对
- 会写数据的调用（如复制、创建）使用可识别的名称前缀，报告里列出产生的测试数据，清理由用户决定
- 页面交互需要的登录态 agent 拿不到时（例如项目环境 OA 网关不认自动化浏览器 profile 的线上登录态），不要把 Cookie 转发到其他环境或公网 IP 绕过；把页面检查项列为用户验收项，并附具体操作与预期
- 发现与预期不符的差异时，先区分是本次改动造成的还是原有链路行为：对照改动代码能触达的字段范围，并核对源数据是否本身异常；原有行为记为观察项，不计入本次失败
