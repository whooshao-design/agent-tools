# dev-finish-branch

## 定位

用于在提交、提测、交付或请他人接手前，对当前开发分支做最终收口。

它是交付前阶段的主入口：确认 diff 是否清晰、验证是否到位、评审问题是否已处理，并整理可直接交付的摘要；不替代验证阶段重跑完整测试，也不重复做完整代码评审。

## 默认产物目录

如需把交付摘要落盘，默认放到 `/home/joney/docs/requirements-development/<requirement-name>/delivery-handoff/`，建议文件名使用 `handoff.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中给出收口结论时，可不创建文件

## When to Use

适合以下场景：
- 本次改动已基本完成，准备提交、提测、交付或发起后续流程
- 需要确认当前 diff 是否只包含应交付内容
- 需要检查验证结论、评审结论与已知风险是否已经收口
- 需要输出一份简明交付摘要，方便自己或他人继续推进

不适合以下场景：
- 代码仍在频繁修改，范围尚未稳定，此时先回到 `dev-build-change`
- 关键验证尚未完成，无法判断是否可交付，此时先转 `dev-verify-change`
- 尚未做过基本代码评审，但已需要评审结论支撑交付，此时先转 `dev-review-change`

## Workflow

### 1. 收口当前 diff
先看本次准备交付的改动是否清晰：
- 按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md` 检查 `gate_context G`、相关记录、已验证/已评审的 `change_revision` 是否与待交付工作区精确匹配（含暂存区指纹）；`D/W` 必须重读不可变记录并复算外部 fingerprint
- 只交接工作区时，快照身份（已含暂存区指纹）与已验证的 `change_revision` 匹配即可，不要求先暂存；用户要求提交、或交付对象是暂存内容时，待提交内容（`git diff --cached`）必须就是已验证的那份：暂存区与工作区不一致（部分暂存、暂存的是修复前版本）就重新暂存到已验证版本，或把交付范围明确绑定到暂存内容并按它重新验证
- 改了什么
- 为什么改
- 是否混入无关变更
- 是否还留有明显未完成内容
- `change_revision` 中是否仍有 Planned/InProgress/Blocked DEV，Skipped 是否有充分依据，全部实际写集是否都有 DEV 归属

### 2. 按模式检查收口门禁

先使用以下矩阵，不能把一种模式的事实套到另一种模式：

| `G.mode` | 上游正式门禁 | 验证 | 代码评审 |
|---|---|---|---|
| `approved` | `solution-review` 必须精确绑定 `(R,S,B)`；`test-design-review` 必须精确绑定 `(R,S,C,B)`；两者均引用有效 `approval-record-v1` | 必须匹配当前 `G + change_revision`，覆盖全部检查项 | 必须有独立 reviewer 形成的匹配审批记录 |
| `direct` | 不要求也不声称方案/清单审批；重读 `G.D={ref,fingerprint}` 指向的 `direct-record-v1`，其完成标准与 `B` 必须匹配 | 必须覆盖该记录中的完成标准 | 重读记录所得 `code_review_required=true`、风险较高或用户要求时必须独立评审；否则记录未要求的依据 |
| `waived` | `G.W={ref,fingerprint}` 指向有效 `waiver-record-v1`；只免除闭包完整的 `skipped_gates[]`，其余适用门禁须有匹配审批 | 必须逐门禁覆盖替代证据和残余风险 | 除非 `change-review` 被明确豁免，否则按任务风险与原流程要求执行 |

`waived` 不再要求被明确豁免的上游审批；但必须校验枚举和依赖闭包，例如跳过 `solution-review` 时 `test-design-review` 也必须在跳过列表中。每个跳过门禁都必须有独立的用户授权、替代证据、残余风险、范围和有效期；授权范围外的缺失门禁仍会阻塞收口。`direct` 不能回填不存在的审批或 waiver。

### 3. 确认验证状态
只确认现有验证状态是否足以支撑交付：
- 已执行了哪些验证
- 关键路径是否已有结果
- 当前失败、跳过或未覆盖点是什么
- 是否仍存在必须补验的风险
- approved 有已批准测试清单时，每个范围内检查项 ID 是否都有结果证据或显式未覆盖原因；direct 则逐条检查完成标准
- 每个范围内 DEV 是否为 Done 或有效 Skipped；存在未完成、无归属写集或 producer 溯源缺失时不得收口为可交付
- 验证为 `受限通过` 时，每个 `VL-*` 是否仍与当前指纹、`G`、`change_revision` 匹配并具有用户授权

这里关注“是否已满足当前交付条件”，而不是重新展开完整验证流程。

### 4. 确认评审状态
检查评审相关结论是否已收敛：
- 当前模式要求代码评审时，是否已有匹配当前 `G + change_revision` 的结论；不要求时是否记录了判断依据
- 当前模式要求的每项正式评审是否有不可变 `approval-record-v1`，且记录/报告/委派结果指纹、冻结输入、全部 `producer_agent_refs`、真实 `reviewer_agent_ref` 和独立性检查均匹配
- approved 必须分别核对方案审批的 `bound_inputs=(R,S,B)` 和测试清单审批的 `bound_inputs=(R,S,C,B)`；只写“匹配当前 T”不足以放行
- direct/waived 必须核对 `D/W` 的 ref/fingerprint、schema、记录内容和当前 `B`；记录被修改、自指纹、闭包不全或替代证据缺失均判失效
- 阻断问题是否已修复或明确处理
- 可延后问题是否已被记录；标为接受时是否存在绑定当前 `G`、finding 和 `change_revision` 的用户明确授权
- 当前是否仍存在不能忽略的发布风险

### 5. 整理交付摘要
把当前分支收敛成可交付信息：
- 变更摘要
- 验证摘要
- 风险摘要
- 后续注意事项

### 6. 给出最终收口判断
结论只能是以下之一：

- `可交付`：`G`、验证、当前模式要求的评审、风险授权和待交付 `change_revision`（含暂存区指纹）全部匹配
- `需清理后重验`：仅存在本任务拥有且可安全修正的 diff/遗留项；修改后必须重新验证和评审
- `审批或证据失效`：任一身份、审批、验证或评审记录与当前版本不匹配
- `等待人工`：混入来源不明或用户改动、需要风险决策，或无法安全判断清理权限

任一当前模式要求的审批、验证、评审或风险授权与当前版本/diff 不匹配，或正式 reviewer 与任一 producer 相同/身份缺失时，不得收口为可交付；结论必须是 `审批或证据失效`，并指出最早恢复阶段。不得因 direct 没有上游审批而判失效，也不得因 waived 缺少已明确跳过的审批而进入死路。

## 收口原则

- 以当前分支现状为准，不把收口阶段扩成新一轮开发
- 优先确认差异、验证、评审三件事是否闭环
- 不重跑完整测试，不重复做完整 CR
- 对未解决风险要显式标出，不把未知写成已完成
- 输出要让接收方一眼看懂本次交付的边界与状态

## 输出物

默认输出一份轻量收口结果，建议包含：
- 交付范围：本次准备提交或交付的内容
- 开发项状态：`DEV-*` 完成/跳过依据、实际写集和 producer 溯源
- diff 结论：是否存在无关改动、遗留项或需清理内容
- 验证状态：已验证、未验证、失败或带风险接受的部分
- 评审状态：带稳定 ID/指纹的已处理问题、待跟进问题、验证限制项和已接受风险
- 基线状态：`G`、`change_revision`、当前模式要求的审批/验证/评审引用及其匹配结论
- 收口结论：四种唯一结论之一及恢复阶段
- 交付摘要：可直接用于提交说明、提测说明或 handoff

## 结果要求

一份合格的收口结果应满足：
- 能说明当前分支是否真的到了可交付状态
- 能证明没有未完成 DEV、无归属写集或缺失 producer 溯源
- 能区分“已完成”“已知风险”“仍未收口”
- 能帮助后续提交、提测或交接，而不是重复前面阶段的正文
- 保持轻量，不重新展开完整测试或评审流程

## 可选增强

- 若发现关键验证结论不足，回到 `dev-verify-change`
- 若发现仍有重要评审问题未收敛，回到 `dev-review-change`

## 交接建议

- `可交付` → 基于本结果整理 commit、提测或交付说明
- `需清理后重验` → 回 `dev-build-change`，仅处理本任务拥有的变更，之后重新验证和评审
- `审批或证据失效` → 使旧结论失效并回最早受影响阶段
- `等待人工` → 停止并列出需要用户决定的精确对象
