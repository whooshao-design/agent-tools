# dev-derive-test-cases

## 定位

用于在方案评审通过后、编码开始前编写测试清单。测试清单是版本化的待验证检查项集合；每项使用内部 ID `TC-*`，写清改动完成后要检查什么、怎样算通过以及需要什么证据。

本 skill 负责建立“需求 → 方案 → 检查项”三向追踪并暴露缺口；不替方案补做产品或技术决策，不生成测试代码，不执行测试，也不批准自己的清单。完整性由 `dev-review-test-cases` 独立核对，实现与执行分别交给 `dev-build-change`、`dev-verify-change`。

## 默认产物目录

正式测试清单默认放到 `/home/joney/docs/requirements-development/<requirement-name>/test-cases/test-cases.md`。

- `<requirement-name>` 与方案使用同一需求目录；用户指定路径时优先使用
- 仅需对话输出时不创建文件；落盘时使用 `references/test-cases-template.md`
- 首次送审前可在当前版本编辑；一旦进入 `Reviewing`、生成审批记录或已交付评审，任何内容修订都必须先归档到 `test-cases/versions/test-cases-v<旧版本号>.md`，再递增清单版本并回到 `Draft`
- 方案升级、补充遗漏、修改断言或追踪关系都属于内容修订；不得在已送审版本上原地修改

## 输入契约

开始编写前按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md` 固定以下输入；关键项缺失时列为材料缺口，不用猜测补齐：

- 完整需求身份 `R`，以及稳定的需求/验收标准 ID
- 完整方案身份 `S`，以及绑定 `(R,S,B)` 的明确评审结论；方案未通过时先转 `dev-review-solution`
- **本轮闭包分母**：`R` 的 `AC-*` 集合与已审批方案附录追踪矩阵中的 `CHG-*` 集合。两个枚举的来源产物、`ref + fingerprint` 与条目计数必须记入输入绑定；`CHG-*` 矩阵或验收标准位于独立指纹的附录时，**必须一并绑定该附录的 `ref + fingerprint`，只绑定 `S` 不算完成冻结**。分母之外的行为不得由清单侧自行补充枚举，只能记为方案缺口
- 已明确接受的风险、假设或排除项及其匹配授权记录；推导者不得自行接受风险
- 代码基线 `B` 和必要代码上下文。编排器或上游提供的代码证据必须逐条区分 `fact`（附检索命令 + 范围 + 计数）与 `inference`（附推理链）；**未标来源的一律按假设处理，不得作为某维度判 N/A 或某检查项判不适用的依据**。「无并发场景 / 无上游消费方 / 该路径不可达」这类负向断言需要两条相互独立的检索路径佐证
- 本轮范围、排除范围及其依据

## Workflow

### 1. 建立三向追踪

逐条连接需求/验收标准、方案章节和检查项 ID：

- 每条需求与验收标准都必须落到方案条目和至少一个检查项，或明确标成缺口
- 每个已审批方案的 `CHG-*` 都必须有需求来源和检查项去向；分母以输入契约冻结的 `CHG-*` 集合为准，来源不明的行为不得静默纳入，也不得由清单侧自行扩充分母
- 每个检查项都必须同时标注需求/验收标准来源和方案依据

### 2. 编写待验证检查项

每个检查项至少写清前置条件、输入/触发、预期业务结果、失败信号和预期验证证据。断言必须约束真实业务行为，不能只写“能运行”或“不报错”。

至少覆盖正常、异常和边界路径，并按变更风险检查相关的并发、权限、安全、兼容、迁移、性能、观测、发布与回滚等维度。类型是开放标签，可按领域扩展；不得把检查项锁死为三种枚举。

**适用维度集合继承已审批方案**：本轮适用维度直接沿用方案按 `solution-structure-contract.md` §5 做出的横切维度相关性判定。`N/A` 只允许写成对方案该判定的引用（章节号 + 方案给出的 N/A 理由），**不得由清单产出者重新做全称否定判断**。方案未覆盖某维度、或引用与方案不一致时，记为方案缺口而非自行判 N/A。

### 3. 暴露缺口

- 需求与方案矛盾、方案遗漏或描述不清：记录为方案缺口，不代替设计方决策
- 缺少需求、审批事实、风险授权或基线：记录为材料缺口
- 保留缺口的证据、影响、建议和关闭条件，供后续评审与回退使用

### 4. 自查并提交复核

- 核对追踪矩阵无孤立需求、孤立方案条目或来源不明检查项；**输出三组计数与差集**——`|AC|` / `|CHG|` / `|TC|` 及各自未映射的 ID 列表，闭包是集合 diff 而非主观判断，必须可被复核方按同一分母重算
- 汇总各覆盖维度的检查项 ID 或不适用理由（`N/A` 按 §2 写成对方案判定的引用）
- 记录产物版本、`R/S/B` 和内容变更历史；**「变更摘要」列必须给出 TC 级 ID diff（新增/修改/删除的 `TC-*`）**，否则下一轮无法做定点复审。交付评审前在 handoff 中计算最终测试清单身份 `C`，其指纹和后续审批记录均不写回清单文件本体
- 关闭 finding 时**优先收窄或删除不成立的断言与冗余检查项，而不是无差别追加 `TC-*`**；新增检查项必须落在输入契约冻结的分母格子内
- 记录所有实质编写或修订清单的 `producer_agent_refs[]`；仅做字节不变的持久化不算 producer
- 将测试清单交给 `dev-review-test-cases`；不得自行写成 `Approved`

## 输出要求

默认输出输入绑定、三向追踪矩阵、测试清单、覆盖汇总和缺口清单。合格产物应满足：

- 任一检查项可回溯到具体需求/验收标准和方案条目
- 任一需求或方案行为都有检查项覆盖或显式缺口
- 风险接受有授权证据，清单版本与送审历史可追溯
- 检查项足以指导实现和验证，但不绑定未经方案确定的实现细节

## 交接

- 测试清单编写完成 → `dev-review-test-cases`
- 方案缺口 → 单独执行时转 `dev-design-solution`；处于 `dev-auto-loop` 时只输出带证据的 `upstream_gap`，由编排器按其 producer 结果契约交独立 reviewer 确认，producer 自评不能直接推翻已有方案审批
- 材料缺口 → 补齐指定输入后继续编写
