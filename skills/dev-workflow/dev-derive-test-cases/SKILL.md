# dev-derive-test-cases

## 定位

用于在方案评审通过后、编码开始前，把需求意图和方案行为转化为版本化测试场景。

本 skill 负责建立“需求 → 方案 → 场景”三向追踪并暴露缺口；不替方案补做产品或技术决策，不认定自己的产物已经通过评审，不生成测试代码。完整性由 `dev-review-test-cases` 独立核对，实现与执行分别交给 `dev-build-change`、`dev-verify-change`。

## 默认产物目录

正式场景清单默认放到 `/home/joney/docs/requirements-development/<requirement-name>/test-cases/test-cases.md`。

- `<requirement-name>` 与方案使用同一需求目录；用户指定路径时优先使用
- 仅需对话输出时不创建文件；落盘时使用 `references/test-cases-template.md`
- 首次送审前可在当前版本编辑；一旦进入 `Reviewing`、生成评审报告或已交付评审，任何内容修订都必须先归档到 `test-cases/versions/test-cases-v<旧版本号>.md`，再递增场景版本并回到 `Draft`
- 方案升级、补充遗漏、修改断言或追踪关系都属于内容修订；不得在已送审版本上原地修改

## 输入契约

开始推导前固定以下输入；关键项缺失时列为材料缺口，不用猜测补齐：

- 原始需求产物的路径与版本，以及稳定的需求/验收标准 ID
- 技术方案的路径与版本，以及该版本明确的评审结论；方案未通过时先转 `dev-review-solution`
- 已明确接受的风险、假设或排除项及其授权记录；推导者不得自行接受风险
- 代码基线（commit、分支或可复现的工作区快照）和必要代码上下文
- 本轮范围、排除范围及其依据

## Workflow

### 1. 建立三向追踪

逐条连接需求/验收标准、方案章节和场景 ID：

- 每条需求与验收标准都必须落到方案条目和至少一个场景，或明确标成缺口
- 每个方案行为都必须有需求来源和场景去向；来源不明的行为不得静默纳入
- 每个场景都必须同时标注需求/验收标准来源和方案依据

### 2. 系统推导场景

每条场景至少写清前置条件、输入/触发、预期业务结果、失败信号和预期验证证据。断言必须约束真实业务行为，不能只写“能运行”或“不报错”。

至少覆盖正常、异常和边界路径，并按变更风险检查相关的并发、权限、安全、兼容、迁移、性能、观测、发布与回滚等维度。类型是开放标签，可按领域扩展；不得把场景锁死为三种枚举。确实不适用的维度写明理由。

### 3. 暴露缺口

- 需求与方案矛盾、方案遗漏或描述不清：记录为方案缺口，不代替设计方决策
- 缺少需求、审批事实、风险授权或基线：记录为材料缺口
- 保留缺口的证据、影响、建议和关闭条件，供后续评审与回退使用

### 4. 自查并发布

- 核对追踪矩阵无孤立需求、孤立方案条目或来源不明场景
- 汇总各覆盖维度的场景 ID 或不适用理由
- 记录产物版本、输入版本、代码基线和变更/评审历史
- 将产物交给 `dev-review-test-cases`；不得自行写成 `Approved`

## 输出要求

默认输出输入绑定、三向追踪矩阵、场景清单、覆盖汇总和缺口清单。合格产物应满足：

- 任一场景可回溯到具体需求/验收标准和方案条目
- 任一需求或方案行为都有场景覆盖或显式缺口
- 风险接受有授权证据，场景版本与送审历史可追溯
- 场景足以指导实现和验证，但不绑定未经方案确定的实现细节

## 交接

- 场景产出 → `dev-review-test-cases`
- 方案缺口 → `dev-design-solution`；方案重新通过后，对受影响范围生成新的场景版本
- 材料缺口 → 补齐指定输入后继续推导
