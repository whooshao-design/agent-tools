# 前端评审要点与评审后改动处理

评审写集含 `.vue`、`.js`、`.jsx`、`.ts`、`.tsx`、样式文件或位于前端仓库时，在四个核心维度之外补查本文第 1 节；严重度仍按 `severity-and-complexity.md` 判定，有证据和影响才写 finding。开发侧的对应规则见 `dev-build-change` 的 `references/frontend.md`。

## 1. 前端评审要点

| 检查项 | 怎么查 | 常见判级 |
|---|---|---|
| 是否符合仓库组件惯例 | 对改动涉及的 UI 类型（弹窗、确认框、表单、表格、提示）用 `rg` 统计仓库同类写法和使用次数，对照本次写法 | 绕开项目封装另起一套：Medium |
| 是否手写 VNode 或用命令式弹窗替代项目封装 | 搜 diff 中的 `$createElement`、`h(`、`render(`、`this.$confirm`/`$msgbox` 拼复杂内容 | 仓库已有封装却手写：Medium；仓库同类代码本就如此：不报 |
| 是否遵守仓库编码规范文件 | 读 `AGENTS.md` 指明的规范文件（如 `CLAUDE.md`、`.eslintrc*`、`.prettierrc*`），核对 JSDoc、alias、import 顺序、组件结构顺序、props 声明 | 一般 Low；与同文件现有风格一致的偏差不报 |
| 组件库与框架版本 | 对照 `package.json` 版本，确认没有用到该版本不存在的 API（如在 Element UI 2.x 用 Element Plus 写法） | 运行时报错或功能缺失：High |
| 注入风险 | 搜 `v-html`、`innerHTML`、`dangerouslySetInnerHTML`，以及绑定到 `:href`/`:src` 的外部值；确认来源是否可信、是否经过仓库已有的净化 | 渲染不可信内容：High |
| 交互保护 | 破坏性操作是否有确认；提交中是否防重复点击；失败提示是否说明下一步 | 可重复提交写操作：Medium 起 |
| 前后端契约 | 字段命名映射（驼峰/下划线）、返回结构是否两侧一致 | 字段或结构不一致导致功能失效：High |
| 发布顺序 | 新前端 + 旧后端、旧前端 + 新后端能否共存 | 只提醒，不写成代码 finding：发布顺序靠发布安排保证，不靠改代码；在评审结论里提醒并确认开发结果、发布计划已写明先后顺序 |
| 版式与组件库默认值 | 对照 `dev-build-change` 的 `references/frontend.md` 第 4 节：内边距是否小于组件默认值、按钮顺序与主按钮数量、图标与标题对齐、状态是否齐全 | 按钮或文字贴边、被裁剪、互相重叠：Medium；对齐偏差、间距不在刻度上、多个主按钮：Low |
| 样式泄漏 | 改动组件及其父组件、`@import` 的样式里搜 `/deep/`、`>>>`、`::v-deep`、`!important`，判断是否命中本次新增的子组件 | 命中并改变了子组件布局：Medium |
| 视觉自检证据 | 是否有 `ui_check.js` 的结论（`status`、`fail`/`warn` 明细）和 `target-*.png` 截图；`warn` 是否有保留理由；评审者打开截图核对 | 界面改动没有截图或 `ui_check` 结论：按证据限制处理，结论最多“证据不足”，不写成实现 finding |
| 验证证据 | 是否有本地 dev server 编译通过的证据；需要登录态的交互是否已列为用户验收项并写明步骤与预期 | 缺证据时按 `证据不足` 或证据限制处理，不写成实现 finding |

前后端产物各写各的：前端评审不要求前端产物包含后端配置，发现前端产物混入后端配置（如 Hippo）时按材料缺口记录。

## 2. 评审后又改了代码

评审对象是某个 `change_revision`。评审结束后代码又被修改（包括其他 agent 或用户的重构），`change_revision` 随之变化，旧评审结论和 `approval-record-v1` 不覆盖新代码，不能直接拿来收口。按改动性质处理：

- 行为、接口、数据或风险边界有变化：在新 `change_revision` 上重新评审。
- 行为不变的小改动（如换成项目封装组件、模板化写法、重命名、补注释）：可做定点复审，只评审两个 revision 之间的增量 diff，并确认它没有改变行为；前端页面效果也可以由用户在页面上复核。
- 用户在对话中明确表示新 `change_revision` 评审通过（如“我评审通过”），即作为该 revision 的评审结论收口，不再要求独立 reviewer 复审；记录用户原话、对应 revision 和时间。
- 用户没有这样表态时，正式门禁（approved/waived 要求代码评审，或用户要求正式审批）下的定点复审由满足委派契约的独立 reviewer 在新 `change_revision` 上执行并形成新的轮次记录；用户页面复核只作为验证证据。
- 建议审查或 direct 任务未要求代码评审时，用户页面复核或实现者自查可以作为收口依据，但要如实标注来源。

无论哪种方式，都记录：旧 `change_revision` 与新 `change_revision`、增量 diff 范围、复核方式（重新评审 / 定点复审 / 用户评审通过 / 用户页面复核）、复核人和结果。没有记录时，交付说明里要写明“最终代码未经评审覆盖”。
