# dev-review-change

## 定位

用于在代码改动与基础验证之后，对本次变更做证据驱动的代码评审。

它是代码评审阶段的主入口：围绕当前变更识别正确性、架构、安全与稳定性风险，输出问题判断与后续动作；数据库、中间件、语言实现等重专项细节下沉到增强 skill，不在这里展开。

## 先选择评审结果类型

普通 PR、diff 或代码审查默认是**建议审查**：确认目标和 base/head（未提交改动则记录当前 diff），读取受影响上下文与已有验证，按下文核心维度和严重度给出有位置、影响与修复建议的 findings。验证未运行时说明证据限制，仍可完成静态审查。可先按 `references/ocr-evidence.md` 用 `ocr` 生成候选线索和可评审文件清单，再逐条按下文口径复核。只读审查不授权修复、提交、推送或发布评论。

建议审查不要求补造 `G`、`DEV-*`、producer 身份或审批记录，也不因缺少治理历史而转入开发/验证流程。需要文档时默认写入本产物目录的 `advisory.md`；对话输出也可。由实现者自查时明确标注自查；有独立审查结果时保留其真实来源。完成后交付问题与证据限制，不声称正式准入或自动进入收口。

只有用户明确要求正式准入、既有 approved/waived 路径要求该门禁，或任务记录明确要求**正式审批**时，才执行下面的正式 Workflow 及不可变审批契约。direct 任务要求代码审查本身不等于要求正式审批。普通建议审查不能代替已经适用的正式门禁。

## 默认产物目录

正式代码评审每轮写入 `/home/joney/docs/requirements-development/<requirement-name>/code-review/rounds/round-<N>/`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中给出评审结论时，可不创建文件
- 每轮目录不可覆盖，包含 `report.md`、`delegation-result.json` 和 `approval-record.json`；顶层 `review.md` 只能作为当前轮展示或指针
- reviewer 始终只读；编排器在 stop 后附着 runtime 身份、计算报告/委派结果指纹并生成 `approval-record-v1`

## When to Use

适合以下场景：
- 代码已改完，且已经具备最小可评审证据，如 diff、验证结果、关键上下文
- 需要判断这次改动是否可以继续合并、交付或进入收口
- 需要按正确性、架构、安全、稳定性几个维度检查本次变更
- 需要把问题按严重程度收敛，并给出可执行修复建议

不适合以下场景：
- 还在实现或调试过程中，代码尚未稳定，此时先回到 `dev-build-change`
- 正式准入且连最小验证都还没做：先转 `dev-verify-change`；普通建议审查可继续，并披露验证限制
- 需要数据库、中间件或特定语言栈的专项深挖，此时按需调用对应增强 skill

## 正式 Workflow

### 1. 明确评审对象
先确认本轮评审聚焦的是哪一批改动：
- 本次改动的目标与边界
- 变更涉及的模块、接口、数据或配置
- 已有验证结论与已知风险
- 按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md` 生成的 `gate_context G`、审批/direct/waiver 记录和待评审 `change_revision`
- `change_revision` 中全部代码 `producer_agent_refs[]`
- `change_revision` 中各 `DEV-*` 的来源、最终状态、实际写集和执行证据

若 `G`、验证对象或 `change_revision` 与当前工作区不匹配，停止代码准入结论并回最早失效阶段；不能用针对旧版本的验证或评审继续收口。

正式评审必须由 `agent-tools-change-reviewer` 或满足同一契约的独立 agent 执行，并遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/delegation-contract.md`。身份、只读、写入、工具面和结果结构的准入只以该契约为准；任何一项无法由运行时事实证明时，不得形成准入事实。编排器冻结 `G`、`change_revision`、diff 和验证证据，只传原始任务、冻结输入及上一轮待复核 findings，不传实现者的推理过程或预期结论。

代码改动的 `producer_agent_refs[]` 必须完整且可稳定标识；根 agent 直接产出时使用会话级 ref 并在执行记录中说明其强度限制，不构成审批阻塞（见 `delegation-contract.md` §1）。

### 2. 先拿证据再下结论
优先基于可见证据评审，例如：
- diff 与受影响文件上下文
- 已执行的测试、构建或验收结果
- `DEV-*` 到实际写集、producer 和完成条件证据的映射；检查是否存在未完成 DEV、无 DEV 归属的改动或越界写入
- 已批准测试检查项 ID（内部 `TC-*`）到实现、测试/人工检查和结果证据的完整映射
- 需求、方案或实现说明中的关键约束
- 编排器提供的外部评审证据（如 `ocr` 结果）与可评审文件清单：只作候选线索与覆盖基线，逐条核实后才能成为 finding，清单中每个文件都要标记已评审或跳过原因；用法见 `references/ocr-evidence.md`

若关键证据缺失，先明确缺口，再限制结论范围，而不是把猜测写成结论。

### 3. 按核心维度评审
默认围绕以下四类问题展开：
- 正确性：逻辑、边界、异常路径、状态一致性
- 架构：分层、职责、复用、改动边界是否失控
- 安全：输入处理、权限、敏感信息、危险用法
- 稳定性：失败处理、回退路径、可观测性、发布风险

复杂度、冗余与严重度的统一判定口径见 `references/severity-and-complexity.md`。只报告有当前变更证据和实际影响的问题，不把个人风格偏好升级为 finding。

### 4. 收敛问题与建议
对发现的问题给出：
- 稳定 ID（如 `CR-001`）与内容指纹；问题、证据或影响实质变化时更新指纹
- 对象引用：优先绑定相关 `DEV-*`、文件或代码位置
- 根因类型：`实现问题` / `清单缺口` / `方案缺口` / `需求缺口` / `材料缺口`
- 证据位置
- 问题判断
- 影响范围
- 严重程度
- 建议动作
- 关闭条件与状态：`Open` / `Resolved` / `Accepted`

`Resolved` 必须有满足关闭条件的当前 `change_revision` 证据；`Accepted` 仅允许用于 Medium，且必须绑定精确 finding ID/指纹、当前 `G`、`change_revision`、条件和用户授权引用。High 不接受风险放行。

严重度、复杂度和风险接受均按 `references/severity-and-complexity.md` 判断，每条 finding 写入前先过该文件的写入前自检。代码评审有意只使用 High / Medium / Low：最高行动等级 High 已要求必须修复且不得接受；根因类型另行决定最早恢复阶段，不是严重度的替代字段。Medium 只有在用户对精确 finding、`G`、`change_revision` 和条件明确授权后才可进入复核。

### 5. 输出评审结论

先确认评审执行状态为 `valid`。独立 reviewer 无法启动、超时或返回无效结果时，可在相同冻结输入上换一个新 reviewer 重试一次；再次失败则返回 `formal_reviewer_unavailable`，不生成领域结论。有效 reviewer 给出“修复后再评”等结论属于正常结果，不得更换 reviewer 刷取通过。

最终明确：
- 唯一结论：`可继续推进` / `修复后再评` / `带风险接受` / `证据不足`
- 哪些问题必须先处理
- 哪些问题可后续跟进
- 是否需要转专项增强 skill 深挖

- `可继续推进`：没有 Open High/Medium；Open Low 已记录后续动作
- `修复后再评`：存在 Open High，或未经匹配授权的 Open Medium
- `带风险接受`：没有 Open High，剩余 Medium 均已按当前 finding 指纹、`G` 和 `change_revision` 获得用户授权并标为 `Accepted`
- `证据不足`：缺少判断当前代码是否可交付所必需的验证或材料，且尚不能形成实现 finding

默认按“结论 → 高/中 findings → 低严重度建议 → 验证与证据 → 后续动作”输出。每个 finding 使用 `ID / 指纹 / 根因类型 / 状态 / 问题 / 证据 / 影响 / 建议 / 关闭条件`；正式落盘时使用 `references/review-template.md`。

用户风险授权不是编排器修改状态或结论的许可。获得授权后，编排器必须保持同一组冻结 `(G, change_revision)`，连同新增授权记录重新派发独立 reviewer，由其核对绑定和条件后决定是否标记 `Accepted` 并给出 `带风险接受`；编排器不得机械改写原结论。

### 6. 按根因路由最早失效阶段

本节只定位根因和建议恢复阶段，不授权自动跳转。若由 `dev-auto-loop` 编排，交付阶段发现需求、方案或测试清单级缺陷时必须遵循其止损规则，停止为 `awaiting_human`，不得自动跨段回跳。

- `实现问题` → `dev-build-change`；修复并验证新的 `change_revision` 后复审
- `清单缺口` → `dev-derive-test-cases`，新 `C` 独立复核后再实现、验证和代码评审
- `方案缺口` → `dev-design-solution`，新 `S` 独立评审后重新生成下游产物
- `需求缺口` → `dev-clarify-task`；形成新 `R` 后重新执行受影响门禁
- `材料缺口` → 补齐材料；缺验证证据时转 `dev-verify-change`

多个根因并存时路由到最早失效阶段；旧的下游审批记录和验证证据不得继续放行。

## 评审原则

- 只评审本次变更，不把范围扩成对整个系统做全面审计
- 结论基于证据，不基于想象中的理想实现
- 先关注会影响正确交付的关键问题，再讨论优化项
- 若代码虽能工作，但明显存在可删除的重复、冗余防御式代码或过度工程化结构，应明确指出并给出简化方向
- 对高严重度问题要说明为什么严重，以及建议怎么处理
- 轻量主入口只保留通用判断骨架，不承载栈专项细节

## 正式准入输出物

默认输出一份轻量评审结果，建议包含：
- 评审对象：`G`、`change_revision`、验证证据引用和本轮范围
- 开发项证据：`DEV-*` 状态、实际写集归属及对应 producer
- 结论概览：四种唯一结论之一，以及一句话依据
- 高严重度：带稳定 ID/指纹、状态和关闭条件的必须处理问题；没有则明确写无
- 中严重度：带相同身份字段的本轮优先问题及匹配风险授权（如有）
- 低严重度 / 建议：不阻断但值得记录的优化项
- 验证与证据：本次评审参考了哪些 diff、测试、覆盖率或上下文
- 外部评审证据：`ocr` 结果引用、provider/model 与逐文件覆盖表；未使用时写无
- 后续动作：下一步先做什么、是否需要补验证或专项复查
- 严重度口径：本次高/中/低分别基于什么标准判定，避免误把一般优化项写成阻塞项

## 正式准入结果要求

一份合格的评审结果应满足：
- 能看出结论建立在当前变更证据之上
- 能确认范围内 DEV 已完成或有有效 Skipped 依据，实际改动均有 DEV 归属且未越界
- 能通过 `approval-record-v1` 确认全部代码 producer、真实 reviewer、身份不相交、有效工具面只读且 reviewer 未写入工作区
- 每个 finding 都能被稳定引用、复核关闭，并防止旧授权跨 `G` 或 `change_revision` 复用
- 缺证据但尚无实现 finding 时使用 `证据不足`，不伪装成代码修复结论
- 能区分阻断问题、重要问题和一般建议
- 能对复杂度、重复代码、过度抽象、重复判空等常见设计问题给出清晰判断
- 能说明高/中/低的判定依据，避免严重度漂移
- 能按“结论优先、阻断优先、证据支撑、动作明确”的结构输出，便于研发快速消费
- 能指导下一步修复、复验或收口
- 保持轻量，不内嵌数据库、消息、缓存或特定语言栈的大段细则

## 可选增强

- 如涉及数据库结构、SQL、事务或数据一致性专项，可调用 `review-db-change`
- 如涉及缓存、消息、任务调度、外部依赖可靠性等专项，可调用 `review-middleware-reliability`
- 如涉及 Java 服务实现模式、分层约定或语言惯用法专项，可调用 `lang-java-service-patterns`
- 需要外部评审工具作为候选线索或逐文件覆盖基线时，按 `references/ocr-evidence.md` 调用 `ocr`；其结果不能替代独立 reviewer 的结论

## 交接建议

- 按 finding 根因类型回到第 6 节规定的最早失效阶段，不把上游缺口一律当作实现问题
- `证据不足` → 缺验证证据时回 `dev-verify-change`；缺外部材料时报告材料缺口和恢复条件
- 若结论为 `可继续推进`，或独立 reviewer 在相同冻结输入上确认 `带风险接受`，携带 `G`、`change_revision`、验证证据和 `approval-record-v1` 的 ref/fingerprint 进入 `dev-finish-branch`
- `formal_reviewer_unavailable` → 补齐独立 reviewer 能力后，在同一冻结输入上重新执行正式评审
