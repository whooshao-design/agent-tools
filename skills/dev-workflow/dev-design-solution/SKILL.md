# dev-design-solution

## 定位

用于在需求已基本明确后，结合代码证据形成可评审、可实施、可验证的技术方案。

它是技术方案设计阶段的主入口：负责分析现状、比较有意义的候选路径、收敛推荐方案，并明确影响、风险和验证路径；不替代需求澄清、正式技术方案评审或代码实现。

方案的层级、变更单元、内容唯一归属、追踪闭环与篇幅预算统一遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/solution-structure-contract.md`。

默认只读取需求、代码和配置并输出方案，不修改业务代码。只有用户明确要求落盘时才创建方案文档。

## 默认产物目录

正式方案默认放到 `/home/joney/docs/requirements-development/<requirement-name>/solution-design/solution.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中收敛方案时，不创建文件
- 落盘时使用 `references/solution-template.md`，删除不适用章节，不保留空占位
- 修订已存在的 `solution.md` 前，先把旧版本归档到 `solution-design/versions/solution-v<旧版本号>.md`（文件名取自文档内的方案版本号），再修改 `solution.md` 本体并递增方案版本；首次成案、还没有旧版本时不创建 `versions/` 目录，也不写"变更记录"这节
- 设计方只维护 `Draft` / `Reviewing` 状态，不自行把方案标成 `Approved`；审批事实只来自 `dev-review-solution` 针对 `(R,S,B)` 形成的不可变 `approval-record-v1`，顶层 `review.md` 仅作展示或最新轮次指针

## When to Use

适合以下场景：

- 需求目标、范围和验收标准已基本明确，需要决定怎么实现
- 需要基于现有代码、接口、数据或配置形成技术方案
- 存在实质性技术取舍，需要比较候选路径并给出推荐结论
- 编码前需要明确改动边界、异常路径、风险和验证方式

不适合以下场景：

- 需求边界或验收标准仍不清楚，此时先转 `dev-clarify-task`
- 已有完整技术方案，需要独立评审，此时转 `dev-review-solution`
- 实现路径已明确且用户要求直接编码，此时转 `dev-build-change`

## Workflow

### 1. 确认设计输入

至少确认：

- 目标、In Scope、Out of Scope 与验收标准
- 遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md` 的稳定需求身份 `R`，以及可稳定引用的验收标准 ID；缺少编号时先补 `AC-001` 这类稳定 ID
- 兼容性、权限、时效、数据、发布等已知约束
- 可读取的代码上下文、相关模块、相似实现和仓库约定
- 同一共享契约定义的实现前代码基线 `B`

若未知项会改变范围、核心行为或方案方向，先请求确认或回退 `dev-clarify-task`；低风险、可逆的未知项可以作为显式假设继续分析。

### 2. 建立现状与证据

聚焦最小必要上下文：

- 当前模块职责、调用链、数据流或状态流
- 现有可复用模式、接口契约、配置与限制
- 可能受影响的模块、文件、数据结构和上下游
- 支撑结论的代码、配置、数据或文档证据

本步骤只描述已有行为和约束，不夹带目标方案。明确区分已确认事实、设计假设和待确认事项，不把推测写成事实；长调用链、SQL、日志和完整核验结果只保留引用，正文放入附录或独立证据文件。

### 3. 生成有意义的候选方案

存在实质性取舍时为关键决策分配 `DEC-*`，给出 2-3 个候选方案并比较：

- 改动范围与实现复杂度
- 与现有模式和架构边界的一致性
- 兼容、迁移、回滚和验证成本
- 正确性、稳定性与后续演进风险

若明显只有一个合理的最小方案，不为凑数制造陪跑方案；说明其他路径为何不成立即可。

### 4. 先给结论，再按变更单元展开

先写一页结论，使用 3–5 句话分别说明问题和核心方案，并列出主要收益、代价、风险与阻塞项；它只是导航摘要，不产生正文没有的新事实。

然后建立完整变更地图。每个独立行为变化分配稳定 `CHG-*`，动作只取 `新增` / `修改` / `删除` / `保持不变`，并绑定需求/约束来源、影响模块和验收标准。详细设计只按 `CHG-*` 分节，每节依次说明现状、调整、调整后行为、不变项、异常/兼容边界和验证方式；接口、数据、配置、并发等横切维度放入相关 CHG，不与模块或变更项并列。

跨多个 CHG 的公共决策只在对应 `DEC-*` 解释一次，其他位置引用；只展开当前需求相关维度，不把方案写成现有系统说明书或通用架构百科。

若本次是针对已评审方案的修订（收到 `dev-review-solution` 的“修改后复审”或“退回重设计”结论，或
`dev-review-test-cases` 的“方案缺口”结论），
递增文档信息中的方案版本，在“变更记录”记录上一版 `S`、触发 finding、受影响的 `DEC-*` / `CHG-*` /
`RISK-*`、改动位置和处理结论。需要定点复审时同时提供新旧方案差异和影响范围；定点复审仍须执行全局结构、
追踪与非回归检查，无法证明未受影响范围稳定时必须完整复审。

### 5. 建立验证与评审入口

- 建立 `AC-* → CHG-* → 验证方式/预期结果/失败信号` 追踪；每个 CHG 都必须有来源、影响对象和验证入口
- 按相关性检查接口、数据、配置、异常、并发、兼容、安全、观测、发布与回滚；不适用项写明理由，不制造空章节
- 明确失败信号、重点回归点和未验证风险
- 区分阻塞问题与非阻塞开放问题
- 标明 `R`、方案版本、`B` 和评审所需证据；交付评审前在 handoff 中计算最终方案身份 `S`，其指纹保存在审批记录而不写回方案本体
- 记录所有实质参与方案内容生成或修订的 `producer_agent_refs`；仅做字节不变的持久化不算 producer
- 已存在用户预授权风险时，记录授权来源、适用范围、生效前提和到期条件；只有 `dev-review-solution` 对当前 `(R,S,B)` 复核后才能登记为 `Accepted`

## 设计原则

- 先尊重现有代码模式，再考虑新增抽象
- 优先当前需求下的最小可行方案，避免为假设中的未来过度设计
- 结论基于需求和代码证据，不基于理想化架构偏好
- 方案既要说明怎么做，也要说明为什么这样做和如何证明成立
- 现状集中描述，变更优先展示；同一事实只保留一个权威位置，摘要和矩阵只引用正文
- 每个父章节使用一个划分维度，同级内容保持相同抽象层级；横切关注点用矩阵而不是重复章节
- 不在设计阶段越权修改业务代码

## 输出模式

### 对话模式

默认按“一页结论 → 变更地图 → 必要细节 → 验证与风险”给出轻量方案；路径明确时不展开完整模板。

### 文档模式

用户要求正式方案或落盘时，使用 `references/solution-template.md`。删除不适用章节；正文目标不超过约 300 行，长 SQL、日志、调用链、完整数据核验和大段清单放入附录，超过约 450 行时拆为独立证据文件。

## 结果要求

一份合格的结果应满足：

- 能指导后续编码，而不只停留在概念层
- 一页结论可以快速说明问题、方案、主要变更和最大风险
- 现状与新增/修改/删除/不变项明确分离，变更地图与详细设计的 `CHG-*` 集合一致
- 能解释关键设计决策和被排除路径
- 能看出影响边界、异常路径、风险和验证重点
- 每个验收标准都能追踪到变更项和验证信号，每个变更项都有来源且没有重复事实源
- 能区分事实、假设、阻塞问题与非阻塞开放问题
- 已达到可交给 `dev-review-solution` 独立评审的完整度

## 交接建议

- 方案达到可评审状态时，冻结 `S` 和 `producer_agent_refs`，由另一个独立 agent 执行 `dev-review-solution`
- 评审要求修改或重设计时，根据 findings 更新方案后重新评审
- `dev-review-solution` 对当前 `(R,S,B)` 给出 `通过`，或基于匹配授权给出 `有条件通过` 后，转 `dev-derive-test-cases`
- 只有正式门禁原本适用且用户明确要求跳过时，才可生成不可变 `waiver-record-v1`、校验门禁枚举与依赖闭包，并携带引用它的 `G={mode: waived,W:{ref,fingerprint}}` 转 `dev-build-change`；从未进入正式治理的普通任务使用 `direct` 上下文，不在设计阶段伪造 waiver
- 若争议仍集中在需求边界而非实现本身，回退 `dev-clarify-task`
