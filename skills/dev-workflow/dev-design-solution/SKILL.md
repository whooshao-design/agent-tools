# dev-design-solution

## 定位

在需求已基本明确后，结合代码证据形成可评审、可实施、可验证的技术方案。它负责分析现状、收敛技术决策、解释目标机制及其正确性，并明确影响、发布、风险和验证；不替代需求澄清、正式方案评审、详细测试清单或开发执行清单。

默认只读取需求、代码和配置。只有用户明确要求落盘时才创建或修改方案文档，不在设计阶段改业务代码。

方案结构、内容归属、追踪和可读性统一遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/solution-structure-contract.md`。

## 参考资料路由

不要一次加载所有 reference：

- 每次先读 `references/template-routing.md`，判断是否需要正式方案并选择一个主 profile。
- 输出正式文档时读 `references/solution-template.md`、`references/design-dimensions.md`、`references/readability-and-writing.md` 和选中的 `references/profiles/<profile>.md`。
- 关系、顺序、分支、状态、层级或部署映射确实需要图时，再读 `references/visualization-routing.md`。
- 路径明确且无需正式方案时，转 `dev-build-change`，不加载完整模板和 profile。

## 默认产物目录

正式方案默认放到 `/home/joney/docs/requirements-development/<requirement-name>/solution-design/solution.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名；用户指定路径时优先使用。
- 只需在对话中收敛方案时不创建文件。
- 落盘使用统一核心模板，只装配一个主 profile，删除不适用章节和占位。
- 修订已有 `solution.md` 前，把旧版本归档到 `solution-design/versions/solution-v<旧版本号>.md`，再递增方案版本；首次成案不创建 `versions/`，也不写变更记录。
- 设计方只维护 `Draft` / `Reviewing`，不得自行标记 `Approved`。审批事实只来自 `dev-review-solution` 针对 `(R,S,B)` 形成的不可变 `approval-record-v1`。

## When to Use

适合：

- 需求目标、范围和验收标准已基本明确，需要决定如何实现；
- 需要基于现有代码、接口、数据或配置形成正式方案；
- 存在实质技术取舍，或需要明确机制、迁移、契约、数据状态、发布及验证风险。

不适合：

- 需求边界或验收标准不清楚：转 `dev-clarify-task`；
- 已有完整方案，需要独立评审：转 `dev-review-solution`；
- 实现路径唯一且风险可直接从完成标准得出：转 `dev-build-change`。

## Workflow

### 1. 冻结设计输入与范围事实源

至少确认目标、In Scope、Out of Scope、稳定 `AC-*`、已知约束、代码基线 `B`、相关代码上下文，以及符合 `artifact-identity.md` 的需求身份 `R`。

明确哪份产物定义变更范围，记录其 `ref + fingerprint`、条目枚举或计数、非目标与裁定人。当范围事实源是 agent 自建的脚本、扫描器或清单，或 `R` 缺少带稳定 ID 的验收标准时，必须先由用户裁定它是“范围事实源”还是“定位辅助工具”；未裁定不得进入正式评审。

会改变范围、核心行为或方案方向的未知项必须先确认或回退需求澄清；低风险、可逆未知项可以作为显式假设继续。

### 2. 建立最小必要现状与证据

只收集理解本次决策需要的当前职责、调用/数据/状态流、可复用模式、限制和影响对象。现状章节不夹带目标方案；事实、假设和待确认事项必须区分，长调用链、SQL、日志和完整核验结果放附录或独立证据文件。

上游事实必须标注可复核来源。对“0 命中、无消费方、无影响”等负向断言，至少使用两条相互独立的检索路径；单一路径结论只能记为待复核。全称断言同时遵循结构契约中的可复现规则。

### 3. 路由文档粒度和主 profile

按 `template-routing.md` 先判断是否需要正式方案。正式方案只选择一个主要正确性问题：

- `mechanism-architecture`（机制/架构型）：证明多个运行时参与者协作后机制仍正确；
- `migration-remediation`（迁移/整改型）：证明现状能安全切换到目标状态且不漏不误；
- `contract-evolution`（契约演进型）：证明新旧生产方和消费方在版本窗口内兼容；
- `data-state-consistency`（数据/状态型）：证明数据、状态和事务在并发及失败下保持不变量。

多项命中时选择风险最高、最影响正确性结论的一项，其他问题作为横切维度写回相关机制；不得拼接多份 profile。`CHG-*` 默认只做交付追踪，不控制正文叙事。

### 4. 收敛推荐方案

存在实质取舍时为关键决策分配 `DEC-*`，比较 2–3 个真实候选的正确性、现有边界一致性、复杂度、兼容/迁移/回滚成本和演进风险。明显只有一个合理最小路径时，不制造陪跑方案，只说明其他路径为何不成立。

先建立七个读者问题和横切相关性矩阵，再写正文。这样完整性由覆盖地图保证，不需要把检查项全部扩写为章节。

### 5. 先建立理解，再提供实现精度

一页结论只回答问题与影响、推荐方案、主要机制变化、最大代价/风险和阻塞状态，不放完整 CHG 清单，也不产生正文没有的新事实。

第 4 章按选中 profile 使用 guide → reference 顺序：先用机制导读和代表性场景建立心智模型，再说明参与者、契约、状态、时序、不变量、失败、兼容和边界；最后解释这些细节为何能保证代表性场景成立。标题使用技术机制或状态变化，不使用文件名、`CHG-*`、“处理逻辑”或“其他”作为主叙事。

正文只展开本次变化、违反直觉、高风险、存在争议、影响正确性或缺少细节会导致不同实现的内容。接口、数据、配置、并发、安全、性能和观测按相关性写回对应机制，不创建重复事实源。

### 6. 建立交付追踪与评审入口

- 为独立交付行为分配 `CHG-*`，动作只取 `新增` / `修改` / `删除` / `保持不变`。
- 建立 `AC → 设计正文 → CHG → 验证信号 → 发布/回滚`；每个 CHG 都有来源、影响对象和验证入口。
- CHG 完整清单放附录；逐文件对象、工时、负责人、commit 和开发批次交给 `dev-build-change`。
- 区分阻塞问题、非阻塞开放问题和已授权风险；记录完整 `producer_agent_refs[]`。
- 交付评审前在 handoff 计算最终方案身份 `S`；指纹进入审批记录，不写回方案本体。

若是评审后修订，递增版本并记录上一版 `S`、触发 finding、受影响的 `DEC/CHG/RISK`、修改位置和结论。关闭 finding 时优先删除或收窄不成立的断言；确需新增全称断言时附可复跑检索命令。定点复审仍需提供新旧方案差异和影响范围，并执行全局结构、追踪与非回归检查。

### 7. 输出前自检

按 `readability-and-writing.md` 执行 30 秒、5 分钟、标题、双读者、删除、唯一归属、完整性和范围隔离测试。篇幅阈值只触发结构复核，不因行数自动通过或失败。

方案必须能交给 `dev-review-solution` 独立评审：reviewer 不读附录也能理解机制、影响和上线验证，深读时能定位精确契约、边界、证据及所有 CHG。

## 输出模式

### 对话模式

默认按“结论 → 推荐方案与机制导读 → 必要精度 → 验证与风险”输出。路径明确时保持轻量，不展开完整模板。

### 文档模式

用户要求正式方案或落盘时使用统一核心模板和一个主 profile。长证据、完整对象清单和执行内容移出正文；正文超过约 300 行时复核是否重复或混入错误内容，超过约 450 行时优先拆分证据，不机械删减必要设计。

## 交接建议

- 方案达到可评审状态时冻结 `S` 和 `producer_agent_refs`，交由独立 `dev-review-solution`。
- `通过` 或有效的 `有条件通过` 后转 `dev-derive-test-cases`。
- `修改后复审` / `退回重设计` 时按 findings 修订；需求边界争议回退 `dev-clarify-task`。
- 只有用户明确豁免原本适用的正式门禁时才生成 `waiver-record-v1`；普通直接任务使用 `direct` 上下文，不伪造 waiver。
