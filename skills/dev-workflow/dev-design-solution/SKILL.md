# dev-design-solution

## 定位

用于在需求已基本明确后，结合代码证据形成可评审、可实施、可验证的技术方案。

它是技术方案设计阶段的主入口：负责分析现状、比较有意义的候选路径、收敛推荐方案，并明确影响、风险和验证路径；不替代需求澄清、正式技术方案评审或代码实现。

默认只读取需求、代码和配置并输出方案，不修改业务代码。只有用户明确要求落盘时才创建方案文档。

## 默认产物目录

正式方案默认放到 `/home/joney/docs/requirements-development/<requirement-name>/solution-design/solution.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中收敛方案时，不创建文件
- 落盘时使用 `references/solution-template.md`，删除不适用章节，不保留空占位
- 修订已存在的 `solution.md` 前，先把旧版本归档到 `solution-design/versions/solution-v<旧版本号>.md`（文件名取自文档内的方案版本号），再修改 `solution.md` 本体并递增方案版本；首次成案、还没有旧版本时不创建 `versions/` 目录，也不写"变更记录"这节
- 设计方只维护 `Draft` / `Reviewing` 状态，不自行把方案标成 `Approved`；审批事实以 `dev-review-solution` 针对“方案路径 + 方案版本 + 需求版本 + 代码基线”产出的正式报告或带消息引用的结构化对话结果为准

## When to Use

适合以下场景：

- 需求目标、范围和验收标准已基本明确，需要决定怎么实现
- 需要基于现有代码、接口、数据或配置形成技术方案
- 存在实质性技术取舍，需要比较候选路径并给出推荐结论
- 编码前需要明确改动边界、异常路径、风险和验证方式

不适合以下场景：

- 需求边界或验收标准仍不清楚，此时先转 `dev-clarify-task`
- 已有完整技术方案，需要独立评审，此时转 `dev-review-solution`
- 实现路径已明确且用户要求直接编码，此时转 `dev-build-change`

## Workflow

### 1. 确认设计输入

至少确认：

- 目标、In Scope、Out of Scope 与验收标准
- 需求版本，以及可稳定引用的验收标准 ID；缺少编号时先补 `AC-001` 这类稳定 ID
- 兼容性、权限、时效、数据、发布等已知约束
- 可读取的代码上下文、相关模块、相似实现和仓库约定

若未知项会改变范围、核心行为或方案方向，先请求确认或回退 `dev-clarify-task`；低风险、可逆的未知项可以作为显式假设继续分析。

### 2. 建立现状与证据

聚焦最小必要上下文：

- 当前模块职责、调用链、数据流或状态流
- 现有可复用模式、接口契约、配置与限制
- 可能受影响的模块、文件、数据结构和上下游
- 支撑结论的代码、配置、数据或文档证据

明确区分已确认事实、设计假设和待确认事项，不把推测写成事实。

### 3. 生成有意义的候选方案

存在实质性取舍时给出 2-3 个候选方案，并比较：

- 改动范围与实现复杂度
- 与现有模式和架构边界的一致性
- 兼容、迁移、回滚和验证成本
- 正确性、稳定性与后续演进风险

若明显只有一个合理的最小方案，不为凑数制造陪跑方案；说明其他路径为何不成立即可。

### 4. 收敛并展开推荐方案

明确推荐结论、选型理由和被排除方案，补齐：

- 模块职责、主流程和关键调用关系
- 接口、数据、状态、配置或事务变化
- 正常路径、异常路径、边界条件和失败恢复
- 与需求相关的并发、幂等、性能、安全、可观测性、发布和回滚设计

只展开与当前需求相关的维度，不把方案写成通用架构百科。

若本次是针对已评审方案的修订（收到 `dev-review-solution` 的“修改后复审”或“退回重设计”结论，或
`dev-review-test-cases` 的“方案缺口”结论），
递增文档信息中的方案版本，在“变更记录”补一行本次版本的触发原因和摘要，并对每条被处理的 finding ID
注明改动位置和处理结论，使评审方可以只复核指定 findings 而不必通读全文。

### 5. 建立验证与评审入口

- 将每个验收标准 ID 映射到测试、检查或可观察信号
- 明确失败信号、重点回归点和未验证风险
- 区分阻塞问题与非阻塞开放问题
- 标明需求版本、方案版本、代码基线和评审所需证据
- 已存在用户明确接受的风险时，记录授权来源、适用范围、生效前提和到期条件；不得把设计方建议写成已接受

## 设计原则

- 先尊重现有代码模式，再考虑新增抽象
- 优先当前需求下的最小可行方案，避免为假设中的未来过度设计
- 结论基于需求和代码证据，不基于理想化架构偏好
- 方案既要说明怎么做，也要说明为什么这样做和如何证明成立
- 不在设计阶段越权修改业务代码

## 输出模式

### 对话模式

默认给出轻量结论：目标与边界、候选取舍、推荐方案、影响范围、主要风险、验证路径和开放问题。

### 文档模式

用户要求正式方案或落盘时，使用 `references/solution-template.md`。正文结论前置；长 SQL、日志、完整数据核验和大段清单放入附录。

## 结果要求

一份合格的结果应满足：

- 能指导后续编码，而不只停留在概念层
- 能解释关键设计决策和被排除路径
- 能看出影响边界、异常路径、风险和验证重点
- 能区分事实、假设、阻塞问题与非阻塞开放问题
- 已达到可交给 `dev-review-solution` 独立评审的完整度

## 交接建议

- 方案达到可评审状态时，转 `dev-review-solution`
- 评审要求修改或重设计时，根据 findings 更新方案后重新评审
- `dev-review-solution` 对当前需求版本、方案版本和代码基线给出 `通过`，或基于用户明确授权给出 `有条件通过` 后，转 `dev-derive-test-cases`
- 只有用户明确要求同时跳过方案评审和测试场景链路时，才可直接转 `dev-build-change`，并显式记录被跳过的门禁与风险
- 若争议仍集中在需求边界而非实现本身，回退 `dev-clarify-task`
