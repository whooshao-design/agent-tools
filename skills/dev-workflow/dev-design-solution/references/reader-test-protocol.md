# 读者测试协议 reader-test-v1

读者测试检验一份 `solution.md` 能否被没有背景的读者独立理解。它不评判技术正确性，那是 `dev-review-solution` 的事。每个进入正式评审的方案版本先做一次 agent 读者测试；进入人评审会之前，用户再做一次人的读者测试。

## 1. 输入

读者只拿到 `solution.md` 的正文。把它单独复制到一个空目录，不给 `traceability.md`、证据文件、需求文档、评审记录或任何会话上下文。

## 2. 问题

七个固定问题，对应方案必须回答的读者问题：

1. 要解决什么问题，证据是什么？
2. 目标、非目标与约束是什么？
3. 最终选了什么方案，为什么不选主要的替代路径？
4. 目标机制怎样工作，正常和失败情况下凭什么成立？
5. 哪些东西改变，哪些明确不变？
6. 如何发布、验证和回滚？
7. 剩余风险与未决问题有哪些？

三个探针，用来暴露读者答对了也可能存在的问题：

- 哪些地方有歧义或读不懂？
- 文档假设读者已经知道什么？
- 文档前后有没有矛盾？

## 3. 答案键

设计方在派发读者测试之前写 `solution-design/reader-test/answer-key-v<N>.md`：一张表，列为问题、预期答案、所在章节。答案键不进入方案正文，也不给读者。它的作用是让比对有依据，避免由读者自评"是否理解"。

## 4. agent 读者

- 新会话，与设计方不同的模型。模型对自己写的文本有系统性偏好，同模型读自己的方案会高估可读性。优先选实测能发现结构问题的后端，选模用 `skills/common/build-codeagent/scripts/pick_agent.py quick-check` 预览。
- 工具面只有 Read，工作目录只含 `solution.md` 副本，不联网、不写文件、不委派。
- 提示词固定为本文件第 6 节的模板；每问回答不超过两句，附一句逐字引用和所在标题，找不到就写"找不到"。
- 输出只有一个 JSON 代码块，原样保存为 `reader-test/agent-v<N>.raw.json`。
- 不记录 agent 耗时，它对模型没有意义。

## 5. 比对与判定

编排器逐问比对答案键与读者回答，写 `reader-test/agent-v<N>.md`：

- 语义一致且引用能在正文中定位，记通过。
- 答案错误、写"找不到"、或引用的原文不支持答案，记不通过，并写明读者定位到的章节。
- 探针指出的歧义、假设已知、矛盾，逐条判定成立与否，成立的写处置。

任一问不通过，或探针发现的矛盾影响决策、实施或验证，作为类别"结构/可读性"的 Medium finding 进入 `dev-review-solution` 的输入。设计方修订后重新做读者测试。

## 6. agent 提示词模板

```text
你是一位第一次读到这份技术方案的后端工程师，对项目没有任何背景，也拿不到其他材料。当前目录下只有一个文件 `solution.md`，请用 Read 工具完整读一遍，然后只依据它回答下面的问题。不要搜索其他文件，不要写文件，不要猜测文档之外的信息。

七个问题，每题回答不超过两句话，并附一句原文引用（逐字复制，不超过一句）和它所在的标题；如果文档里找不到答案，答案写"找不到"，引用留空：

1. 要解决什么问题，证据是什么？
2. 目标、非目标与约束是什么？
3. 最终选了什么方案，为什么不选主要的替代路径？
4. 目标机制怎样工作，正常和失败情况下凭什么成立？
5. 哪些东西改变，哪些明确不变？
6. 如何发布、验证和回滚？
7. 剩余风险与未决问题有哪些？

三个探针，各答一到三条，没有就写"无"：

- 哪些地方有歧义或读不懂？
- 文档假设读者已经知道什么？
- 文档前后有没有矛盾？

最后只输出一个 JSON 代码块，结构如下，代码块之后不要再写任何内容：

{"answers": [{"q": 1, "answer": "", "quote": "", "heading": ""}], "ambiguities": [], "assumed_knowledge": [], "contradictions": []}
```

Claude Code 后端的派发命令形如：

```bash
cd <只含 solution.md 的目录> && claude-<backend> -p "$(cat <prompt 文件>)" --allowedTools Read \
  --disallowedTools 'Bash,Write,Edit,WebSearch,WebFetch,Glob,Grep,Task' --max-turns 12 --output-format json
```

## 7. 人的读者测试

用户在人评审会之前读 `solution.md`，限时 5 分钟，填 `reader-test/human-v<N>.md`：

| 问 | 答案或"找不到" | 在哪一节找到 | 用时 |
|---|---|---|---|

七问全部能答且总用时不超过 5 分钟为通过。找不到的问题按第 5 节同样处理。

## 8. 已知局限

- 模型读者对答案位置和文档长度敏感：位于长文中部的答案更容易被判为找不到。摘要与方案概览承载七问里的大部分答案，文档长度按写作原则控制。
- 模型可能靠词汇线索答对而不是真的理解，所以要求逐字引用并核对引用是否支持答案。
- 模型对结构缺陷不如对矛盾敏感，结构问题主要靠三个探针和人的读者测试暴露。
