# 方案纲要与关键问题清单模板

`dev-design-solution` 第 4 步在写 `solution.md` 正文前生成 `solution-design/key-questions.md`。文件有两部分：第 0 节方案纲要，让用户在详细设计前看到方案的整体形状（方向、核心机制、改动范围）；第 1～4 节关键问题清单，把会改变设计的问题交用户裁定，把能从代码查到的事实先查清。文件名沿用 `key-questions.md`，因为 `review_round.py` 的机械检查和评审清单按这个文件名与第 1～4 节的编号核对。

这份文件只由用户确认：不做读者测试，不派 agent 评审，不进方案身份 `S`。用户确认的结果写进 `traceability.md` 第 2 节的确认表（见 `traceability-template.md`），评审只核对 `solution.md` 是否与已确认内容（第 0 节的方向和变更范围、确认表、第 4.1 节）一致，不评第 0 节本身写得好不好。`review_round.py freeze` 检查状态行以"状态：已确认"开头，否则报 `key_questions_not_confirmed`。对话模式或无需正式方案时不生成本文件。

## 1. 骨架

第 0 节按本模板 1.1 的写法填写；第 1～4 节每个标题下是一张 Markdown 表，没有条目的表写"无"并说明查过什么，不删标题。本文件是写正文前的工作文件，状态行就是第一屏，不另写相关文档和摘要。

### 1.1 第 0 节的写法

第 0 节是方案的缩略版，目标是让用户用 5 分钟判断方向对不对。总长不超过约 80 行；超过时删细节，不删小节。每一小节在用户确认后成为 `solution.md` 对应章节的初稿：

| 小节 | 写什么 | 确认后去向 |
|---|---|---|
| 0.1 问题与验收承接 | 问题两三句；需求的每条 `AC-*`、`CON-*` 一行，写明由哪个机制满足，有疑点的填对应 KQ。暂时没有机制满足的 AC 写"未覆盖"，并列一条待裁定 | `solution.md` 1.1、1.2 与 `traceability.md` 验收映射 |
| 0.2 一句话方案与主图草图 | 一句话方案；主图按 `visualization-routing.md` 的 profile 默认图型画草图，只画全貌，不经 `check_mermaid.js` 校验 | 2.1 |
| 0.3 候选方向与推荐 | 2 到 3 个真实候选方向，推荐项在第一行；只有一个合理方向时写一行并说明其他方向为什么不成立。有两个及以上真实候选时，方向选择必须同时是第 1 节的一条待裁定 | 2.2 的 `DEC-*` 与第 4 章 |
| 0.4 核心机制要点 | 三行固定：关键数据结构（名称、形状怎么变）、全部写入入口（写同一数据的每个入口及本方案是否覆盖）、不变量（方案要保证的条件）。每行给代码位置；详细的依赖行为在 4.1，不在这里重复 | 第 3 章核心机制小节 |
| 0.5 变更范围 | 本次新增、修改、删除的对象，粒度到应用、接口、表或字段、页面，不到方法；变更只取 `新增` / `修改` / `删除` | 2.4 变更总览 |
| 0.6 发布顺序与最大风险 | 多应用或前后端的发布顺序与兼容窗口、不可逆点、最大风险及拦住它的手段；没有顺序要求或不可逆点时写"无"并说明依据 | 第 6、7 章 |

第 0 节只写已经从代码查证的事实和设计方的推荐；还没查证的前提写"未查证"并在第 1 节列一条来源为证据缺口的问题，不写成结论。

## 2. 问题来源与筛选

按六类来源逐类过一遍，待裁定、待选型的每个问题在"来源"列写出类别和具体编号（设计方已定的条目在理由里写依据，不设来源列）：

| 来源 | 从哪里找 |
|---|---|
| AC 或 CON | 需求的每条 `AC-*`、`CON-*`：实现方式不唯一、或方案做法与原文不一致的地方；相对需求的偏差填被偏离的编号 |
| 主 profile 的核心证明 | 选中 profile 要证明的正确性问题（并发、迁移、兼容、协作）里需要取舍的点 |
| 横切维度 | `design-dimensions.md` 横切矩阵里本方案命中的维度 |
| 证据缺口 | 查证时读不到代码或日志、只能靠假设的前提 |
| 不可逆点 | 上线后不能靠还原代码撤回的动作：数据迁移、发布给其他团队或外部系统调用的契约、删除数据或配置、通知外部方。同一需求内随版本一起发布、可一起回滚的前后端接口不算 |
| 需求开放问题 | 需求文档列出的未关闭问题，以及需求里写明留给方案阶段决定的事项（如"接口形式在方案阶段与前端商定"） |

能从代码、配置、日志或文档查到的事实不交给用户，直接查清写进第 4 节。其余问题按答案影响什么分节：答案会改变用户看到的行为、范围或 AC 的可验证行为，需要业务判断，属于不可逆点，或是 0.3 有两个及以上真实候选时的方向选择（来源写"主 profile 的核心证明"）的，进待裁定；组件选型进待选型；只影响内部实现、不改变用户看到的行为的，由设计方决定，进设计方已定。

分节规则：

- 待选型只收引入、替换或移除组件、依赖库、存储、中间件的选择，以及改错后返工成本高的选择。用户确认的待选型照 `dev-design-solution` 第 5 步写成选型 `DEC-*` 与第 4 章选型对比表。
- 其余实现选择由设计方决定，写进第 3 节"设计方已定"并给理由，不阻塞；用户读清单时可以推翻。
- 待裁定超过 7 条时先检查需求边界是否未收敛：是则交互运行回 `dev-clarify-task`，auto-loop 下返回 `awaiting_human` 并说明需求未收敛；否则按影响排序全部列出。
- 待裁定与待选型都为空时，仍生成本文件并交用户确认第 0 节（第 0 节和第 4 节是写正文的前提），并在第 1、2 节按六类来源逐类写"已查，无"，让"查过没有"与"没查"能区分。

## 3. 字段规则

| 部分 | 含义与格式 | 特殊值 |
|---|---|---|
| 状态行 | 文件状态（覆盖第 0 节和第 1、2 节）、对应需求版本、主 profile、核心机制 | 需求在对齐期间被改时，状态行的需求版本与当前不同，重新对照 0.1 和 4.3 |
| `ID` | `KQ-01` 起编号，第 1～3 节共用一个序列；第 4 节不编号 | 无 |
| 来源 | 第 2 节六类之一，并写出具体编号 | 无 |
| 默认答案 | 设计方推荐的答案，用户不作答即采用 | 不允许为空；万一为空，该条目在 auto-loop 下按"auto-loop 停"为是处理，评审记为缺陷 |
| auto-loop 停 | `是`：答案会改变范围或 AC，或属于不可逆点，相对需求的偏差一律为是；`否`：只在需求允许的范围内选择。只在第 1、2 节有这一列 | 空值按 `是` 处理 |
| 4.1 依赖行为 | 只列核心机制依赖的现有方法、组件和外部输入；其他机制的依赖写正文时写进 `solution.md` 第 3 章各自小节，不进清单。代码依赖的情形从成功有数据、成功为空、目标不存在、抛异常、超时、部分成功中取，用到哪种写哪种；没写的情形在"区分与处理"列用一句话合并说明为什么不会出现（例如"纯本地计算，无超时"），不必六种逐行列出。非代码依赖（用户回复、需求文档、`producer-stage-result-v1` 这类上游结果结构）写它自己的状态名，并在"区分与处理"列写判定方法 | 证据列：代码依赖写代码或日志位置；非代码依赖写其行为定义所在位置，现有文件写文件位置，本方案新定的规则写"本方案规则：<章节>"；本地查证不了的写"未查证：<原因>；查证方法：<怎么查>"，影响设计时以"证据缺口"为来源列一条问题 |
| 4.2 影响面 | 每个改动对象的受影响方，附可复跑的检索命令与命中数；改动对象按各条默认答案确定，其他答案会改变影响面时写在该 KQ 的"不同答案对设计的影响"列。跨制品时按"目标坐标持有者 → 锁定持有者版本的制品 → 可达性"多跳枚举，每一跳一条命令和命中数，例如先 `rg -l '<artifactId>' --glob pom.xml` 找持有者，再对每个持有者的坐标重复检索 | 负向结论（0 命中）至少两条独立检索路径 |
| 4.3 是否偏差 | `是` 时必须对应一条待裁定 | 没有偏差时写已对照的 AC 范围 |

确认表"改变需求"一栏写 `是，需求 v<N>` 时，写正文前要判断"需求已升到所需版本"：冻结的需求版本不低于表中所写。比较时两边去掉前缀 `v`，按 `.` 分段逐段比整数，缺的段按 0 计（`v1.10` 高于 `v1.9`，`v1.2` 等于 `v1.2.0`）；任一边分不出整数段时按"未升到"处理。这项判断由设计方执行，只比较版本号；新版本的 AC 原文是否体现确认答案由评审核对。

## 4. 用户回复的处理

| 情况 | 处理 |
|---|---|
| 只回复部分条目 | 未提及的条目采用默认答案，确认表逐行写明；第 0 节没有被提出异议即视为确认 |
| 回复笼统（"好的""继续""按默认"） | 本文件已经展示且回复没有提出异议，视为确认第 0 节并全部采用默认答案；确认表照录原话。回复里只要有针对本文件的表态（同意、按默认、对某条作答），就按表态处理，同一条回复里的其他话题不影响确认 |
| 对第 0 节提出修改（换方向、增减范围、改机制） | 先改第 0 节和受影响的 KQ、第 4 节查证，状态保持"待用户确认"，再次交用户确认；改动使 AC 不再被覆盖或超出需求范围时回 `dev-clarify-task` |
| 回复与清单无关，或只有半句表态 | 不视为确认，状态保持"待用户确认"，不写正文；下一轮先复述清单，请用户明确表态 |
| 会话结束没有回复 | 状态保持"待用户确认"；恢复时从清单继续 |

用户在同一会话回复后，设计方把状态行改为"已确认"并写上原话与日期，写确认表，从"需求已升到所需版本"继续；需求版本不变时不重新冻结 `R`。

## 5. 由 dev-auto-loop 派发时

派发任务要求返回带 `run_id` 的 `producer-stage-result-v1` 时按本节处理；没有这项要求或缺 `run_id` 按交互运行处理。

| 状态 | 处理 |
|---|---|
| 状态行不是"已确认" | 返回 `status=blocked`、`outcome=awaiting_human`，不采用默认答案继续 |
| 状态行已是"已确认"（用户在启动 auto-loop 前或上一次停止后确认），之后出现新的待裁定、待选型 | "auto-loop 停"为是的返回 `awaiting_human`；为否的采用默认答案在同一次派发内继续，确认表写 `auto-loop 采用默认` |
| "改变需求"为是的行，冻结的需求版本低于确认表所写 | 返回 `awaiting_human`，列出所需版本与当前版本；不在 auto-loop 内改需求 |

`output_artifacts` 每次返回都列出本次派发写过的全部文件；`produced` 只在 `solution.md`、`traceability.md` 都写出后返回。停止与恢复的编排规则见 `$AGENT_TOOLS_ROOT/skills/dev-workflow/dev-auto-loop/references/design-review-loop.md`。

## 6. 确认后的变更

第 0 节确认后是详细设计的约束。写正文或评审后修订时，出现以下任一情况就停下来，改第 0 节并重新交用户确认，确认前不继续写：

- 改用 0.3 中没有被推荐的方向，或出现 0.3 没有列出的方向；
- 0.4 的关键数据结构、写入入口覆盖范围或不变量改变；
- 0.5 增加或减少应用、对外接口、表或字段、页面；
- 0.6 的发布顺序或不可逆点改变。

只改实现细节（方法拆分、内部命名、0.5 已列对象内部的改法）不需要重新确认。auto-loop 下遇到上述情况返回 `status=blocked`、`outcome=awaiting_human`，列出变化的小节和原因。

## 7. 写正文时搬移查证结论

第 2、4 步查到的长调用链、日志和核验结果，在 `traceability.md` 写出之前先放在清单第 4 节。第 6 步写正文时，4.1 的行整行搬进 `solution.md` 第 3 章核心机制小节的依赖调用结果表，4.2、4.3 的结论进 `traceability.md` 证据清单；清单第 4 节只留"依赖 + 情形 → 章节号"或 `[E-n]` 引用，同一结论不在两处各写一份。

## 8. 小实例

取一行 0.3 候选方向、一行待裁定、一行核心机制依赖和一行影响面：

```markdown
| 复用现有终态 | 设计方返回 `awaiting_human`，编排器按现有规则停止 | 能 | 终态汇报要多列一类条目 | 推荐（KQ-01） |
| KQ-01 | `dev-auto-loop` 遇到改范围或 AC 的待裁定项停在哪个终态 | 复用现有终态 `awaiting_human` | 新增终态要改 3 处枚举和契约测试 | 需求开放问题 Q1 | 是 |
| `producer-stage-result-v1` | 返回 `awaiting_human` | `status=blocked`，编排器停止并列出决策 | 恢复条件为用户完成指定决策，决定作为新冻结输入 | `run-state-and-resume.md:60`、`:90` |
| `freeze` 增加读者测试检查 | 调用方 2 处：`dev-review-solution`（受影响）、`dev-review-test-cases`（阶段不同） | `rg -n 'freeze --artifact' skills` → 2 |
```
