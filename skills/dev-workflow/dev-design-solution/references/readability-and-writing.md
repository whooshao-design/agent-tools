# 技术方案可读性与写作规则

## 1. 三层阅读入口

同一事实不复制三遍，但要支持三种阅读深度：

| 阅读层 | 读者应得到什么 | 主要位置 |
|---|---|---|
| 决策扫描（约 30 秒） | 问题、选择、主要机制变化、最大风险、是否阻塞 | 一页结论 |
| 方案理解（约 5 分钟） | 为什么这样选、机制怎样工作、影响什么、如何上线和证明 | 方案选择、机制导读、代表性场景、发布验证 |
| 深度评审/实施 | 契约、不变量、失败边界、兼容、追踪和证据 | reference-level 设计、矩阵和附录 |

时间是体验测试，不是精确 SLA。下层增加精度，不得推翻上层表述。

## 2. Guide → Reference

第 4 章先建立心智模型，再提供实现精度：

1. 机制导读：问题本质、参与者、核心变化和为何能成立；
2. 代表性正常场景：用短流程、示例或必要主图建立直觉；
3. 实现级参考：契约、状态、时序、不变量、失败、兼容和边界；
4. 回到代表性场景，说明这些细节怎样保证结果成立。

不要让读者在理解目标机制前先处理类名、字段、配置和异常分支。

## 3. 风险驱动展开

只有符合任一条件才详细展开：

- 本次确实发生变化；
- 行为违反直觉或容易误用；
- 影响正确性、兼容性、安全、数据或发布回滚；
- 存在实质候选取舍或评审争议；
- 缺少细节会导致两个实现者作出不同实现；
- 关键假设、容量结论或全称断言需要证据。

系统历史、完整对象清单、长 SQL/日志/调用链、逐文件动作和未来设想默认压缩、引用或移出正文。

## 4. 标题、段落与术语

- 标题使用技术机制、状态变化或关键结论；不用“方案项一”“处理逻辑”“其他”“模块改动”。
- 同级标题保持同一抽象层级；只看第 4 章标题应能恢复设计推理，而不是文件清单。
- 一段只推进一个判断，首句先给结论或主题；先写正常路径，再写异常和例外。
- 优先使用“参与者 + 动作 + 对象 + 条件/结果”的具体表达，少用抽象名词串联。
- 使用代码和需求中的真实术语；一个概念只保留一个名称，新术语首次出现时定义。
- 删除没有信息增量的“综合考虑”“通过上述方案”“为了确保”“需要注意的是”等套话。
- 不设置统一中文字符数或句长硬门禁；连续短句也可能割裂，长句有时承载必要条件。

示例：

| 空泛标题 | 机制化标题 |
|---|---|
| `配置修改` | `运行时从 Hippo namespace 读取分类凭证` |
| `异常处理` | `Hippo 不可用时拒绝启动，不回退到硬编码凭证` |
| `其他改动` | 删除或按真实机制归并 |

## 5. 选择表达形式

| 信息 | 首选形式 | 避免 |
|---|---|---|
| 理由、不变量、失败语义 | 短段落 | 用表格隐藏推理 |
| 同类条件、少量步骤 | 列表 | 一个列表项塞入多个长段落 |
| 字段、版本、对象映射、追踪 | 表格 | 单元格写长篇论证 |
| 关系、顺序、状态、层级、部署 | 按需图表 | 把 CHG/文件清单画成流程图 |
| 代码、配置、完整证据 | 短代码块或附录 | 在正文粘贴大段原文 |

## 6. 唯一事实源

- 一页结论压缩正文已有结论，不增加条件和例外。
- DEC 定义选择和理由；目标设计解释落地，不重写候选比较。
- 失败语义在对应机制或契约处定义；风险章节只写残余风险。
- CHG 矩阵只做交付映射，不重新解释机制。
- 附录提供证据和明细，不产生正文没有的新方案结论。

必须在多个视图出现时，其他位置使用稳定 ID 或链接引用。

## 7. 输出前可复核测试

| 测试 | 通过条件 |
|---|---|
| 30 秒扫描 | 一页结论能回答问题、选择、主要变化、最大风险和是否阻塞 |
| 5 分钟理解 | 不读附录也能解释机制、主要影响以及怎样上线和证明 |
| 标题测试 | 第 4 章标题呈现推理顺序，不是文件/CHG 清单 |
| 双读者测试 | 新读者能建立心智模型，实施者能定位精确契约和边界 |
| 删除测试 | 每段都增加事实、理由、约束、边界或证据 |
| 唯一归属测试 | 摘要、正文、矩阵和图没有多个权威定义 |
| 完整性测试 | 所有相关维度有权威位置，AC/CHG 可追踪，N/A 有理由 |
| 范围隔离测试 | 当前方案、开放问题、未来设想、证据和 DEV 内容没有混写 |

篇幅超过约 300/450 行只触发结构复核：检查重复、系统百科、证据和执行清单；不得机械删除必要设计。
