# 技术方案可读性与写作规则

通用表达规则（第一屏、段落、列表与表格、标识与引用、标题与篇幅）在 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/writing-principles.md`，本文件只写技术方案专属的部分。

## 1. 三层阅读入口

同一事实不复制三遍，但要支持三种阅读深度：

| 阅读层 | 读者应得到什么 | 主要位置 |
|---|---|---|
| 决策扫描（约 30 秒） | 问题、选择、最大风险、是否有待裁定项 | 摘要 |
| 方案理解（约 5 分钟） | 为什么这样选、机制怎样工作、影响什么、如何上线和证明 | 方案概览（主图、关键决策、成立理由）、详细设计导读、发布验证 |
| 深度评审/实施 | 契约、不变量、失败边界、兼容、追踪和证据 | 详细设计的 reference-level 小节、`traceability.md` |

时间是体验测试，不是精确 SLA。下层增加精度，不得推翻上层表述。

## 2. 七个读者问题

正式方案必须让读者找到以下答案，它们也是读者测试的题目（`reader-test-protocol.md`）：

1. 当前要解决什么问题，证据是什么？
2. 目标、非目标和已确认约束是什么？
3. 最终选择什么，为什么不选主要替代路径？
4. 目标机制怎样工作，凭什么在正常和失败情况下成立？
5. 哪些外部行为、数据、上下游或相邻逻辑改变，哪些明确不变？
6. 如何发布、观测、验证和回滚？
7. 还存在哪些风险、阻塞和开放问题？

profile 和横切矩阵负责提示"还要考虑什么"，正文仍按技术机制和推理顺序展开，不把七个问题机械变成七个章节。

## 3. 各章节的默认表达形态

| 章节 | 回答的读者问题 | 默认形态 | 长度信号 |
|---|---|---|---|
| 相关文档 | 这份方案依据哪些材料 | 短列表：类型、名称、可见的路径或 URL | 不超过 8 条 |
| 摘要 | 问题、方案、最大代价或风险、待谁决定 | 一段，不分点 | 不超过 150 字 |
| 1 背景与目标 | 问题与证据；目标、非目标、约束 | 现状流程用时序图，数据现状用表；目标/非目标用表；术语对照表 | 现状只写理解决策必需的事实 |
| 2 方案概览 | 选了什么、为什么成立、动了什么 | 一句话方案 + 主图（标新增/修改/现有） + 关键决策表 + 成立理由（情形表或段落） + 变更总览表 | 关键决策 3 到 7 条 |
| 3 详细设计 | 机制怎样工作 | 按 profile guide → reference；核心机制单列一节：前后示例 + 流程图 + 实现对照表 + 边界表 | 核心机制最深；其余只展开变化、违反直觉、高风险、有争议或缺细节会分歧的内容 |
| 4 替代方案与取舍 | 为什么不选别的 | 表格"候选 \| 不选的原因"，原因复杂时改为每个候选一段 | 最多 3 个候选 |
| 5 影响与兼容 | 什么不变、上下游谁受影响 | 段落或短列表；改动清单引用 2.4，不重列 | 表格不超过 4 列 |
| 6 发布、验证与回滚 | 怎么上线、怎么证明、怎么退 | 阶段表；有发布顺序约束时加版本组合表 | 详细测试项交给测试清单 |
| 7 风险与未决问题 | 还有什么没解决 | 风险表 | 只写残余风险 |

## 4. Guide → Reference

第 3 章先建立心智模型，再提供实现精度：

1. 机制导读：问题本质、参与者、核心变化和为何能成立；
2. 代表性正常场景：用短流程、示例或主图建立直觉；
3. 实现级参考：契约、状态、时序、不变量、失败、兼容和边界；
4. 回到代表性场景，说明这些细节怎样保证结果成立。

不要让读者在理解目标机制前先处理类名、字段、配置和异常分支。

### 4.1 核心机制写透

动笔前先回答一句话："本方案若做错，哪段逻辑会直接违背需求？"这段就是核心机制，在第 3 章单列一节，标题写机制本身。它要让实施者不看代码也能照着写、让评审者能逐条挑错，因此必须有：

- 变更范围表：哪一步改、改什么、哪些照原样复制或保持；
- 前后对照示例：用真实形态的数据、脚本或报文展示变化前后（可简化，但关键写法与代码一致）；
- 流程图或时序图，配"节点 → 代码位置"的实现对照表，不写伪代码；
- 边界情况表：多值、重复、缺失、旧版本数据、不适用的类型；
- 不变量及由谁保证。

其他小节的篇幅不超过核心机制小节。方案里出现"复用现有方法"时，要写清复用的方法在这个场景下处理了哪些形态，而不是只给方法名。

### 4.2 区分新增、修改与现有

评估者读方案最想先知道"这次动了什么、动多大"。方案里出现的每个对象（接口、方法、字段、配置、页面逻辑、数据）都归入一类，全文用同一组词：

| 标识 | 含义 | 对应 CHG 动作 |
|---|---|---|
| 新增 | 本次新写的对象 | 新增 |
| 修改 | 已有对象的行为、签名或取值变化 | 修改 |
| 删除 | 本次移除的对象或逻辑 | 删除 |
| 现有 | 本次不改，只为理解上下文出现 | 保持不变 |

标识出现在四处，同一对象在四处一致：

- 2.4 变更总览表：列出全部新增、修改、删除，是标识的权威清单；
- 第 2、3 章的图：按 `visualization-routing.md` 第 4 节着色，图后一句图例；1.1 的现状图全是现有，不着色；
- 第 3 章的步骤表、变更范围表和实现对照表：加"变更"列；
- 段落：一段同时涉及新旧逻辑时，在句中点明"现有的……不变，新增……"，不让读者自己推断哪部分是本次写的。

## 5. 风险驱动展开

只有符合任一条件才详细展开：

- 本方案的核心机制（4.1），始终详细展开；
- 本次确实发生变化；
- 行为违反直觉或容易误用；
- 影响正确性、兼容性、安全、数据或发布回滚；
- 存在实质候选取舍或评审争议；
- 缺少细节会导致两个实现者作出不同实现；
- 关键假设、容量结论或全称断言需要证据。

系统历史、完整对象清单、长 SQL、日志、调用链、逐文件动作和未来设想默认压缩、引用或移出正文。

## 6. 唯一事实源

- 摘要压缩正文已有结论，不增加条件和例外。
- 关键决策定义选择和理由；详细设计解释落地；第 4 章解释为何不选别的，三处不互相重写。
- 失败语义在对应机制或契约处定义；第 7 章只写残余风险。
- `traceability.md` 只做映射、登记和证据索引，不重新解释机制。
- 修订痕迹和 finding 处置在 `solution-review/rounds/round-<N>/resolution.md`，不在正文。

## 7. 输出前可复核测试

| 测试 | 通过条件 |
|---|---|
| 30 秒扫描 | 摘要能回答问题、选择、最大风险和是否有待裁定项 |
| 5 分钟理解 | 不读 `traceability.md` 也能解释机制、主要影响以及怎样上线和证明 |
| 标题测试 | 第 3 章标题呈现推理顺序，不是文件或 CHG 清单 |
| 双读者测试 | 新读者能建立心智模型，实施者能定位精确契约和边界 |
| 核心机制测试 | 读者能指出核心机制所在小节，并能复述改什么、怎么改、边界怎么处理；该小节有前后示例、流程图和实现对照表 |
| 变更标识测试 | 只看 2.4 和图就能说出本次新增、修改了哪些对象；同一对象在总览、图、第 3 章表格和 CHG 矩阵中的标识一致 |
| 表达形式测试 | 流程、对比、清单、前后变化没有写成段落；满足图触发条件的地方都有图或写了不画的理由；代码名集中在术语或实现对照表 |
| 删除测试 | 每段都增加事实、理由、约束、边界或证据 |
| 唯一归属测试 | 摘要、正文、追踪文件和图没有多个权威定义 |
| 完整性测试 | 所有相关维度有权威位置，AC/CHG 可追踪，N/A 有理由 |
| 范围隔离测试 | 当前方案、开放问题、未来设想、证据和 DEV 内容没有混写 |
| 读者测试 | 按 `reader-test-protocol.md` §5 判定通过：全文读者七问、截断读者前五问、成立的探针问题已处置 |

`scripts/doc_metrics.py <solution.md> --traceability <traceability.md>` 给出长段落、正文代码名密度、术语对照表是否存在、变更总览与图中变更标识是否存在、图数量、单元格长度、ID 与否定词密度、修订痕迹、摘要长度和主图存在性等信号，用于自检和评审前复核；它是提示，不是门禁。篇幅超过约 300 行触发结构复核：检查重复、系统百科、证据和执行清单；不机械删除必要设计。
