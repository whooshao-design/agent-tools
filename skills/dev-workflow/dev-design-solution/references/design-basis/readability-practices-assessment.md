# 技术方案可读性实践调研与 `dev-design-solution` 借鉴评估

> 状态：Draft<br>
> 评估日期：2026-08-31<br>
> 评估对象：`dev-design-solution`、技术方案核心模板及四类 profile<br>
> 关联方案：`template-system-optimization.md`

## 0. 结论摘要

GitHub 上优秀的 RFC、设计提案和架构文档项目没有通过“越短越好”解决可读性，也没有通过增加更多必填章节保证完整。它们更稳定的共同机制是：

1. **按阅读深度分层**：先让读者快速知道问题、结论和影响，再解释方案如何工作，最后提供实现级契约和边界。
2. **按决策风险展开**：只详细说明改变的、意外的、高风险的、存在争议的或影响正确性的内容；常识和无关维度不扩写。
3. **叙事与覆盖分离**：正文按问题和机制组织，覆盖完整性由目标、相关性矩阵和追踪表校验，不把检查清单直接写成正文。
4. **每种表达形式各司其职**：正文解释理由和语义，示例建立直觉，表格承载精确映射，图表达关系和时序，附录保存长证据。
5. **未来内容与当前方案隔离**：当前范围、已选设计、开放问题和未来可能性分别放置，避免读者误判哪些内容会实施。

建议把以下原则作为 `dev-design-solution` 3.0 的可读性主线：

> 技术方案的简洁不是字数少，而是读者能以最小成本找到决策所需的信息；技术方案的完整不是章节多，而是所有与本次正确性和交付风险相关的问题都有唯一、可追踪的答案。

具体采用“**三层阅读入口 + guide/reference 双层设计 + 风险驱动展开 + 语义覆盖矩阵**”。不增加另一套完整模板，不设置统一中文字符数、句长或图表数量硬门禁。现有“正文约 300 行、超过约 450 行拆分”可保留为结构复核信号，但不能作为质量结论。

## 1. 调研问题与评价标准

### 1.1 要解决的不是单纯的篇幅问题

技术方案可读性同时受四个目标约束：

| 目标 | 读者需要 | 单独追求该目标的副作用 |
|---|---|---|
| 简洁 | 快速找到问题、结论和关键理由 | 过度压缩后只剩结论，缺少成立条件和边界 |
| 清晰 | 建立统一的系统心智模型 | 为解释清楚而重复背景，正文膨胀 |
| 完整 | 能评审正确性、影响和交付风险 | 把检查项全部展开为章节，退化成说明书或清单 |
| 可实施 | 非作者能据此编码和验证 | 过早进入文件、类、步骤和工期，退化成开发清单 |

因此，本次不把“模板长度”或“平均句长”作为第一评价指标，而重点检查信息分层、认知路径、唯一事实源和风险覆盖。

### 1.2 评价维度

| 维度 | 评价问题 |
|---|---|
| 首屏有效性 | 读者能否在短时间内判断文档是否相关，并说出问题、选择和最大风险 |
| 叙事连续性 | 正文是否沿“问题 → 约束 → 选择 → 机制 → 结果”前进，而不是按文件或检查项跳转 |
| 实现精度 | 非作者能否找到契约、不变量、异常、兼容和验证条件 |
| 信息密度 | 每段是否推进理解或决策，是否存在无内容的套话和重复事实 |
| 扫读能力 | 只看标题、首句、图表标题能否恢复文档主线 |
| 内容完整性 | 相关风险维度和验收标准是否都有答案，不相关内容是否能安全删除 |
| 渐进阅读 | 管理者、评审者、实现者能否停在不同深度而不丢失各自所需信息 |
| AI 适配性 | 规则是否能被 agent 稳定执行和 reviewer 独立复核，而非依赖“写得优美”这类主观提示 |

## 2. GitHub 项目的客观评估

### 2.1 总体对比

| 项目 | 最值得借鉴的机制 | 适配度 | 不应直接照搬的部分 |
|---|---|---:|---|
| Rust RFC | Guide-level 先建立理解，Reference-level 再给实现和边界；示例贯穿两层 | 很高 | 面向语言特性的教学措辞需改写为系统机制和代表性场景 |
| Swift Evolution | 独立短摘要；Proposed Solution 不追求全面；Detailed Design 达到他人可实现；Future Directions 隔离 | 很高 | “50 个英文单词”不适合作为中文硬门禁；ABI 等固定章节仅适用于其场景 |
| React RFC | 模板短，但保留动机、详细设计、代价、替代路径、采用策略、教学方式和未决问题 | 高 | 缺少后端生产系统常见的数据、发布、观测、回滚和追踪治理 |
| Kubernetes KEP | Summary/Proposal/Design Details 分层；Goals/Non-Goals；先高层、后迭代；测试只写有区分度的内容 | 高 | 完整 KEP 面向平台级演进，章节很多，局部需求照搬会非常重 |
| Microsoft Engineering Playbook | 设计材料按 Game Plan、Milestone、Feature、Task 分级；决策日志和权衡研究独立 | 高 | 更偏团队流程和评审组织，不足以单独约束正文写法 |
| arc42 | 相关性优先于完整性；只展开重要、意外、高风险、复杂、易变内容；视图按问题选择 | 高 | 整套架构模板适合系统级文档，不适合所有局部技术改动 |
| GitHub Docs style guide | 简单语言、主动表达、可描述内容的标题、短段落、图文等价 | 中高 | 解决表达层问题，不能替代技术正确性和覆盖校验 |
| Diátaxis | 解释“为什么/如何理解”和参考“精确事实”服务不同阅读需求，混写会相互干扰 | 中高 | 不应机械要求一份技术方案只能属于单一文档类型，应在章节层分工 |
| Vale / textlint | 可对 Markdown 文本执行可配置检查，适合在 PR 中提供反馈 | 低到中 | 中文语义简洁和方案完整性难以通用规则化；未经调优会制造噪声 |

这个排序不是按 Star 数量，也不是项目权威性的排名，而是针对当前 Markdown 技术方案生成链路的适配度评估。

### 2.2 Rust RFC：先建立心智模型，再提供参考级精度

[Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/master/0000-template.md)把方案解释分为两层：

- Guide-level explanation：像功能已经存在一样教会读者如何理解和使用它，引入必要概念，优先使用具体示例说明影响。
- Reference-level explanation：给出足以理解交互、实施方案和边界情况的技术细节，并回到前一层示例解释其为何成立。

这是本次最有价值的借鉴。很多技术方案难读，不是细节太多，而是读者在还没有心智模型时就被迫理解类名、字段、配置和异常分支。相反，如果只有总览而没有 reference-level 内容，方案又无法实施和评审。

适配到当前 skill 后，第 4 章不应直接进入实现清单，而应固定按以下认知顺序：

1. 一段“机制导读”：问题本质、参与者、核心变化和为何能成立；
2. 一个代表性正常场景：用示例、简图或短流程建立直觉；
3. 实现级参考：契约、不变量、状态、失败、兼容和关键边界；
4. 回到代表性场景，说明细节怎样保证结果成立。

### 2.3 Swift Evolution：摘要、方案总览与详细设计职责分明

[Swift Evolution 模板](https://github.com/swiftlang/swift-evolution/blob/main/proposal-templates/0000-swift-template.md)要求摘要能够脱离上下文单独展示，让读者判断是否相关；Proposed Solution 只聚焦最重要部分，不要求全面；Detailed Design 则必须详细到非作者能够合理实施。

可借鉴三点：

- 一页结论必须自洽，但只做导航，不重写整份正文；
- 推荐方案总览负责建立主线，详细设计负责提供精度，两者不能合并成一大段；
- 未来方向与当前提案隔离，避免尚未承诺的内容污染当前范围。

Swift 使用“不超过 50 个英文单词”的摘要约束有明确场景价值，但中文信息密度、术语长度和内部技术方案复杂度不同。当前 skill 应约束摘要回答哪些问题，并以人工扫读测试复核，不应机械换算为固定中文字数。

### 2.4 React RFC：少章节不等于少问题

[React RFC 模板](https://github.com/reactjs/rfcs/blob/main/0000-template.md)本身很短，但仍要求回答 Summary、Motivation、Detailed Design、Drawbacks、Alternatives、Adoption Strategy、How We Teach This 和 Unresolved Questions。它说明完整性可以由少量高价值问题维持，而不是依靠几十个固定章节。

尤其值得借鉴的是：Motivation 应描述问题约束，不应过早绑定推荐方案；否则候选方案比较会变成对既定结论的补证。

React 的模板不能单独作为后端技术方案模板，因为它没有为数据一致性、跨版本兼容、发布观测和回滚建立明确入口。最合理的用法是借鉴“短模板 + 深提示”，再由当前四类 profile 和横切维度补足生产系统风险。

### 2.5 Kubernetes KEP：渐进展开，而不是一次填满

[Kubernetes KEP 模板](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/README.md?plain=1)区分 Summary、Motivation、Proposal 与 Design Details：Proposal 需要让人理解提议，但不应塞入 API 和实现细枝末节；Design Details 再承担精确设计。模板还强调 Goals/Non-Goals、风险、升级/降级和测试计划。

可直接借鉴的机制包括：

- 先写高层可评审方案，再随决策收敛补充细节；“尚未填满”不等于“已经批准”。
- 用户故事或代表性场景用于让设计变得具体，但不能把读者拖入完整业务百科。
- 备选方案只需足以表达核心思路和拒绝原因，不必把每个候选都写到推荐方案同等深度。
- 测试章节写本方案特有的风险和例外，不枚举任何实现都应具备的常规测试。

不建议复制完整 KEP 章节。KEP 面向 Kubernetes 平台级能力和长期演进，直接照搬会和“简洁”目标冲突。

### 2.6 Microsoft Playbook：先选文档粒度

[Microsoft Code With Engineering Playbook 的设计评审](https://github.com/microsoft/code-with-engineering-playbook/blob/main/docs/design/design-reviews/README.md)强调设计评审需要在信息过多和不足之间取得平衡，并按 Game Plan、Milestone/Epic、Feature/Story、Task 使用不同粒度的设计材料。它还把关键决定和权衡研究从大型设计文档中分离为决策日志和 Trade Study，减少查找历史理由的成本。

对当前 skill 的意义是：可读性问题有一部分发生在写作之前。如果一个简单改动被路由到正式九章方案，再好的表达规则也会显得冗长；如果一个平台级改造被塞进单个 feature 文档，也会因上下文和细节争抢篇幅而失控。

因此“是否需要正式方案”和“四类主 profile”不仅是结构路由，也是可读性门禁。复杂项目可以拆为一份路线/总览和若干可独立评审的方案，但当前 skill 不应把路线图、技术方案和开发计划合并。

### 2.7 arc42 与 Diátaxis：相关性和内容模式

[arc42 Markdown 模板](https://github.com/NetworkedAssets/arc42-in-markdown-template/blob/master/2.%20Single%20File%2FArc42%20Template%20in%20Markdown.md)强调只详细描述重要、意外、高风险、复杂或易变的内容，运行时视图也只选择有架构意义的代表性场景。这比“所有章节都填一点”更适合保证信息密度。

[Diátaxis](https://github.com/evildmp/diataxis-documentation-framework)指出，解释性内容帮助读者理解“为什么”，参考性内容帮助读者准确工作；混在一起时，解释会打断查找，参考细节也会割裂理解。

技术方案无需被强行归为单一类型，但每个区域应有明确模式：

| 区域 | 主要模式 | 不应混入 |
|---|---|---|
| 一页结论、推荐方案、正确性论证 | 解释/决策 | 逐文件动作、完整字段清单 |
| 契约、状态、兼容矩阵、阈值 | 参考 | 长篇背景和重复理由 |
| 附录证据 | 参考/证据 | 新的权威设计结论 |
| DEV 清单 | 执行 | 方案为什么成立的主叙事 |

### 2.8 GitHub 写作规则：用于最后一公里，不负责技术完整性

[GitHub Docs style guide](https://github.com/github/docs/blob/main/content/contributing/style-guide-and-content-model/style-guide.md)强调清晰、简单、面向受众的语言，标题应能描述内容，层级应连续，强调格式应克制；图表需要有相邻文本解释，不能让关键信息只存在于视觉内容中。

这些规则适合转化为 agent 的表达约束，但只能解决“已有内容怎样写清楚”，不能决定“方案缺了什么”。因此表达规则和覆盖规则必须分开：前者优化句段和标题，后者通过 profile、横切矩阵和追踪关系保证完整。

## 3. 推荐的信息架构

### 3.1 三层阅读入口

同一份正式技术方案提供三个阅读深度，不为三类读者复制三份事实：

| 阅读深度 | 目标时间 | 需要回答的问题 | 主要载体 |
|---|---:|---|---|
| 决策扫描 | 约 30 秒 | 什么问题、选择什么、主要变化、最大代价/风险、是否阻塞 | 一页结论 |
| 方案理解 | 约 5 分钟 | 为什么这样选、系统怎样工作、影响什么、如何上线和证明 | 背景精简段、方案选择、机制导读、主视图、发布验证 |
| 深度评审/实施 | 按需 | 契约、不变量、失败边界、兼容矩阵、对象追踪和证据在哪里 | 详细设计参考层、表格、附录 |

“目标时间”是阅读体验测试，不是精确计时 SLA。关键要求是每一层都能独立回答该层问题，下层只增加精度，不推翻上层表述。

### 3.2 第 4 章采用 guide/reference 双层设计

每个主 profile 的“目标技术设计”按以下顺序组织：

```text
4. 目标技术设计
├── 4.1 机制导读
│   ├── 问题本质
│   ├── 核心变化与成立理由
│   └── 代表性正常场景/必要主图
├── 4.2 ~ 4.n 实现级设计
│   ├── 参与者和职责
│   ├── 契约/状态/数据/时序
│   ├── 不变量与正确性
│   └── 失败、兼容和边界
└── 4.x 明确保持不变的行为
```

不同 profile 改变 4.2～4.n 的必答问题，但不改变从“先理解”到“再查精度”的认知顺序。

### 3.3 风险驱动的细节预算

正文默认简写，只有符合以下任一条件才展开：

- 本次确实发生变化；
- 行为违反直觉或容易误用；
- 影响正确性、兼容性、安全、数据或发布回滚；
- 存在实质候选取舍或评审争议；
- 缺少细节会导致两个实现者作出不同实现；
- 需要证据支撑关键假设或容量结论。

下列内容默认压缩、引用或移出正文：

- 与本次决策无关的系统历史和完整架构；
- 正常工程实践中的通用检查项；
- 重复出现的相同事实和理由；
- 文件、行号、完整对象清单、长 SQL、日志和扫描结果；
- 工时、负责人、commit 拆分和逐步编码命令；
- 未进入当前范围的未来设想。

## 4. 简洁但不漏项的生成规则

### 4.1 先回答读者问题，再选择章节

正式方案必须让读者找到以下七个答案，但不要求七个问题机械变成七个大章：

1. 当前要解决什么问题，证据是什么？
2. 目标、非目标和已确认约束是什么？
3. 最终选择什么，为什么不选主要替代路径？
4. 目标机制怎样工作，凭什么在正常和失败情况下成立？
5. 哪些外部行为、数据、上下游或相邻逻辑改变，哪些明确不变？
6. 如何发布、观测、验证和回滚？
7. 还存在哪些风险、阻塞和开放问题？

profile 和横切矩阵负责提示“还要考虑什么”，正文组织仍应沿技术机制和推理顺序展开。

### 4.2 标题承担导航职责

- 标题使用机制、状态变化或关键结论，不使用“方案项一”“处理逻辑”“其他”“模块改动”这类空标题。
- 同级标题保持同一抽象层级，不把组件、接口、文件和风险混在一层。
- 只看第 4 章标题，应能复述机制怎样成立，而不是只知道改了哪些文件。
- 标题不堆完整句子；需要限定条件时在该节首句说明。

示例：

| 不推荐 | 推荐 |
|---|---|
| `4.2 配置修改` | `4.2 运行时从 Hippo namespace 读取分类凭证` |
| `4.3 异常处理` | `4.3 Hippo 不可用时拒绝启动，禁止回退到硬编码凭证` |
| `4.4 其他改动` | 删除或按真实机制归并 |

### 4.3 段落和句子规则

- 一段只推进一个判断，首句先给该段结论或主题。
- 优先使用“参与者 + 动作 + 对象 + 条件/结果”的具体表达，少用抽象名词串联。
- 先写常见正常路径，再写异常、兼容和例外；不要让读者从边界情况反推主流程。
- 使用代码和仓库中的真实术语，一个概念只保留一个名称；新术语首次出现时定义。
- 删除没有新增信息的开场语和总结语，例如无具体对象的“综合考虑”“通过上述方案”“为了确保”“需要注意的是”。
- 句子长度只作为重读信号，不做统一硬限制；连续短句同样可能生硬和割裂。

### 4.4 正文、列表、表格、图和附录的选择

| 信息类型 | 首选形式 | 反例 |
|---|---|---|
| 设计理由、不变量、失败语义 | 短段落 | 用“优点/缺点”表格隐藏推理 |
| 同类并列条件、少量步骤 | 列表 | 一个列表项包含多个长段落 |
| 精确字段、版本、对象映射、追踪 | 表格 | 表格单元格塞入长篇论证 |
| 关系、顺序、状态、层级、部署 | 按需图表 | 把文件或 CHG 清单画成流程图 |
| 代码、配置、完整证据 | 代码块或附录引用 | 在正文粘贴大段原文 |

图表的运行时路由和质量契约以 `../visualization-routing.md` 为准；完整调研依据见 `diagram-practices-assessment.md`。

### 4.5 内容只定义一次

- 一页结论压缩正文已有结论，不增加新的条件和例外。
- DEC 定义选择和理由，目标技术设计引用 DEC 并说明如何落地，不重复整段候选比较。
- 失败语义只在对应机制或契约处定义；风险章节只描述残余风险、概率/影响和缓解。
- CHG 矩阵只做交付映射，不重新解释机制。
- 附录只提供证据和明细，不产生正文没有的新方案结论。

如果同一事实必须在多个视图出现，其他位置使用稳定 ID 或链接引用，并保持摘要表述不引入新语义。

## 5. 完整性不靠扩写正文保证

### 5.1 语义覆盖矩阵

生成方在写作前完成相关性判断，评审方在提交前复核。矩阵可以保留在方案的“影响范围与兼容性”中，也可以作为生成过程的内部清单；不相关项仅给出简短 N/A 原因，不创建空章节。

| 维度 | 是否相关 | 权威位置 | 完整的最低条件 |
|---|---|---|---|
| 需求与范围 | 是 | 目标与范围 | AC、In/Out、约束无冲突 |
| 核心机制 | 是 | 目标技术设计 | 参与者、路径、不变量、失败成立 |
| 接口/契约 | 按需 | 对应机制/契约小节 | 可见行为和错误语义明确 |
| 数据/状态 | 按需 | 对应机制/数据小节 | 模型、事务、一致性和恢复明确 |
| 配置/安全 | 按需 | 对应机制/发布小节 | 默认值、权限、敏感信息和失败策略明确 |
| 并发/幂等 | 按需 | 正确性论证 | 重复、乱序、竞态和重入边界明确 |
| 兼容/迁移 | 按需 | 影响/迁移小节 | 版本窗口、顺序、完成和退出条件明确 |
| 性能/容量 | 按需 | 对应机制/专项小节 | 结论有数据、估算或显式阻塞 |
| 观测/回滚 | 是 | 发布章节 | 信号、阈值、通过/回滚条件明确 |
| 追踪 | 是 | 验证与附录 | `AC → 设计 → CHG → 验证/发布` 闭环 |

### 5.2 两类完整性必须区分

- **设计完整性**：目标机制、关键契约、不变量、失败和边界足以评审及实施，由正文承担。
- **交付完整性**：所有文件、对象和变更单元都有来源、验证和发布归属，由 CHG 追踪矩阵承担。

把交付完整性全部搬进正文会产生开发清单；只写机制而没有追踪矩阵，又会漏掉实际改动。二者同时存在，但不能使用同一叙事结构。

### 5.3 代表性场景代替穷举

正文选取能够暴露设计核心的少量场景：

- 一条代表性正常路径；
- 一条最关键失败或恢复路径；
- 一条确实影响兼容、并发或迁移正确性的边界路径。

完整对象和普通变体放入矩阵或附录。场景数量不是硬指标；简单方案可能一个场景足够，复杂协议也可能需要多条时序。

## 6. 不建议采用的做法

### 6.1 全局硬字数或句长门禁

统一限制中文字数容易促使 agent 删除限定条件、失败语义和不变量，或通过表格压缩视觉长度但不降低认知负担。建议只保留结构性告警：正文明显超预算时检查是否混入证据、执行清单、系统百科或重复事实。

### 6.2 用更多模板章节防漏项

固定的接口、MySQL、Redis、缓存、异常、监控章节会让不相关方案产生空壳，也会让同一机制在多章重复。覆盖应由相关性矩阵保证，相关内容写回机制的权威位置。

### 6.3 强制每节填写 N/A

大量 N/A 会掩盖真正的遗漏。可选章节不相关时直接删除，只在一张相关性矩阵中记录必要理由。

### 6.4 把摘要写成正文缩印版

摘要若重复所有背景、变更和风险，既不便扫描，也产生第二事实源。一页结论只保留决策所需的五项：问题、选择、主要变化、最大代价/风险、阻塞状态。

### 6.5 过度依赖自然语言 lint

[Vale](https://github.com/vale-cli/vale)和[textlint](https://github.com/textlint/textlint)适合执行可配置的格式和词语规则，但无法可靠判断一个中文技术方案是否遗漏正确性论证，或某段详细解释是否确实必要。尤其通用中文 preset 多集中在标点、空格和术语，不能替代技术评审。

因此第一阶段不引入新的 prose linter 依赖；先做确定性的结构契约检查。以后若积累了真实误报样本，再评估定制规则，并只对新增内容提供建议性反馈。

## 7. 当前模板与 skill 的可读性缺口

| 当前位置 | 已有优点 | 主要缺口 | 建议调整 |
|---|---|---|---|
| `SKILL.md` 一页结论 | 已要求结论前置、正文不新增事实 | “3–5 句话”只约束形式，未定义五项扫描答案 | 改为五项信息契约，句数仅作建议 |
| 当前 `solution-template.md` | 有现状/目标/方案/验证/风险闭环 | 一页结论含 CHG 表，容易一开始就把读者带入交付颗粒度 | 一页结论改为“主要变化”自然语言或极简机制表，完整 CHG 移附录 |
| 机制轴详细设计 | 已要求先说明机制为何成立 | 未显式区分机制导读和实现级参考，容易一段后直接按组件罗列 | 各 profile 固定 guide → reference 顺序 |
| 变更轴 | 允许独立变更直接组织 | 模型很容易把“多个对象复用同一机制”误判为独立变更 | 仅保留为少量独立变更例外；批量方案按 profile |
| 横切维度 | 已要求相关才展开 | 完整性规则散在 skill 和模板中，写作者可能通过增加正文来求稳 | 统一为相关性矩阵，记录权威位置 |
| 篇幅预算 | 已有约 300/450 行信号 | 容易被误解为可读性验收，表格和长句也可规避行数 | 明确只触发结构复核，不直接判失败 |
| 标题自检 | 已要求标题能表达所做事情 | 仍可能出现正确但空泛的“核心机制/处理流程” | 增加机制化标题规则和反例 |
| 追踪矩阵 | 能保证 AC/CHG 覆盖 | 追踪表与变更地图重复，且摘要也展示 CHG | 核心正文保留一处导航，完整映射统一附录化 |
| reviewer | 可检查机制/变更轴与追踪 | 缺少分层阅读、重复事实和信息密度检查 | 增加 30 秒、5 分钟、标题、唯一归属和双读者测试 |

当前模板方向并非整体错误。结论前置、删除不适用章节、同一事实只保留一个权威位置、长证据移附录和标题自检都应保留。主要需要补足的是“怎样先建立理解、再给精度”和“怎样在不扩写正文的情况下证明完整”。

## 8. 对 `dev-design-solution` 的具体改造建议

### 8.1 文件职责

```text
dev-design-solution/
├── SKILL.md
├── agents/openai.yaml
└── references/
    ├── solution-template.md
    ├── template-routing.md
    ├── design-dimensions.md
    ├── readability-and-writing.md
    ├── visualization-routing.md
    └── profiles/
        ├── mechanism-architecture.md
        ├── migration-remediation.md
        ├── contract-evolution.md
        └── data-state-consistency.md
```

新增 `readability-and-writing.md`，但不新建“简洁版模板”。它只定义：

- 三层阅读入口；
- guide/reference 设计顺序；
- 风险驱动展开信号；
- 标题、段落、术语和表达形式规则；
- 常见冗余和 AI 套话反例；
- 输出前可读性测试。

`SKILL.md` 只保留执行摘要并按阶段读取该参考，避免主 skill 膨胀。四类 profile 只补充本场景的代表性场景和 reference-level 必答问题，不复制公共写作规则。

### 8.2 生成顺序

建议将正式方案生成调整为：

1. 先确认是否需要正式方案及主 profile；
2. 建立七个读者问题和相关性矩阵；
3. 形成一页结论与机制导读；
4. 只对相关、高风险内容展开 reference-level 设计；
5. 建立 CHG 与 AC 追踪，不改变正文叙事轴；
6. 执行删减、唯一归属和分层阅读自检；
7. 交由独立 reviewer 检查完整性和可读性。

关键点是先建立“覆盖地图”，再写简洁正文。否则 agent 往往为了防遗漏，把所有检查问题直接转换为标题和段落。

### 8.3 一页结论的信息契约

一页结论只回答：

1. 问题与影响；
2. 推荐方案；
3. 主要机制变化；
4. 最大代价或风险；
5. 当前阻塞状态。

完整 CHG 表、详细 AC、候选方案、对象盘点和实施顺序不放在这里。必要时使用不超过几行的机制摘要表，但不以 CHG 为行。

### 8.4 reviewer 的可读性门禁

reviewer 不评价文风是否“漂亮”，而执行以下可复核测试：

| 测试 | 通过条件 |
|---|---|
| 30 秒扫描 | 从一页结论能说出问题、选择、主要变化、最大风险和是否阻塞 |
| 5 分钟理解 | 不读附录也能解释机制如何工作、主要影响以及怎样上线和证明 |
| 标题测试 | 只看第 4 章标题能恢复设计的推理顺序，不是文件/CHG 清单 |
| 双读者测试 | 新读者能建立心智模型，实施者能定位精确契约和边界 |
| 删除测试 | 每段都在增加事实、理由、约束、边界或证据；无作用句可删除 |
| 唯一归属测试 | 同一事实无多个权威定义，摘要/矩阵/图不引入新语义 |
| 完整性测试 | 所有相关维度有权威位置，所有 AC/CHG 有追踪，N/A 有合理原因 |
| 范围隔离测试 | 当前方案、开放问题、未来可能性和 DEV 执行内容没有混写 |

## 9. 自动化检查的合理边界

### 9.1 第一阶段可做硬检查

- 必需核心章节存在且非空；
- 不同时加载多套 profile；
- 无旧的机制轴/变更轴完整双骨架；
- `CHG-*` 默认不作为第 4 章批量标题；
- AC、DEC、CHG、RISK ID 无重复或悬空引用；
- 核心模板不包含固定 Redis/MySQL/缓存等无关章节；
- 不存在未删除的占位符和连续空章节；
- 图表规则、正文和 reviewer 使用一致术语。

### 9.2 只做建议性提示

- 单段明显过长，建议检查是否包含多个判断；
- 表格单元格包含多段长文本，建议改为正文；
- 标题过于泛化，如“其他”“处理逻辑”“方案项”；
- 同一非通用短语在多节重复，建议检查事实重复；
- 出现高频空泛连接语，建议人工确认是否有信息增量；
- 正文超过篇幅预算，触发结构复核而不是直接失败。

### 9.3 不自动判定

- 中文句子是否“太长”；
- 某段解释是否一定冗余；
- 方案是否必须包含某张图；
- 方案是否因字数少而完整；
- 技术取舍和正确性论证是否成立。

这些判断必须由理解需求和代码证据的生成方与独立 reviewer 完成。

## 10. 建议的实施顺序

1. 先把本评估中的分层阅读和风险驱动原则并入模板体系优化方案；
2. 实施时新增 `readability-and-writing.md`，同步核心模板和四类 profile；
3. 同步修改 solution reviewer，避免生成方优化后仍被旧检查清单推回冗长结构；
4. 增加确定性的结构测试，不在第一阶段引入 Vale/textlint；
5. 用硬编码整改方案做双重试点：既检查是否摆脱开发清单，也检查是否能在 30 秒、5 分钟和深度评审三个层次阅读；
6. 收集真实评审中的“看不懂、找不到、重复、遗漏”样本，再决定是否增加提示性 lint。

## 11. 最终建议

应当开始优化，但把“可读性”作为与模板路由、图表规则并列的独立设计维度，而不是在 skill 中追加一句“请简洁清晰”。

最核心的落地决策是：

- 保持一套核心模板，不再新建“简版/详版”两套完整模板；
- 通过一页结论、方案理解和深度参考形成三层阅读入口；
- 在详细设计内部借鉴 Rust 的 guide/reference 分层；
- 通过 profile 和相关性矩阵保证语义完整，通过 CHG 附录保证交付完整；
- 只展开与变化、风险、争议和正确性相关的内容；
- reviewer 使用可复核的阅读测试，不用主观“文笔好坏”或全局字数判断；
- 自动化先检查结构和追踪，中文语义可读性仍由独立评审负责。

这套做法同时回应了两个看似冲突的目标：正文可以简洁，因为覆盖检查不再依赖正文铺满章节；方案仍然完整，因为每个相关维度、验收标准和交付单元都有唯一权威位置和追踪闭环。
