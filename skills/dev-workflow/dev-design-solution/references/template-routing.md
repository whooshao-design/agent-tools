# 技术方案模板路由

## 1. 先判断是否需要正式方案

用户明确要求正式方案时直接进入正式方案路由。否则，只有以下条件全部成立，才不生成正式方案并转 `dev-build-change`：

- 需求边界和验收标准明确；
- 只有一个显而易见的最小实现路径；
- 不改变外部契约、数据/状态模型或关键运行时机制；
- 不存在跨模块迁移、并发、一致性、安全或发布顺序风险；
- 验证方式可以直接从完成标准得出。

任一条件不成立，都需要正式方案。不要用“改动文件少”代替风险判断。

## 2. 只选择一个主 profile

选择问题是“本方案最需要证明什么”，不是“使用什么组件”或“有多少 CHG”。

| 主要需要证明 | 主 profile | 典型场景 |
|---|---|---|
| 多个参与者协作后运行时机制仍正确 | `mechanism-architecture` | 异步处理、任务编排、重试补偿、插件/拦截、新运行链路 |
| 能安全从现状切换到目标状态且不漏不误 | `migration-remediation` | 配置/凭证整改、跨仓治理、依赖升级、数据搬迁、旧机制下线 |
| 新旧生产方和消费方在版本窗口内兼容 | `contract-evolution` | HTTP/Dubbo/API、消息、SDK、配置格式、跨系统协议演进 |
| 数据、状态和事务在并发及失败下保持不变量 | `data-state-consistency` | 表结构、状态机、事务边界、缓存一致性、回填与对账 |

多项命中时选择风险最高、最影响正确性结论的一项。其他问题通过横切维度或主 profile 内的小节处理，不拼接另一份 profile。

## 3. 防止方案退化为开发清单

满足任一信号时，禁止用 `CHG-*`、仓库名、文件名或配置 key 作为第 4 章主标题：

- 三个及以上 CHG 共享同一个 DEC 或处置模式；
- 存在跨 CHG 的顺序、共同不变量、共享状态或统一退出门禁；
- CHG 数量超过 8 个；
- 删除 CHG 编号后，标题无法表达技术机制；
- 对象可以分别提交，但正确性依赖同一迁移、契约或运行时规则。

真正独立、可分别实施/验证/回滚且没有共享机制的少量改动，通常应转 `dev-build-change`。用户仍要求正式方案时，按主要风险选 profile，并在 reference-level 小节紧凑说明差异；完整 CHG 仍放附录。

## 4. 场景验收

| 输入场景 | 预期路由 | 正文主线 |
|---|---|---|
| 硬编码凭证跨多个仓库迁入配置中心 | `migration-remediation` | 分类、目标机制、阶段、退出门禁；位置清单进附录 |
| 新增 MQ 重试和补偿 | `mechanism-architecture` | 时序、幂等、失败恢复和正确性 |
| HTTP API v1 升级 v2 | `contract-evolution` | 语义差异、兼容窗口、调用方迁移和废弃条件 |
| 订单状态表改造并回填历史数据 | `data-state-consistency` | 不变量、事务、回填、校验和切换 |
| 单文件空指针修复 | 无正式方案 | 转开发执行清单 |

## 5. 输出路由结果

正式方案开始前明确记录：

- 是否需要正式方案及依据；
- 选中的唯一主 profile；
- 未选 profile 的相关问题如何作为横切维度处理；
- 是否存在会改变 profile 或实现方向的阻塞输入。
