# Profile：机制/架构型

## 适用与核心证明

适用于新增运行时机制、跨组件流程、任务编排、异步处理、插件/拦截、重试补偿或多参与者协同。核心要证明：参与者按目标时序协作后，机制在正常、重复、乱序和失败情况下仍满足不变量。

## 第 3 章组织方式

### 3.1 机制导读（Guide）

- 问题本质和旧机制为什么不足；
- 参与者及其责任边界；
- 新机制的核心变化和成立理由；
- 一条代表性正常场景。主图（放在 2.1）默认是参与者时序图，或调用关系的前后对照；关系简单时按 `visualization-routing.md` 写豁免理由。

### 3.2 入口、生命周期和职责

说明入口、触发、生命周期、所有权和相邻机制边界。"挂载位置、触发时机、入口白名单"只有相关时才出现。

### 3.3 数据/控制流与关键时序

说明状态如何传递、谁读取/写入、顺序要求、异步边界和完成定义。

### 3.4 失败、重试、降级与恢复

按失败类别说明可见结果、重试/补偿、降级、恢复和观测信号。

### 3.5 并发、幂等与整体正确性

相关时论证重复、乱序、竞态、重入和多副本。必须正面回答不会漏处理、重复处理、提前处理或破坏原有保护的原因。

### 3.6 保持不变的行为

列出刻意不改变的相邻逻辑及保护原因。

## Reference-level 最低内容

- 参与者、入口和责任唯一；
- 正常、最关键失败和恢复场景可推演；
- 不变量有对应机制和验证信号；
- 接口、数据、配置、并发和观测只在相关机制处定义；
- 完整 CHG 放 `traceability.md`，不按组件/文件拆碎正文。

## 常见误用

- 按 controller/service/DAO 或仓库逐节罗列；
- 只画成功流程，不定义失败后的可见状态；
- 把"加锁/重试/幂等"当结论，不说明键、范围、冲突和终止条件；
- 每个 CHG 重复同一公共机制。
