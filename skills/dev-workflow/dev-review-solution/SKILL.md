# dev-review-solution

## 定位

用于在技术方案形成后、代码实现前，对指定版本的方案做独立、证据驱动的技术评审。

它是技术方案评审阶段的主入口：负责验证需求覆盖、技术可行性、设计完整性与实施风险，输出分级 findings 和明确评审结论；不重新生成整份方案，也不替代编码后的 `dev-review-change`。

默认只读取方案、需求、代码和配置，不直接修改方案或业务代码。评审可以否决推荐方向，但方案修订交回 `dev-design-solution` 完成。

## 默认产物目录

正式评审默认放到 `/home/joney/docs/requirements-development/<requirement-name>/solution-review/review.md`。

- `<requirement-name>` 与被评审方案使用同一需求目录
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中给出结论时，不创建文件
- 落盘时使用 `references/review-template.md`，不复制完整方案正文
- 同一需求进入第 2 轮及以后的评审前，先把上一轮 `review.md` 归档到 `solution-review/rounds/review-round-<上一轮次号>.md`，再写入本轮结论；首轮评审不创建 `rounds/` 目录，也不写"评审历史"这节
- 正式文档模式下 `review.md` 是审批事实源；对话模式下以包含相同绑定字段的结构化评审结果及消息引用作为审批记录。两者都必须绑定方案路径、方案版本、需求版本和代码基线；任一项变化都会使旧结论失效

## When to Use

适合以下场景：

- 已有候选或推荐方案，需要在进入开发前做技术评审
- 用户明确要求评审技术方案、架构方案或实现方案
- 方案涉及跨模块、接口、数据、状态、兼容、并发或发布风险
- 需要判断方案能否实施、是否必须修改或退回重设计

不适合以下场景：

- 方案方向尚未形成，此时先用 `dev-design-solution`
- 需求边界或验收标准仍不清楚，此时回到 `dev-clarify-task`
- 当前评审对象是已经完成的代码变更，此时使用 `dev-review-change`

## Workflow

### 1. 固定评审对象与边界

至少确认：

- 被评审方案的路径或完整内容、版本和状态
- 原始需求及其版本、范围、非目标与带稳定 ID 的验收标准
- 相关代码基线、模块、接口、数据和配置证据
- 本轮评审范围以及明确不评审的内容

若关键材料缺失，先列出缺口并限制结论范围；无法判断核心方向时，结论必须是“材料不足”，不能把猜测写成通过。

### 2. 独立核对方案依据

- 可用子代理时，在新上下文中只传原始需求、待评方案和必要代码证据，不传设计方的推理过程或预期结论；不可用时明确标注“同上下文自评”，并从原始材料重新建立证据链
- 不直接继承方案中的推荐结论，重新核对关键事实和约束
- 区分可验证事实、设计假设、已接受约束与个人偏好
- 只评审当前方案和必要影响面，不扩大成全系统审计
- 对无法从代码或材料确认的判断，降低结论强度并标记证据限制

### 3. 按相关维度评审

默认必查（对应 `references/review-template.md` 评审维度覆盖表的前 6 行）：

- 需求覆盖与边界：目标、范围、非目标和验收标准是否被方案覆盖
- 技术可行性：关键机制、依赖能力和代码落点是否成立
- 架构与模块职责：模块职责、上下游责任和复用方式是否合理
- 接口、数据、状态和配置：协议、状态、配置、事务和兼容性是否完整
- 异常、并发与一致性：失败、超时、重试、幂等、补偿和恢复是否自洽
- 验证与可测试性：验证思路整体是否可信（大致说清楚怎么验证、能看到什么信号）；逐场景覆盖交给下游 `dev-derive-test-cases` / `dev-review-test-cases`，本阶段不重复展开

性能、容量、安全、权限、可观测性、发布、迁移、灰度等维度按相关性检查（对应模板表格后 4 行）；不适用时明确标记 `N/A`，不为完整感制造无关问题。

### 4. 形成分级 findings

每条问题都包含：问题、证据、影响、严重度、建议和是否阻塞开发。

- `Blocker`：核心方向不可行、关键约束冲突，或缺少无法绕过的决策与证据；不得进入开发
- `High`：高概率导致正确性、兼容性、安全或稳定性问题；原则上修改后复审
- `Medium`：当前可能可实施，但存在明确维护、演进或实施风险；应修正或显式接受
- `Low`：不阻塞开发的局部改进或表达问题；控制数量，避免噪音

事实性风险与偏好建议分开写；严重度必须与实际影响匹配。

### 5. 给出评审结论

结论只能是以下之一：

- `通过`：没有未关闭的 Blocker/High/Medium；Low 不影响结论
- `有条件通过`：没有 Blocker/High，剩余 Medium 已由用户明确授权接受，并记录授权来源、适用范围、生效前提、到期条件和后续动作
- `修改后复审`：方向基本成立，但存在必须修正的问题
- `退回重设计`：核心方向、边界或技术依据不成立
- `材料不足`：证据不足以判断是否可以实施

任何未关闭的 Blocker/High 都不能通过；未关闭且未经用户明确授权的 Medium 必须落在 `修改后复审`，不能由评审者自行登记为 Accepted。没有发现问题时也要明确写“未发现阻断问题”。

### 6. 收敛后续动作

- 明确需要修改的方案章节和关闭条件
- 标明哪些风险已接受、由什么前提约束
- 判断是否需要完整复审或只复核指定 findings
- 记录进入 `dev-derive-test-cases` 前必须满足的条件，并交出需求版本、方案版本、代码基线、评审轮次/结论以及已授权风险及其前提

## 评审原则

- 评审结论基于需求、方案和代码证据，不基于理想化偏好
- 评审者不静默改写方案，但有权否决方向并要求重设计
- 先结论、再阻断、再证据、再动作
- 每条问题只表达一个可验证风险，避免把多个主题混在一起
- 评审深度与改动风险相匹配，简单方案不强行扩展成重型审计

## 输出模式

### 对话模式

默认按“结论 → 阻断问题 → 重要 findings → 证据限制 → 后续动作”输出轻量评审结果。

### 文档模式

用户要求正式评审或落盘时，使用 `references/review-template.md`。评审报告引用指定版本的 `solution.md`，不重写架构、流程和候选方案正文。

## 可选增强

- 方案涉及复杂 SQL、DDL、索引、事务边界或数据兼容性时，可调用 `review-db-change` 做数据库风险专项判断
- 方案涉及 Redis、MQ、任务调度，或存在超时、重试、幂等、降级等可靠性设计时，可调用 `review-middleware-reliability` 补查中间件与外部依赖行为

## 结果要求

一份合格的评审结果应满足：

- 能确认评审对象、版本、范围和证据来源
- 能区分阻断问题、重要问题、一般建议与证据限制
- 能说明方案是否可以进入开发以及判断依据
- 能指导方案修订、findings 关闭和必要复审
- 不重复整份技术方案，不把评审报告写成第二份方案

## 交接建议

- `通过` 或已取得用户明确风险授权的 `有条件通过` → 转 `dev-derive-test-cases` 推导测试场景；用户明确要求跳过测试场景链路时，可直接转 `dev-build-change` 并记录跳过风险
- `修改后复审` 或 `退回重设计` → 转 `dev-design-solution`，修订后重新评审
- 需求边界不清 → 回到 `dev-clarify-task`
- `材料不足` → 补充指定证据后继续当前评审
