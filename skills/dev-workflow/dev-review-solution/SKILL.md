# dev-review-solution

## 定位

用于在技术方案形成后、代码实现前，对指定版本的方案做独立、证据驱动的技术评审。

它是技术方案评审阶段的主入口：负责验证需求覆盖、技术可行性、设计完整性与实施风险，输出分级 findings 和明确评审结论；不重新生成整份方案，也不替代编码后的 `dev-review-change`。

默认只读取方案、需求、代码和配置，不直接修改方案或业务代码。评审可以否决推荐方向，但方案修订交回 `dev-design-solution` 完成。

方案的核心壳、主 profile、横切覆盖、内容归属、可读性和追踪闭环统一按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/solution-structure-contract.md` 评审；本 skill 只补充证据复核、严重度和准入结论。

## 默认产物目录

正式评审每轮写入 `/home/joney/docs/requirements-development/<requirement-name>/solution-review/rounds/round-<N>/`。

- `<requirement-name>` 与被评审方案使用同一需求目录
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中给出结论时，不创建文件
- `report.md` 使用 `references/review-template.md`；编排器同时保存 `delegation-result.json` 与 `approval-record.json`
- 轮次不可覆盖、`review.md` 只是指针、`approval-record-v1` 的生成与 reviewer 只读规则见委派契约 §5；本阶段审批按 `artifact-identity.md` 绑定完整 `(R,S,B)`、报告与委派结果指纹和 runtime 检查，任一绑定项变化都会使旧结论失效

## When to Use

适合以下场景：

- 已有候选或推荐方案，需要在进入开发前做技术评审
- 用户明确要求评审技术方案、架构方案或实现方案
- 方案涉及跨模块、接口、数据、状态、兼容、并发或发布风险
- 需要判断方案能否实施、是否必须修改或退回重设计

不适合以下场景：

- 方案方向尚未形成，此时先用 `dev-design-solution`
- 需求边界或验收标准仍不清楚，此时回到 `dev-clarify-task`
- 当前评审对象是已经完成的代码变更，此时使用 `dev-review-change`

## Workflow

### 1. 固定评审对象与边界

至少确认：

- 被评审方案身份 `S`（`solution.md` + `traceability.md` 的文件集指纹）和状态
- 读者测试结果 `solution-design/reader-test/agent-v<N>.md`；缺失时按材料不足处理
- 原始需求身份 `R`、范围、非目标与带稳定 ID 的验收标准
- 代码基线 `B`、相关模块、接口、数据和配置证据
- 方案的全部 `producer_agent_refs[]`
- 本轮评审范围以及明确不评审的内容
- 评审模式是完整评审还是定点复审；定点复审还必须提供上一版 `S`、上一轮审批记录、待关闭 findings、编排器生成的新旧方案 diff 与触达标题列表、设计方的 `resolution.md`，以及受影响的 `DEC-*` / `CHG-*` / `RISK-*`

若关键材料缺失，先列出缺口并限制结论范围；无法判断核心方向时，结论必须是“材料不足”，不能把猜测写成通过。

**范围与事实源冻结（前置门禁）**：进入领域评审前先确认整改/变更范围由谁定义。出现下列任一情形时，编排器必须先取得用户对范围事实源的书面裁定，未裁定不得进入正式评审，本轮结论为“材料不足”：

- 范围事实源是 **agent 自建的推导产物**（自写脚本、扫描器、自建清单等）——必须由用户确认它是“范围事实源”还是“定位辅助工具”；
- `R` 缺少带稳定 ID 的验收标准，方案实际以自建枚举替代需求边界。

裁定结果连同范围事实源的 `ref + fingerprint`、范围条目枚举或计数、非目标与裁定人一并冻结，作为本轮及后续各轮的共同输入。范围未先冻结时，围绕“自建枚举是否穷尽”产生的 findings 会在范围改判后整批作废。

### 2. 独立核对方案依据

- 正式评审必须由 `agent-tools-solution-reviewer` 或满足同一契约的独立 agent 执行，并遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/delegation-contract.md`；身份、只读、写入、工具面和结果结构的准入只以该契约为准。派发前按委派契约 §3.1 让用户选择 reviewer 模型（外部模型、同模型子 agent 或双评审），同一需求已选过时沿用；经 `spawn-model-agent` 以 `--readonly --tools Read,Grep,Glob` 运行的外部模型进程同样满足本契约。
- 编排器先冻结 `(R,S,B)` 和输入指纹，再只传原始需求、待评方案、必要代码证据与上一轮待复核 findings；不传设计方的推理过程或预期结论
- 方案的 `producer_agent_refs[]` 必须完整且可稳定标识；根 agent 直接产出时使用会话级 ref 并在执行记录中说明其强度限制，不构成审批阻塞（见 `delegation-contract.md` §1）
- 编排器在 reviewer 停止后按委派契约校验运行记录；任何一项无法由运行时事实证明时，不得形成正式领域结论
- 不直接继承方案中的推荐结论，重新核对关键事实和约束
- 区分可验证事实、设计假设、已接受约束与个人偏好
- 只评审当前方案和必要影响面，不扩大成全系统审计
- 对无法从代码或材料确认的判断，降低结论强度并标记证据限制

### 3. 先做结构与追踪准入

先检查方案是否可被可靠评审：

- 是否使用统一核心壳且只装配一个主 profile；profile 是否匹配本方案最需要证明的正确性问题
- `solution.md` 是否只有设计叙事：摘要只压缩权威正文，现状与目标设计分离，正文没有 CHG/AC/横切矩阵、指纹、finding 处置和修订痕迹；第 3 章是否按 guide → reference 先建立理解、再提供实现精度
- 第 3 章是否按技术机制或状态变化组织；`CHG-*`、仓库、文件或配置 key 是否错误地控制正文叙事
- 同级章节是否使用同一划分维度，`DEC-*` 是否唯一承载跨变更决策，横切维度是否写回对应机制而非形成重复事实源
- `AC → 设计正文 → CHG → 验证信号 → 发布/回滚` 是否闭环；`traceability.md` 的 CHG 集合是否覆盖目标设计的实际行为变化，且不存在孤儿变更；追踪引用的章节号是否都存在于 `solution.md`
- 读者测试是否按 `reader-test-protocol.md` §5 判定通过（全文读者七问、截断读者前五问、核心机制探针、成立的探针问题已处置）；主图是否存在或豁免理由成立，`diagrams/results.md` 是否全部通过
- 核心机制的变更清单表是否按改动对象写出“现在怎么做 → 改成怎么做 → 解决什么问题”：只看这张表能否列出开发要改的方法和每处改成什么；做不到时至少 Medium，类别“结构/可读性”。读者测试中被设计方判为不成立的核心机制缺口和术语歧义，逐条复核判定理由
- 核心机制新增或改变形状的数据结构（进程内缓存、表、Redis key/field/value、消息）是否在流程图之前定义一次：类型签名、字段表、小实例、访问模式（`dev-design-solution` 的 `readability-and-writing.md` 4.1.1）；正文和图描述的操作是否写清取的是整个结构、key、value 还是 entry，且与类型签名一致。缺定义且读者需要倒推结构时至少 Medium，类别“接口数据”；说法与结构不符导致可能实现错误时 High
- 方案声称“原样抽取”“两条路径相同”时，逐个现有方法核对每一步是否真的存在；把不同分支写成相同、照文实现会改变结果的至少 High，类别“可行性”
- 名称与准确性（`writing-principles.md` 2.1 节）：每个名字能否对应到一个真实对象；有没有一个名字指两样东西；动作是否写出主体、对象和结果；“相同/全部/没有”是否有逐项核对。造成误读或可能导致实现错误时至少 Medium
- 自创中文术语是否与项目已有术语重名或丢失原意（如把 Redis Hash 的 field 译成项目里另有含义的“字段”）；造成误读时至少 Medium
- 核心机制是否单列一节并足以照着实现（变更清单、前后对照示例、流程图加实现对照表、边界情况、依赖调用结果表、不变量及其静默破坏条件）；正文里满足图触发条件的内容是否有图或写明不画的理由。是否有 2.4 变更总览，图和第 3 章表格是否标出新增、修改与现有，且与 CHG 矩阵一致。这三项影响实施、评估和验证，缺失时按结构/可读性 finding 处理，不属于文风偏好
- 30 秒、5 分钟、标题、双读者、唯一归属和范围隔离测试是否通过；篇幅阈值是否只被当作结构复核信号
- 全称断言是否可复现：按 `solution-structure-contract.md` §5 附则，“唯一 / 全仓 0 命中 / 完整枚举 / 无其它 X”这类断言必须附可复跑检索命令、检索范围与命中计数。**未附命令的全称断言一律按 `Unknown` 处理，不得作为任何 finding 的关闭依据，也不得作为其它结论的支撑事实**

输入或证据缺失导致无法继续判断时结论为“材料不足”；方案内容本身存在结构或追踪缺陷时形成 finding。除非缺陷使后续判断失去可信基础，否则仍继续领域评审。

### 4. 按 traceability.md 逐项评审交付完整性

评审覆盖表必须包含 `traceability.md` 追踪矩阵中的每个 `CHG-*`，但不要求正文按 CHG 分章。对每项重新核对：

- 当前行为及代码/配置/数据证据是否成立
- 新增、修改、删除或保持不变的动作是否明确，关联 `DEC-*` 的依据是否足够
- 调整后行为、不变量、影响对象和模块责任是否自洽
- 接口、数据、状态、配置、异常、并发、幂等、兼容、安全和观测边界是否按相关性处理
- 验证信号、发布步骤和回滚处置是否能证明该 CHG 可安全交付

`保持不变` 的 CHG 按受保护的回归边界评审，不要求虚构实现步骤。不得只抽查部分 CHG 后给出整体通过。逐 CHG 覆盖不要求正文按 CHG 分章，也不得因此要求生成方把 CHG 搬回正文。

需求列有用户关注点 `CON-*` 时，逐条核对方案的满足方式是否回应了用户原话，而不只满足转写后的验收标准；被缩窄或只满足一半的关注点形成 finding。

### 5. 核查核心机制的隐含前提

前几步主要核对方案写出来的内容；本步专门找方案没写出来、但正确性依赖它的前提。这一步是方案评审的重点，结构与追踪检查不能挤占它：

- 列出核心机制的每条不变量和每个判断条件，写出它成立所依赖的前提，尤其是依赖组件的行为：失败时抛异常还是返回空、超时、部分成功、重试、并发写入、数据过期或残留；
- 每个前提到代码、配置或日志里核实，不采信方案自述；方案缺依赖调用结果表、表中缺格或缺证据，直接形成 finding；
- 方案以"空、缺失、默认值、未加载、null"作为判断条件时，逐一追问它可能由哪些不同原因造成（真的没有数据、还没查询、查询失败被吞掉、部分失败、旧版本数据），方案能否区分；无法区分且会让失败被当成正常结果时，至少定为 High；
- 方案断言现有方法"只做 X""不会 Y"时，读完整个方法体及其直接调用的方法再判断。

报告 4.4 节列出本轮核实的前提、核实位置和结果；核实不了的记 `Unknown` 并写明原因。没有发现问题时，结论里也要写本轮核实了哪些前提，不能只写"未发现阻断问题"。定点复审时，diff 触达核心机制小节或其依赖的前提就重做本步；未触达时至少复核上一轮报告 4.4 节中一条前提是否仍成立。

### 6. 补查跨变更风险

完成逐项评审后，再按主 profile 检查核心正确性证明，并补查跨 CHG 的架构职责、共享状态与事务边界、顺序/并发/一致性、性能容量、安全权限、可观测性、发布迁移和整体回滚。按相关性标记 `Pass / Finding / N/A / Unknown`；`N/A` 写明原因，不为完整感制造问题。

### 7. 形成分级 findings

每条问题都包含：稳定 ID、内容指纹、问题、证据、影响、严重度、类别、对象引用、根因/修复位置、`root_cause_id`、建议、关闭条件、状态和是否阻塞开发。`root_cause_id` 标识同一根因，**同一根因的多条 finding 在结论判定时合并计为一条，严重度取其中最高**；报告仍逐条列出，只在计数与收敛判断时合并。对象引用优先使用 `DEC-*` / `CHG-*` / `AC-*` / `RISK-*`，无法绑定时引用具体章节。问题、证据或影响实质变化时更新指纹。

结构类 finding 还应标记：`profile 误选` / `正文清单化` / `层级错位` / `结构重叠` / `覆盖缺口` / `孤儿变更` / `重复事实源` / `表达冗余` / `读者测试未通过`。只有它造成决策歧义、实现边界不清、内容矛盾、遗漏风险或无法追踪时才形成 finding；纯标题偏好、个人文风或不影响理解的措辞不升级为问题。措辞、追踪引用和证据格式类问题默认定为 Low，只有影响决策、实施或验证判断时才升级。读者测试按协议 §5 判定不通过，或结构缺陷导致读者无法定位机制、取舍、影响或回滚，至少定为 Medium，类别"结构/可读性"。

- `Blocker`：核心方向不可行、关键约束冲突，或缺少无法绕过的决策与证据；不得进入开发
- `High`：高概率导致正确性、兼容性、安全或稳定性问题；原则上修改后复审
- `Medium`：当前可能可实施，但存在明确维护、演进或实施风险；应修正或显式接受
- `Low`：不阻塞开发的局部改进或表达问题；控制数量，避免噪音

事实性风险与偏好建议分开写；严重度必须与实际影响匹配。

### 8. 给出评审结论

先确认评审执行状态为 `valid`；执行失败的一次重试与 `formal_reviewer_unavailable` 规则见委派契约 §3，有效 reviewer 的否决属于正常结果。

结论只能是以下之一：

- `通过`：没有未关闭的 Blocker/High/Medium；Low 不影响结论
- `有条件通过`：没有 Blocker/High，剩余 Medium 已由用户明确授权接受，并记录 finding ID/指纹、`(R,S,B)`、授权来源、适用范围、生效前提、到期条件和后续动作
- `修改后复审`：方向基本成立，但存在必须修正的问题
- `退回重设计`：核心方向、边界或技术依据不成立
- `材料不足`：证据不足以判断是否可以实施

任何未关闭的 Blocker/High 都不能通过。未经匹配授权的 Medium 必须修正并复审；修复只影响论证或引用时可做定点复审，但新 `S` 仍需绑定新审批。纯措辞建议只有在不影响决策、实施边界和验证判断时才归 Low，作为后续建议，不设置“已通过但进入下一阶段前必须改原文”的隐含门禁。没有发现问题时也要明确写“未发现阻断问题”。

严重度决定能否通过，根因决定路由：当前方向内可修复的问题使用“修改后复审”；核心 `DEC-*`、系统边界或技术基础不成立时使用“退回重设计”；关键输入或证据不足时使用“材料不足”。不得仅根据 Blocker 数量机械选择结论。

风险授权是新的评审输入：编排器按委派契约 §3 新建 `task_id` / `round`，保持同一 `(R,S,B)` 并连同授权记录重新派发独立 reviewer，由新一轮决定是否形成 `有条件通过`。

### 9. 收敛后续动作与复审范围

结论为 `修改后复审` 或 `材料不足` 时，编排器按委派契约 §3 归类后直接推进修订与复审，不把“是否修改”交给用户；需要用户决定的只有契约 §3 列出的事项。派发下一轮前，编排器确认修订版本已重做读者测试、信封里的版本号取自产物文件本身、上一轮的 `resolution.md` 和新旧 diff 已就绪。

- 明确需要修改的方案章节和关闭条件
- 标明哪些风险已接受、由什么前提约束
- 判断下一轮是完整复审还是定点复审；定点复审只缩小领域重查范围，不省略方案身份校验、全局结构/追踪一致性检查和变更影响非回归检查
- 强制全局检查按可判定性分两类执行：**机械可判类**（指纹一致性、`CHG-*` 集合计数、`AC-*` 连续性、映射表逐字节 diff）由编排器在派发前跑完并把结果作为冻结输入写进信封，reviewer **抽验**若干项而非全量重跑，抽验项须在报告中列出；发现任一抽验项与信封不符时立即恢复全量重跑并按执行异常处理。**语义类**（摘要与正文一致、已关闭项非回归）保留由 reviewer 执行，范围收敛到“本轮 diff 触达的章节、引用或依赖这些章节的章节（如共享决策变化时的发布、回滚章节）+ 上轮已关闭项中被 diff 触达者”，依赖关系无法确认时按下一条完整复审；核销以编排器下发的 diff 和设计方的 `resolution.md` 为依据，不要求正文自证。编排器承担机械项不等于放弃独立复核——抽验是防止编排器自身出错的必要环节，不得取消
- 新 `S` 的差异、影响范围或未变部分无法可靠证明时，必须完整复审
- 记录进入 `dev-derive-test-cases` 前必须满足的条件，并交出完整 `(R,S,B)`、评审轮次/结论以及已授权风险及其绑定
- 编排器把报告正文和 `delegation-result-v1` 分别保存并计算指纹，生成不可变 `approval-record-v1`；handoff 只引用该记录的 ref 与 fingerprint

## 编排脚本

冻结、快照和审批记录用共享脚本生成，不手写。版本号从产物文件头读取，`--prior-round` 会带上上一轮的报告、findings、审批记录、`resolution.md`，并按上一版归档目录 `versions/<版本>/` 生成 diff：

```bash
RR=/home/joney/projects/ai/agent-tools/skills/dev-workflow/scripts/review_round.py
REQ=/home/joney/docs/requirements-development/<requirement-name>
python3 $RR --req-dir $REQ --round <N> freeze --artifact R=requirements:summary.md \
  --artifact S=solution-design:solution.md,traceability.md \
  --artifact reader_test=solution-design:reader-test/agent-v<M>.md,reader-test/answer-key-v<M>.md \
  --repo <代码仓库> [--repo <前端仓库>]
python3 $RR --req-dir $REQ --round <N> envelope --task-id <id> --scope "<本轮范围>" [--prior-round <N-1>] [--evidence <路径>]
python3 $RR --req-dir $REQ --round <N> snapshot before
# 派发 agent-tools-solution-reviewer，提示词只给信封路径；停止后：
python3 $RR --req-dir $REQ --round <N> snapshot after
python3 $RR --req-dir $REQ --round <N> persist --transcript <subagent 记录> --findings <编排器归类后的 findings.json> \
  --reviewer-ref <spawn 返回的实例 ID> --model <模型> --trust-limit "<信任限制>"
# 用户选了外部模型时，派发与收口改为（双评审时次 reviewer 用 --slot secondary 先落盘）：
python3 $RR --req-dir $REQ --round <N> task
python3 /home/joney/projects/ai/agent-tools/skills/common/spawn-model-agent/scripts/spawn_model_agent.py --backend <后端> \
  --readonly --tools Read,Grep,Glob --cwd <代码仓库> --wait --task @$REQ/solution-review/rounds/round-<N>/evidence/external-task-primary.md
python3 $RR --req-dir $REQ --round <N> persist --spawn-job <作业目录> --findings <json> --selected-by user
```

`--findings` 中每条 finding 带编排器的 `classification`，`噪音` / `契约误读` 附原文证据，双评审标 `found_by`，漏检写 `escaped_from`（委派契约 §3.2）；`persist` 同时把本轮写入本机评审记录，汇报时列出被判为噪音或误读的 finding 供用户抽查。

`freeze` 报出机械检查失败时先修产物再派发；`persist` 在结构、指纹回显、写入证明或工具面任一不通过时退出码非 0，审批记录的结论为空。

## 评审原则

- 评审结论基于需求、方案和代码证据，不基于理想化偏好
- 评审者不静默改写方案，但有权否决方向并要求重设计
- 先结论、再阻断、再证据、再动作
- 每条问题只表达一个可验证风险，避免把多个主题混在一起
- 评审深度与改动风险相匹配，简单方案不强行扩展成重型审计
- 结构评审服务于正确决策和实施，不把个人写作偏好当作门禁

## 输出模式

### 对话模式

默认按“结论 → 阻断问题 → 重要 findings → 证据限制 → 后续动作”输出轻量评审结果。

### 文档模式

用户要求正式评审或落盘时，使用 `references/review-template.md`。报告按“结论 → findings → CHG 覆盖 → 跨变更风险 → 后续动作 → 执行与历史”组织，引用指定版本的 `solution.md`，不重写架构、流程和候选方案正文。向用户汇报本轮结果时，原样粘贴 `rounds/round-<N>/scorecard.md`（`persist` 写入），不改写、不删行。

## 可选增强

- 方案涉及复杂 SQL、DDL、索引、事务边界或数据兼容性时，可调用 `review-db-change` 做数据库风险专项判断
- 方案涉及 Redis、MQ、任务调度，或存在超时、重试、幂等、降级等可靠性设计时，可调用 `review-middleware-reliability` 补查中间件与外部依赖行为

## 结果要求

一份合格的评审结果应满足：

- 能确认评审对象、版本、范围和证据来源
- 能通过 `approval-record-v1` 确认全部 producer、真实 reviewer、身份不相交、有效工具面只读且 reviewer 未写入工作区
- 能区分阻断问题、重要问题、一般建议与证据限制
- 能确认方案只使用一个合理主 profile，摘要与权威正文一致，读者测试通过，并通过 30 秒、5 分钟、标题和双读者测试
- 能确认正文按技术机制组织，横切维度有唯一权威位置，且 `AC → 设计 → CHG → 验证/发布` 可追踪
- 能证明 `traceability.md` 中的每个 `CHG-*` 都被评审，并把 finding 精确绑定到对应决策、设计位置、变更、验收标准或风险
- 能识别 profile 误选、正文清单化、层级错位、覆盖缺口、孤儿变更和重复事实源，而不进行无影响的文风挑错
- 能说明方案是否可以进入开发以及判断依据
- 能指导方案修订、findings 关闭和必要复审
- 不重复整份技术方案，不把评审报告写成第二份方案

## 交接建议

- `通过` 或新一轮独立 reviewer 确认的 `有条件通过` → 先提醒用户安排人工评审方案内容（技术评审，线下审阅或评审会均可），并列出需要人重点判断的关键决策、核心机制、失败与回滚、需求方已确认的偏差及残余风险；人工意见由编排器记为下一轮 findings，修订后定点复审。人的读者测试（`dev-design-solution/references/reader-test-protocol.md` 第 7 节）只检验可读性，不替代人工评审。用户确认无需人工评审或人工评审已无未处置意见后，再转 `dev-derive-test-cases` 编写测试清单。无人值守编排（如 `dev-auto-loop`）不停下等待，把人工评审列入终态汇报的待办；若用户明确要求跳过测试清单链路，必须先生成跳过 `test-design-review` 的不可变 `waiver-record-v1`，记录逐门禁替代证据与残余风险，并以 `G={mode: waived,W:{ref,fingerprint}}` 携带仍有效的方案审批转 `dev-build-change`，不得只写“已记录风险”或构造无 `G` 交接
- `修改后复审` 或 `退回重设计` → 转 `dev-design-solution`，修订后重新评审
- 需求边界不清 → 回到 `dev-clarify-task`
- `材料不足` → 补充指定证据后继续当前评审
- `formal_reviewer_unavailable` → 补齐独立 reviewer 能力后，在同一冻结输入上重新执行正式评审
