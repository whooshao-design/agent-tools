# 开发执行清单契约

本契约供 `dev-build-change` 在编码前把稳定目标拆成可执行的 `DEV-*`，并供 `build-codeagent`、`dev-auto-loop`
消费执行状态。它不是新的需求、方案、测试清单或审批产物，不增加独立门禁。清单文件的表达遵循
`/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/writing-principles.md`（第一屏、段落、表格、标识引用），本契约只规定结构。

## 1. 定位与追踪

开发执行清单回答“按什么顺序修改哪些对象、怎样确认每项完成”，不重新定义目标行为或测试标准：

- `approved`：保持 `AC-* → CHG-* → DEV-* → TC-* → 验证结果` 可追踪。
- `direct`：保持 `direct-record-v1` 完成标准 → `DEV-*` → 验证结果可追踪。
- `waived`：记录 `waiver-record-v1`、仍有效的上游产物、替代证据与 `DEV-*` 的关系，不虚构被豁免的 CHG/TC。

方案 `CHG-*` 是行为变更事实源，测试清单 `TC-*` 是验证事实源，`DEV-*` 只描述施工单元。发现目标或验证标准
需要实质变化时，停止拆分并返回最早失效阶段，不能在开发清单中静默改写上游事实。

## 2. DEV 字段

每个开发项至少包含：

| 字段 | 要求 |
|---|---|
| `DEV-*` | 当前开发清单内稳定且唯一的 ID |
| 来源 | approved 绑定 `CHG-*` 与相关 `TC-*`；direct/waived 绑定对应记录与完成标准 |
| 目标 | 一句话说明完成后可观察的实现结果 |
| 影响对象 | 预计模块、文件、接口、数据或配置；未知项明确标记，不能伪造精确路径 |
| 预计写集 | 用于冲突判断的文件/目录边界；编码中发现偏差时先更新影响判断 |
| 依赖 | 前置 `DEV-*`；无依赖写 `[]`，依赖关系必须无环 |
| 完成条件 | 能独立判断 Done 的代码与必要自检条件 |
| 验证入口 | 关联 `TC-*`、direct 完成标准或替代证据；不在此重复测试正文 |
| 状态 | `Planned` / `InProgress` / `Done` / `Blocked` / `Skipped` |
| 执行证据 | 实际改动路径、producer refs、结果摘要；执行前为空 |

`Blocked` 必须记录原因和恢复条件；`Skipped` 仅用于经重新核对确认无需代码的项，并记录依据。不能用 Skipped
掩盖未完成工作。

## 3. 拆分规则

- 能独立实施并确认完成的行为单元拆成独立 DEV；必须原子完成才能维持同一不变量的多处修改合并。
- 两个 DEV 若存在先后依赖、可分别失败/回滚或适合由不同 producer 执行，应拆开。
- 同一文件可以属于多个 DEV，但必须建立依赖并串行执行，或合并为一个原子 DEV；不得以重叠写集并行。
- 管理动作、阅读代码、汇报进度不单独建立 DEV；必要的测试代码、迁移、配置和回滚实现可以建立 DEV。
- 同级 DEV 使用同一执行粒度；避免一个 DEV 写“完成整个需求”，另一个只写“修改一个字段”。
- 简单任务允许只有一个 `DEV-001`，不为形式完整强制拆分。

## 4. 完整性检查

编码前必须满足：

1. 每个范围内 `CHG-*` 至少映射一个 DEV；保持不变的 CHG 可以映射到“回归保护/无需代码”的 DEV。
2. 每个 DEV 都有稳定来源、完成条件和验证入口，不存在无来源开发项。
3. 每个范围内 `TC-*` 都映射到实现 DEV 或明确的无需代码理由；验证清单不能替代开发清单。
4. 依赖图无环，首批可执行项明确；预计写集足以判断串并行安全。
5. DEV 合集覆盖本次交付范围且不包含明确非目标。

任何一项不满足且会改变实现路径时，先补齐上游材料或回退，不以猜测开始编码。

## 5. 执行、并行与修订

- 默认按依赖拓扑串行执行；只有依赖已满足且预计写集不相交，或使用隔离 worktree 时才并行。
- `build-codeagent` 每个 producer 信封只消费一个已定义 DEV，不自行拆分、合并或扩写范围。
- 开始写入前将状态改为 InProgress；完成后记录实际写集、producer refs 和结果，再改为 Done。
- 实际写集超出预计边界、出现新依赖或完成条件变化时，暂停相关项并先修订清单；不得让其他 producer 继续基于陈旧边界并行。
- 修复验证/代码评审 finding 时新增或修订绑定该 finding 的 DEV，保留已完成项历史，不把旧 Done 静默改写为新工作。

清单结构变化不构成新审批，但必须留在当前开发摘要或 auto-loop checkpoint 中，确保恢复时能区分已完成、待执行和
阻塞项。

## 6. 表达与落盘

简单或单轮任务可在对话/执行计划中维护一行式清单：

| DEV | 来源 | 目标 | 影响对象/写集 | 依赖 | 完成条件 | 验证入口 | 状态 |
|---|---|---|---|---|---|---|---|
| DEV-001 | CHG-001 / TC-001 | | | [] | | | Planned |

跨模块、跨 producer、需要并行或跨会话恢复时，可保存到
`/home/joney/docs/requirements-development/<requirement-name>/code-implementation/development-checklist.md`。
该文件是可更新的执行视图；最终交接以 `change_revision` 中的 DEV 结果摘要、实际写集和 producer 溯源为准。
