# dev-build-change

## 定位

用于在代码开发阶段把“要改什么”落实成最小、可交付的代码变更。

它是开发阶段的主入口：既支持只把稳定目标拆成轻量 `DEV-*` 开发执行清单，也支持继续按清单实施最小安全改动；
不新增独立审批门禁，也不内置特定技术栈细节。用户只要求清单时不得默认修改业务代码。

开发执行清单统一遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/dev-build-change/references/development-checklist.md`。

## 默认产物目录

代码改动默认直接落在当前工作区源码中；如需额外落盘开发摘要，默认放到 `/home/joney/docs/requirements-development/<requirement-name>/code-implementation/`，建议文件名使用 `change-summary.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 若只有代码改动且无需额外摘要，可不创建该文件
- 简单任务在对话或执行计划中维护 `DEV-*`；跨模块、跨 producer、并行或跨会话任务可额外保存 `development-checklist.md`

## When to Use

适合以下场景：
- 只需要根据技术方案、测试清单或完成标准生成/拆分开发执行清单，暂不编码
- 需求和方案已基本明确，准备开始改代码
- 需要先理解现有实现、调用链和约定，再决定怎么改
- 目标是做最小安全改动，而不是顺手重构一大片
- 需要在改动后做最小必要自检，确认改动可继续推进

不适合以下场景：
- 需求边界仍模糊，此时先转 `dev-clarify-task`
- 实现路径还未收敛、需要先比较方案，此时先转 `dev-design-solution`
- 当前重点是验证结果而非继续改代码，此时转 `dev-verify-change`

## 执行模式

### 清单模式

用户要求“生成开发清单”“拆分开发任务”“根据技术方案列实施步骤”或明确暂不编码时，只执行 Workflow 1–3：

- 读取方案和必要代码上下文，输出 `DEV-*` 清单后停止
- 不修改业务代码，不生成虚假的 `change_revision`，DEV 初始状态为 `Planned` 或有明确原因的 `Blocked`
- 可以基于用户明确指定的方案版本生成草案；若方案已归档、未审批、缺少测试清单或代码基线，只标明身份和限制，不虚构正式准入

### 构建模式

用户明确要求实施、编码或继续完成改动时，执行完整 Workflow 1–6；任何代码写入前必须满足相应 `gate_context G`。

## Workflow

### 1. 对齐前提与交付模式
至少确认：
- 需求目标、完成标准已基本明确
- 本次明确不做的内容
- 可以读取的代码上下文、相关模块或相似实现
- 当前产物身份、审批状态，以及已有 `B` 或在任何代码写入前冻结 `B` 的条件

如果目标、完成标准或范围存在会改变实现路径的重大歧义，先回到 `dev-clarify-task` 或 `dev-design-solution`，不直接凭猜测改代码。仅缺少预先构造的 `G/D`，但用户请求稳定、边界清晰且可从仓库确认实现上下文时，不属于该阻塞。

清单模式先固定用户明确提供的 `R/S/C/B` 引用及其已知状态；缺少交付 `G` 不阻塞生成带限制说明的清单草案，但
不能声称清单已获编码准入。构建模式开始编码前，按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md`
固定且只选择一种 `gate_context G`：

- `approved`：核对 `approvals.solution-review` 精确绑定 `(R,S,B)`、`approvals.test-design-review` 精确绑定 `(R,S,C,B)`，两个不可变 `approval-record-v1`、`T` 与当前产物完全匹配，且 `B` 未因外部合并、变基或非本任务改动变化；必须消费全部范围内检查项
- `direct`：仅用于从未进入正式治理流程的普通任务。`G.D` 必须是不可变 `direct-record-v1` 的 `{ref,fingerprint}`；重读并核对任务引用、完成标准、范围和 `B`，不得声称拥有方案或测试清单审批
- `waived`：仅在正式门禁原本适用且用户以不可变 `waiver-record-v1` 明确跳过指定门禁时使用。重读 `G.W={ref,fingerprint}`，校验枚举、依赖闭包、逐门禁替代证据/残余风险和授权范围；其余适用门禁仍须以 `approval-record-v1` 证明

当本 skill 被清晰普通任务直接调用、尚无 `G/D`，且没有正式治理产物、`governance_path=approved` 或 waiver 迹象时：

1. 从当前稳定用户请求提取任务引用、完成标准、范围/排除范围和选择 direct 的理由。
2. 读取必要仓库上下文，在任何代码写入前冻结 `B`。
3. 判断代码评审是否因风险或用户要求而必需。
4. 构造最小 `direct-record-v1`，保存为不可变文件或消息；记录本身不写自身指纹，对最终字节外部计算 SHA-256。
5. 以 `G={mode: direct,D:{ref,fingerprint}}` 继续实现。

这是对 direct 条件的正向确认，不是把“未找到审批”自动解释为 direct。若发现正式路径已开始、存在显著方案取舍或范围仍不稳定，则不得构造 `D`，应回最早缺失阶段。`dev-auto-loop` 只接受 `governance_path=approved`，并在方案和测试清单审批均完成后才形成 `G.mode=approved`。

### 2. 先读懂再改
围绕本次任务做最小必要分析：
- 相关模块、入口、调用链和数据流
- 现有命名、分层、错误处理和复用模式
- 真正需要修改的位置，以及可能受影响的边界
- 仓库的隐性约定：测试发现方式、目录约束、日志粒度、配置开关使用习惯、注释密度
- 是否已经存在相似实现；若已有相似模式，默认沿用，不主动发明新结构

### 3. 拆分开发执行清单

编码前按共享清单契约建立 `DEV-*`：

- `approved` 从范围内 `CHG-*` 和 `TC-*` 派生，保持 `AC → CHG → DEV → TC → 验证` 可追踪
- `direct` 从 `direct-record-v1` 的完成标准派生；`waived` 从仍有效产物、替代证据和授权范围派生，不虚构被豁免的 CHG/TC
- 每个 DEV 明确来源、目标、影响对象、预计写集、依赖、完成条件、验证入口和初始状态
- 简单任务允许只有一个内联 `DEV-001`；复杂任务才落盘，不把执行清单升级成新的审批产物
- 编码前检查范围覆盖、无来源开发项、TC 映射、依赖无环和写集冲突；发现上游缺口时回最早失效阶段

清单模式到此结束，输出来源身份、优先级/依赖说明、完整性缺口和 `DEV-*` 表；不得继续进入第 4 步。

### 4. 按依赖实施最小必要改动

按 DEV 依赖顺序编码，只保留当前任务必需的变更：

- 优先复用现有实现和模式，避免新增无必要抽象
- 保持接口、行为和风险边界清晰
- 新增类、方法或修改关键分支时，同步检查职责、输入输出、异常语义与约束是否易懂；必要注释随实现补齐，不把“沿用仓库密度”解释为可以省略逻辑说明
- 不顺手做无关重构、清理或风格统一
- 新增或迁移单测时，按仓库文档、测试发现配置或实际执行结果所证明的布局放置；仅存在 `mock` 目录不能推出所有测试都必须进入 `mock.*`，只有证据表明 suite/门禁如此发现测试时才应用该约束
- DEV 开始前标记 `InProgress`，完成后记录实际写集、producer refs 和结果并标记 `Done`；Blocked/Skipped 必须记录理由
- 只有依赖已满足且写集不相交，或使用隔离 worktree 时才并行；实际写集超出预计边界时暂停相关并行项并重新判断

涉及多路径、方法拆分、新抽象、参数、防御式代码、重复、配置、日志，或新增类/非自解释方法/关键分支时，读取并遵循 `references/implementation-simplicity.md` 对应细则；不为不相关维度加载细则。

### 5. 编码后先做一次简化回看
进入验证前，至少自查一次：
- 是否保留了本可统一的一条主路径
- 是否有可下沉到使用点的透传参数或中间结果
- 是否新增了其实可以删除的 helper、结果对象、构造器、配置开关、空判断
- 是否存在重复判空、重复条件、重复分支体、重复配置读取、重复中间变量构造
- 是否有只为“显得工程化”而存在的拆分
- 类职责、非自解释的方法语义与关键分支是否已有准确说明，注释是否只帮助理解代码，未混入方案/清单编号、章节、版本、审批或开发过程记录
- 是否有重复代码字面意思、已与实现不符或不符合仓库风格的注释或日志

### 6. 建立执行与检查项映射并交给验证阶段
当改动已形成可验证结果后：
- 说明本次改了什么与影响范围
- 标出主要风险点
- 汇总每个 DEV 的来源、最终状态、实际改动路径、producer refs 和未完成原因；不能把 Planned/InProgress/Blocked 静默当成 Done
- `G.mode=approved` 时，逐条输出“检查项 ID (`TC-*`) → 实现位置/无需代码的理由 → 自动测试或人工检查 → 当前结果/未覆盖原因”；每个范围内检查项都必须出现，未覆盖项不能静默省略
- `G.mode=direct` 时，按 `direct-record-v1` 的完成标准给出实现位置与建议验证映射，并记录代码评审是否必需
- `G.mode=waived` 时，逐门禁列出被跳过项、仍有效审批、替代证据和残余风险
- 按共享身份契约生成 `change_revision`，记录 DEV 结果摘要，并把 `G`、已授权风险、`change_revision` 和上述映射一并交给 `dev-verify-change`
- 在 `change_revision` 中记录所有实质生成或修改代码的 `producer_agent_refs`；子任务产出由主线吸收时不能丢失其 producer 溯源
- 将最小验证重点交给 `dev-verify-change`

## 常见借口与反驳

| 借口 | 反驳 |
|---|---|
| “既然打开了这个类，顺手把旁边的也重构了” | 无关重构扩大写集与影响面，也让评审失焦；记为观察项另立任务，不并入本次 |
| “需求很明显，不用 direct record 直接改” | 记录只需几行；没有 `G` 的改动无法验证、评审和收口，也无法证明范围受控 |
| “先加个开关/helper/参数，以后用得上” | 未来需求不是本次目标；能少一层抽象、少一条透传就先不加 |
| “先能跑，简化回看以后做” | 简化回看是编码的最后一步，不是可选项；重复分支和透传参数在验证前处理最便宜 |
| “仓库注释少，所以我也不写” | 注释以“够用且准确”为标准：新增类、非自解释方法和关键分支要说明，仓库密度不是免写理由 |

## 开发原则

- 先理解上下文，再修改代码
- 以最小改动解决当前问题，避免过度设计
- 尊重现有代码模式，优先复用而非重写
- 先控制影响范围，再考虑增强和扩展
- 复杂度控制和正确性同样重要；能少一层抽象、少一层透传、少一条路径时，默认优先更简单的方案
- 同样重视简洁与去重；若能通过合并分支、复用局部结果、删除重复判断来让实现更直接，默认优先更直接的写法
- 注释以“够用且准确”为标准：必要说明不能缺，简单代码不逐行翻译；只解释代码职责、逻辑及约束，研发追踪信息放开发摘要或执行清单
- 结论基于代码证据，不基于想象中的理想结构

## 输出物

默认输出一份轻量开发结果，至少包括：
- 前提状态：当前 `gate_context G`、对应审批/direct/waiver 记录、`change_revision`
- 产出者：`change_revision.producer_agent_refs[]`
- 开发执行清单：`DEV-*` 的来源、依赖、最终状态、实际写集和执行证据
- 改动摘要：本次完成了什么改动
- 受影响范围：涉及的模块、文件或接口边界
- 关键判断：为何这样改，复用了什么现有模式
- 注释说明：类职责、方法语义和关键分支中哪些需要说明、已补到哪里；无需注释时说明命名或现有说明为何足够，不以“仓库注释少”代替判断
- 风险提示：需要关注的边界、异常路径或兼容点
- 映射：approved 列全量检查项；direct 列 `D` 的 ref/fingerprint 与完成标准；waived 列 `W` 的 ref/fingerprint、被跳过门禁、仍适用门禁、替代证据和残余风险
- 验证建议：下一步最小应验证什么

## 结果要求

一份合格的开发结果应满足：
- 能说明改动建立在已理解代码上下文之上
- 能证明改动范围受控且与任务目标一致
- 能证明全部范围内目标已映射到 `DEV-*`、每个 DEV 有来源与完成条件，且执行状态没有被静默跳过
- 能说明新增抽象、方法拆分、参数传递和日志/注释选择是有依据的，而不是随手工程化
- approved 的全部范围内检查项均有实现与验证映射；direct 不声称上游审批；waived 只跳过授权门禁；上下文陈旧时没有继续编码
- 能自然衔接到验证阶段，而不是停在“已写完代码”
- 保持轻量，不携带特定栈的重型实现细节

## 可选增强

- 如任务复杂或需要多后端 producer，先由本 skill 拆好 `DEV-*`，再调用 `build-codeagent` 按项执行；执行后端不得自行扩写清单

## 交接建议

- 改动完成后，进入 `dev-verify-change` 做围绕本次变更的最小有效验证
- 如果在编码前发现实现路径仍未收敛，回退到 `dev-design-solution`
