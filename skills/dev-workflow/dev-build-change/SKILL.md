# dev-build-change

## 定位

用于在代码开发阶段把“要改什么”落实成最小、可交付的代码变更。

它是开发阶段的主入口：先理解现有代码和边界，再实施最小安全改动；不内置重型流程、固定产物路径或特定技术栈细节。

## 默认产物目录

代码改动默认直接落在当前工作区源码中；如需额外落盘开发摘要，默认放到 `/home/joney/docs/requirements-development/<requirement-name>/code-implementation/`，建议文件名使用 `change-summary.md`。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 若只有代码改动且无需额外摘要，可不创建该文件

## When to Use

适合以下场景：
- 需求和方案已基本明确，准备开始改代码
- 需要先理解现有实现、调用链和约定，再决定怎么改
- 目标是做最小安全改动，而不是顺手重构一大片
- 需要在改动后做最小必要自检，确认改动可继续推进

不适合以下场景：
- 需求边界仍模糊，此时先转 `dev-clarify-task`
- 实现路径还未收敛、需要先比较方案，此时先转 `dev-design-solution`
- 当前重点是验证结果而非继续改代码，此时转 `dev-verify-change`

## Workflow

### 1. 对齐前提与审批元组
至少确认：
- 需求目标、完成标准已基本明确
- 本次明确不做的内容
- 可以读取的代码上下文、相关模块或相似实现
- 当前需求版本、已评审方案版本和实现开始前冻结的代码基线 `B`

如果这些前提仍不成立，先回到 `dev-clarify-task` 或 `dev-design-solution`，不直接凭猜测改代码。

开始编码前检查交接材料和默认产物目录。若存在与当前需求/方案关联的测试场景清单：

- 固定场景审批元组 `T = (R,S,C,B)` 及对应方案/场景审批记录，结论必须是 `dev-review-test-cases` 对该 `T` 给出的“通过”；`B` 是实现开始前的冻结基线，任务自身产生的 diff 另记为 `change_revision`
- 核对 `R/S/C` 与当前产物精确匹配，`B` 未因外部合并、变基或非本任务改动发生变化，且送审后场景正文没有变化；任务自身 diff 不改写 `B`。匹配时必须消费全部本次范围内的场景，不得把它降级成可选参考
- 元组中的需求或方案版本已陈旧时停止编码；当前方案已评审通过则依次回 `dev-derive-test-cases`、`dev-review-test-cases`，否则先回方案设计/评审阶段
- 场景版本、正文或评审结论不匹配时停止编码；需改场景先回 `dev-derive-test-cases`，只缺有效评审则回 `dev-review-test-cases`

确实没有已通过场景清单时，记录“无场景审批元组”及依据，按当前需求、方案和仓库门禁实施；若所属流程本应先产出场景，则停止并依次转 `dev-derive-test-cases`、`dev-review-test-cases`，不能以“未找到”为由跳过。

### 2. 先读懂再改
围绕本次任务做最小必要分析：
- 相关模块、入口、调用链和数据流
- 现有命名、分层、错误处理和复用模式
- 真正需要修改的位置，以及可能受影响的边界
- 仓库的隐性约定：测试发现方式、目录约束、日志粒度、配置开关使用习惯、注释密度
- 是否已经存在相似实现；若已有相似模式，默认沿用，不主动发明新结构

### 3. 做最小必要改动
编码时只保留当前任务必需的变更：
- 优先复用现有实现和模式，避免新增无必要抽象
- 保持接口、行为和风险边界清晰
- 不顺手做无关重构、清理或风格统一
- 新增或迁移单测时，按仓库文档、测试发现配置或实际执行结果所证明的布局放置；仅存在 `mock` 目录不能推出所有测试都必须进入 `mock.*`，只有证据表明 suite/门禁如此发现测试时才应用该约束

涉及多路径、方法拆分、新抽象、参数、防御式代码、重复、配置、日志或非显而易见注释时，读取并遵循 `references/implementation-simplicity.md`；不为不相关维度加载细则。

### 4. 编码后先做一次简化回看
进入验证前，至少自查一次：
- 是否保留了本可统一的一条主路径
- 是否有可下沉到使用点的透传参数或中间结果
- 是否新增了其实可以删除的 helper、结果对象、构造器、配置开关、空判断
- 是否存在重复判空、重复条件、重复分支体、重复配置读取、重复中间变量构造
- 是否有只为“显得工程化”而存在的拆分
- 是否有不符合仓库风格的注释或日志

### 5. 建立场景映射并交给验证阶段
当改动已形成可验证结果后：
- 说明本次改了什么与影响范围
- 标出主要风险点
- 有有效审批元组时，逐条输出“场景 ID → 实现位置/无需代码的理由 → 自动测试或人工检查 → 当前结果/未覆盖原因”；每个范围内场景都必须出现，未覆盖项不能静默省略
- 把 `T`、审批记录、已授权风险、当前 `change_revision` / 待验代码快照和上述映射一并交给 `dev-verify-change`
- 将最小验证重点交给 `dev-verify-change`

## 开发原则

- 先理解上下文，再修改代码
- 以最小改动解决当前问题，避免过度设计
- 尊重现有代码模式，优先复用而非重写
- 先控制影响范围，再考虑增强和扩展
- 复杂度控制和正确性同样重要；能少一层抽象、少一层透传、少一条路径时，默认优先更简单的方案
- 同样重视简洁与去重；若能通过合并分支、复用局部结果、删除重复判断来让实现更直接，默认优先更直接的写法
- 注释以“够用且准确”为标准，默认跟随仓库密度，不主动制造注释噪音
- 结论基于代码证据，不基于想象中的理想结构

## 输出物

默认输出一份轻量开发结果，至少包括：
- 前提状态：当前 `R/S/C/B`、审批记录、`change_revision`，或无有效元组的依据
- 改动摘要：本次完成了什么改动
- 受影响范围：涉及的模块、文件或接口边界
- 关键判断：为何这样改，复用了什么现有模式
- 注释说明：哪些非显而易见逻辑已补充注释，或为什么无需新增注释
- 风险提示：需要关注的边界、异常路径或兼容点
- 场景映射：场景 ID、实现位置、测试/人工检查、当前结果或未覆盖原因；无有效场景清单时明确写“不适用”及原因
- 验证建议：下一步最小应验证什么

## 结果要求

一份合格的开发结果应满足：
- 能说明改动建立在已理解代码上下文之上
- 能证明改动范围受控且与任务目标一致
- 能说明新增抽象、方法拆分、参数传递和日志/注释选择是有依据的，而不是随手工程化
- 存在有效审批元组时，所有范围内场景均有实现与验证映射；元组陈旧时没有继续编码
- 能自然衔接到验证阶段，而不是停在“已写完代码”
- 保持轻量，不携带特定栈的重型实现细节

## 可选增强

- 如任务复杂、需要拆分执行，或需要借助多后端子代理处理较大改动，可调用 `build-codeagent`

## 交接建议

- 改动完成后，进入 `dev-verify-change` 做围绕本次变更的最小有效验证
- 如果在编码前发现实现路径仍未收敛，回退到 `dev-design-solution`
