# dev-review-test-cases

## 定位

用于在测试清单编写后、编码开始前独立复核“需求 → 方案 → 检查项”的完整性和真实性。本阶段检查清单有没有漏项、错项或不可执行项，不执行测试。内部身份继续使用 `C`，检查项 ID 继续使用 `TC-*`；面向用户统一称“测试清单”和“检查项”。

本 skill 不修改清单、不评审测试代码，也不重做方案评审。清单问题交回 `dev-derive-test-cases`；方案缺口交回 `dev-design-solution`；代码落地后由 `dev-review-change` 评审。

## 审批事实与产物目录

正式评审每轮写入 `/home/joney/docs/requirements-development/<requirement-name>/test-cases-review/rounds/round-<N>/`。

- 每轮目录不可覆盖，包含 `report.md`、`delegation-result.json` 和 `approval-record.json`；顶层 `review.md` 只能作为当前轮展示或指针
- `approval-record-v1` 必须按 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/artifact-identity.md` 绑定完整 `(R,S,C,B)`、方案审批、报告/委派结果指纹和 runtime 检查；该审批有效后才由编排器构造 `T/G`，任一绑定项变化都会使原结论失效
- 只需对话结论时不创建文件，但仍按相同字段声明评审对象

## 输入契约

至少固定：

- 测试清单身份 `C`、状态及上一轮审批记录
- 需求身份 `R` 和验收标准 ID
- 方案身份 `S` 及绑定 `(R,S,B)` 的明确评审结论
- **本轮闭包分母**：`R` 的 `AC-*` 集合与已审批方案的 `CHG-*` 集合，含各自来源产物的 `ref + fingerprint` 与条目计数；分母承载在独立指纹的附录时必须一并绑定该附录，只绑定 `S` 不算完成冻结
- **评审模式是完整复核还是定点复审**；定点复审还必须提供上一版 `C`、上一轮审批记录、待关闭 findings、**TC 级差异清单（新增/修改/删除的 `TC-*` ID）**，以及受影响的 `AC-*` / `CHG-*`
- 已明确接受的风险、假设或排除项及授权记录；评审者不得自行接受风险
- 代码基线 `B`、本轮范围和排除范围
- 上一轮未关闭 findings 与待办（复审时）
- 清单的全部 `producer_agent_refs[]`

关键材料或绑定关系缺失时结论为 `材料不足`，不得用推测给出通过。

## Workflow

### 1. 锁定评审对象

记录精确输入绑定。已送审清单若发生任何内容修订，必须按 `dev-derive-test-cases` 规则归档旧版、递增版本后再评审；不得继续沿用原结论。

### 2. 独立核对三向追踪

正式复核必须由 `agent-tools-test-design-reviewer` 或满足同一契约的独立 agent 执行，并遵循 `/home/joney/projects/ai/agent-tools/skills/dev-workflow/references/delegation-contract.md`。身份、只读、写入、工具面和结果结构的准入只以该契约为准；任何一项无法由运行时事实证明时，不得形成正式结论。编排器冻结 `(R,S,C,B)` 和输入指纹，只传原始需求、方案、清单、必要代码证据与上一轮待复核 findings，不传编写过程或预期结论。编排器提供的代码证据必须逐条区分 `fact`（附检索命令 + 范围 + 计数）与 `inference`（附推理链）；**未标来源的一律按假设处理，不得作为判某维度 N/A 或某检查项不适用的依据**。负向断言（无并发场景 / 无上游消费方 / 路径不可达）需要两条独立检索路径。

三向追踪闭包是集合 diff：编排器在派发前按冻结分母重算 `|AC|` / `|CHG|` / `|TC|` 计数与未映射 ID 差集，作为冻结输入写进信封；reviewer **抽验**若干项而非全量重算，抽验项须在报告中列出，发现任一项与信封不符时立即恢复全量重算并按执行异常处理。

清单的 `producer_agent_refs[]` 必须完整且可稳定标识；根 agent 直接产出时使用会话级 ref 并在执行记录中说明其强度限制，不构成审批阻塞（见 `delegation-contract.md` §1）。不采信编写方的自报结论，逐条核对：

- 每项需求/验收标准是否有方案承接，并有足以验证业务结果的检查项
- 每个方案行为是否有需求来源和检查项覆盖
- 每个检查项是否同时有需求与方案依据，且前置条件、断言和证据要求真实可执行

### 3. 核对风险覆盖

至少检查正常、异常、边界路径，并按变更风险检查并发、权限、安全、兼容、迁移、性能、观测、发布与回滚等相关维度。适用维度集合继承已审批方案的横切维度相关性判定；`N/A` 必须写成对方案该判定的可核对引用（章节号 + 方案给出的理由），**引用不可核对的 `N/A` 按未覆盖处理，不按通过处理**，清单侧自行做出的全称否定同样按未覆盖处理。不能因模板没有枚举就忽略某维度。

### 4. 形成 findings

每条 finding 使用稳定 ID（如 `TC-R-001`）和内容指纹，并写明严重度、原因类型、`root_cause_id`、关联需求/方案/检查项、证据、影响、建议、关闭条件和状态。`root_cause_id` 标识同一根因，**同一根因的多条 finding 在结论判定时合并计为一条，严重度取其中最高**；报告仍逐条列出，只在计数与收敛判断时合并。

- 原因类型：`清单问题` / `方案缺口` / `材料问题`
- 严重度：`Blocker`（核心目标无法可靠验证）、`High`（重要路径或风险遗漏）、`Medium`（会导致实现或验证歧义）、`Low`（不影响判断力的轻微问题）
- 状态只使用 `Open` / `Resolved`；`Resolved` 必须有满足关闭条件的证据并经复核
- 已授权的风险接受作为输入前提和关闭证据记录，不另设风险接受状态绕过评审，也不得由评审者代替授权方作决定

### 5. 给出唯一结论

先确认评审执行状态为 `valid`。独立 reviewer 无法启动、超时或返回无效结果时，可在相同冻结输入上换一个新 reviewer 重试一次；再次失败则返回 `formal_reviewer_unavailable`，不生成领域结论。有效 reviewer 给出不通过结论属于正常结果，不得更换 reviewer 刷取通过。

- `通过`：绑定信息完整，且 Open Blocker/High/Medium 均为 0；Open Low 必须显式保留后续动作
- `修改后复审`：存在需要修正的清单问题，且没有未关闭方案缺口
- `方案缺口`：存在任何未关闭方案缺口。若同时有清单问题，先回设计阶段，并在报告中原样保留清单 findings 和待办
- `材料不足`：证据不足以完成判断

**`方案缺口` 的判定门槛与穷尽要求**：只有当方案的缺失或矛盾使某个 `AC-*` 的覆盖判定无法成立、或使某个 `TC-*` 无法从方案推导时，才记为 `方案缺口`；仅影响清单表述精度的记为 `清单问题`。判定 `方案缺口` 前必须完成本轮全部三向追踪与风险覆盖核对，**一次性列出全部方案缺口**，不得在发现首个缺口后中止评审——外环（方案修订 → 方案复审 → 清单重编 → 清单复核）成本远高于本轮补完，逐个上报会把一次外环放大成多次。

**Medium 的处理**：本阶段不设 `有条件通过`。修正后形成新 `C` 并复核；若用户针对精确 finding ID/指纹与当前 `(R,S,C,B)` 明确授权，则按 §4 记录关闭证据，由独立复核决定结论，授权引用写入报告与审批记录。**Blocker/High 无风险接受路径**。失败信号或证据要求不清、会改变实现或验证判断的事项仍为 Medium，不能仅因修复位于文字而降级。纯措辞建议不影响判断时归 Low，记录后续动作；不附加“通过后、编码前必须修改已审批原文”的 must-fix 门禁。

方案缺口收敛后，必须绑定新方案版本及其审批记录，由 `dev-derive-test-cases` 对受影响范围生成新清单版本，再继续复审并逐条关闭或迁移原 findings；不得丢弃待办或直接进入编码。

### 6. 收敛复审范围

- 判断下一轮是完整复核还是定点复审；**定点复审只缩小领域重查范围，不省略清单身份校验、三向追踪闭包计数一致性、以及上轮已关闭 findings 的非回归检查**
- 定点复审范围以 TC 级差异清单为准，并覆盖差异触达的 `AC-*` / `CHG-*` 及其原有覆盖判定
- 新 `C` 的差异、影响范围或未变部分无法可靠证明时，必须完整复核
- `S` 仅局部变更时，受影响范围之外的检查项按非回归抽验处理；但 `(R,S,C,B)` 的绑定不因此弱化——审批仍绑定完整四元组，变的是复核工作量而不是绑定强度

## 输出要求

默认按“输入绑定 → 结论 → 三向追踪与风险覆盖证据 → findings → 后续动作”输出。编排器在 stop 后保存报告与委派结果、计算两者指纹并生成不可变 `approval-record-v1`。只有该记录的身份、只读、工具面和写入检查通过，且针对精确 `(R,S,C,B)` 给出 `通过`，才允许构造 `T/G` 并交给 `dev-build-change`；handoff 只引用审批记录 ref 与 fingerprint。

## 交接

- `通过` → `dev-build-change`，并把测试清单与审批记录一并交接
- `修改后复审` → `dev-derive-test-cases`；内容修订后升清单版本
- `方案缺口` → `dev-design-solution`；保留清单待办，方案重新通过后继续闭环
- `材料不足` → 补齐指定证据后继续当前评审
- `formal_reviewer_unavailable` → 补齐独立 reviewer 能力后，在同一冻结输入上重新执行正式复核
