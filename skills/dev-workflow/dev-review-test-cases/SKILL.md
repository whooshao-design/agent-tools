# dev-review-test-cases

## 定位

用于在场景产出后、编码开始前独立评审“需求 → 方案 → 场景”的完整性和真实性。

本 skill 不修改场景、不评审测试代码，也不重做方案评审。场景问题交回 `dev-derive-test-cases`；方案缺口交回 `dev-design-solution`；代码落地后由 `dev-review-change` 评审。

## 审批事实与产物目录

正式评审默认写入 `/home/joney/docs/requirements-development/<requirement-name>/test-cases-review/review.md`，使用 `references/review-template.md`。

- 正式文档模式下 `review.md` 是场景审批事实源；对话模式下以包含相同绑定字段的结构化评审结果及消息引用作为审批记录。场景清单自身状态和未绑定输入的口头结论都不能替代审批记录
- 报告必须绑定场景产物路径/版本、需求版本、方案版本及其评审结论、已授权风险和代码基线；任一绑定项变化都会使原结论失效
- 新一轮评审前，先把上一轮报告归档到 `test-cases-review/rounds/review-round-<上一轮次号>.md`
- 只需对话结论时不创建文件，但仍按相同字段声明评审对象

## 输入契约

至少固定：

- 场景清单的路径、版本、状态及上一轮评审记录
- 原始需求的路径/版本和验收标准 ID
- 技术方案的路径/版本及该版本的明确评审结论
- 已明确接受的风险、假设或排除项及授权记录；评审者不得自行接受风险
- 代码基线、本轮范围和排除范围
- 上一轮未关闭 findings 与待办（复审时）

关键材料或绑定关系缺失时结论为 `材料不足`，不得用推测给出通过。

## Workflow

### 1. 锁定评审对象

记录精确输入绑定。已送审场景若发生任何内容修订，必须按 `dev-derive-test-cases` 规则归档旧版、递增版本后再评审；不得继续沿用原结论。

### 2. 独立核对三向追踪

可用子代理时，在新上下文中只传原始需求、方案、场景清单和必要代码证据，不传推导过程或预期结论；不可用时明确标注“同上下文自评”这一限制。不采信推导方的自报结论，逐条核对：

- 每项需求/验收标准是否有方案承接，并有足以验证业务结果的场景
- 每个方案行为是否有需求来源和场景覆盖
- 每个场景是否同时有需求与方案依据，且前置条件、断言和证据要求真实可执行

### 3. 核对风险覆盖

至少检查正常、异常、边界路径，并按变更风险检查并发、权限、安全、兼容、迁移、性能、观测、发布与回滚等相关维度。不适用必须有可核对理由，不能因模板没有枚举就忽略。

### 4. 形成 findings

每条 finding 写明严重度、原因类型、关联需求/方案/场景、证据、影响、建议、关闭条件和状态。

- 原因类型：`场景问题` / `方案缺口` / `材料问题`
- 严重度：`Blocker`（核心目标无法可靠验证）、`High`（重要路径或风险遗漏）、`Medium`（会导致实现或验证歧义）、`Low`（不影响判断力的轻微问题）
- 状态只使用 `Open` / `Resolved`；`Resolved` 必须有满足关闭条件的证据并经复核
- 已授权的风险接受作为输入前提和关闭证据记录，不另设风险接受状态绕过评审，也不得由评审者代替授权方作决定

### 5. 给出唯一结论

- `通过`：绑定信息完整，且 Open Blocker/High/Medium 均为 0；Open Low 必须显式保留后续动作
- `修改后复审`：存在需要修正的场景问题，且没有未关闭方案缺口
- `方案缺口`：存在任何未关闭方案缺口。若同时有场景问题，先回设计阶段，并在报告中原样保留场景 findings 和待办
- `材料不足`：证据不足以完成判断

方案缺口收敛后，必须绑定新方案版本及其通过记录，由 `dev-derive-test-cases` 对受影响范围生成新场景版本，再继续复审并逐条关闭或迁移原 findings；不得丢弃待办或直接进入编码。

## 输出要求

默认按“输入绑定 → 结论 → 三向追踪与风险覆盖证据 → findings → 后续动作”输出。只有针对报告绑定的精确场景版本、方案版本和代码基线给出的 `通过`，才允许交给 `dev-build-change`。

## 交接

- `通过` → `dev-build-change`，并把场景清单与评审报告一并交接
- `修改后复审` → `dev-derive-test-cases`；内容修订后升场景版本
- `方案缺口` → `dev-design-solution`；保留场景待办，方案重新通过后继续闭环
- `材料不足` → 补齐指定证据后继续当前评审
