# dev-auto-loop

## 定位

用于在任务已具备自动推进条件时，自动串联两段子循环并持续迭代，直到达到停止条件：

- **设计闭环**：`dev-design-solution` ⇄ `dev-review-solution`
- **交付闭环**：`dev-build-change` → `dev-verify-change` → `dev-review-change` → `dev-finish-branch`

它是自动编排阶段的主入口：负责组织两段子循环各自的执行顺序与循环策略，以及两段之间的移交规则；不复制各阶段 skill 的详细正文，也不承载技术栈专项细节。

## 默认产物目录

如需把循环状态落盘，默认放到 `/home/joney/docs/requirements-development/<requirement-name>/auto-loop/`，建议文件名使用 `status.md`，轮次前缀区分所属子循环（如 `A-2`、`B-1`）。

- `<requirement-name>` 使用简短、稳定、可读的需求名目录标识
- 用户明确指定路径时，优先使用用户路径
- 只需在对话中逐轮汇报状态时，可不创建文件

## When to Use

适合以下场景：
- 任务目标和边界已基本清晰，适合从方案设计阶段就开始自动推进；若已有方案只需评审，也可以只从设计闭环起步
- 需要把"设计 → 评审 → 修订 → …→ 开发 → 验证 → 复查 → 收口"串成连续流程，而不是手动一步步切换
- 希望在满足明确停止条件前，自动继续下一轮修订、修复或验证
- 任务规模较大，必要时需要调用 `build-codeagent` 协助实现或拆分执行

不适合以下场景：
- 需求边界仍然模糊，自动循环会放大误判，此时先转 `dev-clarify-task`
- 只需要执行单个阶段，不需要跨阶段编排
- 用户要求每一步都人工确认，不希望自动连续推进

## Workflow

### 1. 判断是否适合自动编排

先确认以下前提是否成立：
- 任务目标、范围和完成标准基本清晰（哪怕还没有方案，只要需求边界明确即可从设计闭环起步）
- 两段子循环各有可用的停止条件与轮次上限（未特别说明时直接用默认值，不需要每次都让用户先敲定）
- 若已有方案，具备可执行的代码上下文和操作路径

如果需求边界都不清楚，先退回 `dev-clarify-task`，不直接启动自动循环。

### 2. 建立两段式循环骨架

自动编排默认围绕两段骨架组织，顺序衔接、不互相自动回跳：

**第一段：设计闭环**（只有方案已经评审通过时才可以跳过本段，直接从第二段开始；已有方案但尚未评审或只需评审，仍要进入本段——从 `dev-review-solution` 开始，不必重新走 `dev-design-solution`）
- 进入 `dev-design-solution` 产出或修订方案
- 进入 `dev-review-solution` 评审
- 按评审结论决定：退出进入交付闭环 / 回 `dev-design-solution` 修订 / 停止转人工（判定规则见第 3 步）

**第二段：交付闭环**
- 进入 `dev-build-change`
- 产出可验证结果后进入 `dev-verify-change`
- 验证通过或结论足够后进入 `dev-review-change`
- 达到交付条件时进入 `dev-finish-branch`
- 必要时可根据结果回退到前一阶段继续下一轮，而不是线性只走一遍

两段之间只有一条单向移交路径：设计闭环成功退出（`通过`/`有条件通过`）才能进入交付闭环；设计闭环未成功退出，整个自动编排在第一段就停止，不进入第二段。交付闭环内部若发现问题源于方案设计本身而非实现，按第 7 步处理为停止转人工，**不**自动回跳设计闭环。

### 3. 设计闭环的结论判定与轮次消耗

评审结论只能是 `dev-review-solution` 定义的五种之一，对应到循环动作：

| 评审结论 | 循环动作 | 轮次消耗 |
|---|---|---|
| `通过` | 成功退出，进入交付闭环 | 不消耗 |
| `有条件通过` | 成功退出，进入交付闭环，并在状态摘要显著标注已接受的风险 | 不消耗 |
| `修改后复审` | 回 `dev-design-solution` 定点修订，方案版本号 +1 | 消耗 1 轮 |
| `退回重设计`（第 1 次） | `dev-design-solution` 重新构思候选方案，排除已否决方向 | 消耗 2 轮 |
| `退回重设计`（第 2 次） | 立即停止，转人工或建议回 `dev-clarify-task` | 停止 |
| `材料不足` | 先自行补充证据重新评审，补不出来再转人工 | 不消耗 |

`有条件通过` 只有在其"已接受风险"全部满足循环内 Medium 自动接受条件时才算成功退出；只要有一条不满足，就按 `修改后复审` 处理，回 `dev-design-solution` 继续处理该风险项，不直接放行。循环内对 Blocker/High/Medium/Low 的处置比 `dev-review-solution` 自身标准更保守（循环里没有人临场拍板，"显式接受"这类业务判断不能让 agent 自己做主）；完整判定表、`退回重设计`/`材料不足` 的处理细节见 `references/design-review-loop.md`。

### 4. 设计闭环的止损检测

轮次上限只能兜底"改了很多轮还是没收敛"，还要独立检测两种更早期的失败信号，触发即提前停止，不等轮次耗尽：
- **原地打转**：连续两轮之间方案版本或 findings 集合未变化
- **结论不一致**：同一批未变化内容，前后两轮给出不同严重度判断

### 5. 定义两段各自的停止条件与轮次上限

- 设计闭环默认预算：3 轮修订 + 最多 1 次重新构思；未特别说明时直接使用默认值，仅在任务复杂度明显偏离默认场景时才需要调用方明确覆盖
- 交付闭环沿用现状，轮次上限由调用方按任务定义，不强制默认值
- 两段轮次各自独立计数，不共用一个计数器

### 6. 每轮输出状态摘要

每完成一轮，都要收敛成简明状态：
- 当前所处循环段（A/B）与轮次
- 本轮做了什么、当前结论是什么
- 剩余卡点是什么、下一轮准备处理什么
- 设计闭环阶段额外记录：方案版本、`退回重设计` 累计次数、自动接受的 Medium 清单

### 7. 失败或停止时回退或升级

设计闭环内：
- 修改后复审累计达到轮次上限 → 停止转人工，附最近一次评审的完整 Blocker/High/Medium 清单
- `退回重设计` 第 2 次出现 → 停止，建议回 `dev-clarify-task`
- `材料不足` 补充证据后仍不足 → 停止，列出需要人工提供的具体信息
- 止损检测触发 → 停止，说明触发的是"原地打转"还是"结论不一致"

交付闭环内（现状不变）：
- 实现问题明显 → 回退 `dev-build-change`
- 验证证据不足或失败待定位 → 回退 `dev-verify-change`
- 风险判断未收敛 → 回退 `dev-review-change`
- 发现问题源于方案设计本身而非实现 → 停止转人工，不自动回跳设计闭环
- 若任务过大、上下文过重或需要并行实现，可调用 `build-codeagent`

## 编排原则

- 自动编排只负责串阶段和判定是否继续循环，不替代各阶段自身的专业判断
- 设计闭环和交付闭环各自独立计轮次、独立停止条件，不共用计数器
- 循环内 Blocker/High 无自动接受路径；Medium 自动接受需满足明确条件，且结论上限为"有条件通过"
- 交付闭环不自动回跳设计闭环，发现方案级缺陷即停止转人工
- 每轮都要有明确状态结论，避免静默长循环
- 必须有循环上限，避免无限推进；同时要有止损检测，不能只靠轮次上限兜底
- 仅在需要时调用增强能力，不把所有专项能力塞进主入口

## 输出物

默认输出一份轻量循环摘要，建议包含：
- 当前所处循环段（设计闭环/交付闭环）与轮次：已完成到第几轮
- 阶段轨迹：本轮经过了哪些主阶段
- 本轮结果：通过、回退、继续或终止
- 当前卡点：尚未解决的问题或风险
- 设计闭环阶段：方案版本、`退回重设计` 累计次数、自动接受的 Medium 风险清单及生效前提
- 下一步动作：继续哪一阶段，或交给人工决策
- 最终结论：已完成 / 达到上限停止 / 因失败终止

## 结果要求

一份合格的自动编排结果应满足：
- 能看出当前是如何在两段子循环之间推进的
- 能说明为什么继续、为什么回退、为什么停止
- 每轮都有摘要，最终能沉淀出清晰状态
- 保持轻量，不复制设计、评审、开发、验证、收口阶段的详细规则

## 可选增强

- 如需要较大规模实现、并行处理或额外子代理协作，可调用 `build-codeagent`

## 交接建议

- 设计闭环成功退出（`通过`/`有条件通过`）→ 同一次编排内自动衔接进交付闭环，不需要用户二次触发
- 设计闭环内停止 → 按具体原因回 `dev-design-solution`（继续修订）、`dev-clarify-task`（需求层面问题）或转人工
- 交付闭环内持续受阻 → 回退到对应主入口由人工继续判断
- 整体已达到可交付状态 → 进入 `dev-finish-branch`
