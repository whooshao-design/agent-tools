# 测试场景闭环判定细则

供 `dev-auto-loop` 编排 `dev-derive-test-cases` ⇄ `dev-review-test-cases` 时使用。本文件只规定自动编排的路由、预算和止损，不替代场景推导或评审标准。

## 进入与退出约束

- 进入前必须存在匹配当前 `(R,S,B)` 的方案审批；不匹配时回设计闭环
- 场景清单 `C` 必须标明它对应的 `R/S/B`，不能只引用方案文件名
- 成功评审记录完整审批元组 `(R,S,C,B)`；只有当前产物与该元组精确匹配才能进入交付闭环
- 本段没有 `有条件通过`，也没有自动接受 finding 的路径

## 独立预算

`test_case_revision_count` 默认上限为 2。执行一次场景补充/修订前，先判断计数小于上限，再将计数 `+1`；已达上限则停止为 `budget_exhausted`。设计闭环消耗不计入本计数，因 `方案缺口` 回设计也不重置本计数。

## 结论到动作

| 评审结论 | 自动编排动作 |
|---|---|
| `通过` | 确认没有未关闭的 Blocker/High/Medium，写入 `(R,S,C,B)` 场景审批，进入 `dev-build-change` |
| `修改后复审` | 在场景修订预算内回 `dev-derive-test-cases`，定点补充 finding 指向的场景，生成新的 `C` 后复审 |
| `方案缺口` | 保留已有场景 findings，失效受影响审批，按“回设计闭环”处理；不进入交付 |
| `材料不足` | 按标准化缺口 ID 自动补证一次；同一缺口再次出现时停止为 `blocked_material` |

任何送审后内容变化都要形成新的场景版本和内容摘要。只有版本标签变化、场景内容未变化，不算一次有效修订。

## 回设计闭环

只要存在未关闭的方案缺口，整体结论优先为 `方案缺口`；即使同时存在场景问题，也不能先把场景修好后放行。路由步骤固定为：

1. 保留并标记现有场景 findings，不把它们误记为已解决
2. 在 design revision 预算可用时递增 `design_revision_count`，回 `dev-design-solution` 修订方案；需要根本换方向时仍由后续方案评审给出 `退回重设计`，并独立消费 redesign 预算
3. 使旧方案审批及受影响的场景审批、风险授权失效
4. 方案重新得到匹配 `(R,S,B)` 的审批后，回 `dev-derive-test-cases` 推导所有受影响场景
5. 生成新的 `C` 并重新评审；影响范围无法可靠界定时全量重新推导/评审

设计重新通过后的下一步始终是测试场景闭环，不得从设计阶段直达交付。若设计预算耗尽或需人工风险授权，沿用设计闭环的终止状态。

## 材料补证

为每个材料缺口建立稳定 `evidence_gap_id`，并在 handoff envelope 记录 `auto_attempts`：

- `auto_attempts=0` 时，可从代码仓库和已授权只读来源补证一次，然后更新证据摘要
- 同一缺口再次出现、补证后证据摘要未变化，或材料依赖业务决策/额外权限时，停止为 `blocked_material`
- 所需材料相同但措辞变化，仍视为同一缺口，不得重新获得自动尝试次数

补证不消耗场景修订预算，但不能绕过通用无进展止损。

## 无进展与一致性止损

比较连续评审的进展键：`(R,S,C,B, 证据摘要, finding ID/内容/状态, 评审结论)`。

- 需要继续动作但进展键未变化：停止为 `no_progress`
- 修订后相同 findings 和结论再次出现，且没有新证据改变定位或动作：停止为 `no_progress`
- 相同输入出现不同严重度或互相矛盾的结论：停止为 `inconsistent_review`
- `R/S/B` 变化不是继续使用旧审批的“进展”，而是审批失效事件；先回到最早受影响阶段

## 停止时交付状态

无论成功还是停止，都输出：当前 `(R,S,C,B)`、方案与场景版本摘要、场景修订计数、因 `方案缺口` 回设计的历史、完整 Blocker/High/Medium 及状态、证据缺口及补证次数、结论历史、下一状态和恢复条件。成功时明确下一状态为 `dev-build-change`。
