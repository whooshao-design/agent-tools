# 技术方案结构与可读性契约

本契约由 `dev-design-solution` 和 `dev-review-solution` 共同遵循。目标是让 `solution.md` 按技术问题和机制向人解释方案，让 `traceability.md` 用 profile、横切矩阵和 CHG 追踪保证设计与交付完整；不以堆满章节、图表或逐文件清单代替完整性。通用表达规则见 `writing-principles.md`。

## 1. 核心壳、主 profile 与横切维度

正式技术方案由三类文件组成，职责不重叠：

```text
solution-design/solution.md        给人读的设计叙事
├── 头部一行、相关文档、摘要
├── 背景与目标、方案概览（主图、关键决策、成立理由）
├── 详细设计（只装配一个主 profile）
└── 替代方案、影响、发布验证回滚、风险与未决

solution-design/traceability.md    给评审和交付用的追踪台账
└── 身份、AC 映射、CHG 矩阵、横切覆盖、风险登记、证据清单

solution-review/rounds/round-<N>/  每轮评审目录
└── report.md、审批记录、resolution.md（处置）、diff（新旧版本差异）

主 profile：mechanism-architecture / migration-remediation /
              contract-evolution / data-state-consistency

横切维度：接口、数据、配置、并发、可靠性、兼容、安全、性能、观测、发布
```

- 核心壳只有一份；profile 只定义"详细设计"的叙事和必答问题，不复制公共章节。
- 每份正式方案只选择一个主 profile。多项命中时选风险最高、最影响正确性结论的一项，其他问题作为横切维度写回对应机制。
- 横切维度用于检查覆盖，不直接变成固定并列大章；结果和 N/A 理由记录在 `traceability.md`。
- 简单、路径唯一且没有契约/数据/机制/迁移/并发/安全/发布风险的改动不使用正式方案，转开发执行清单。

## 2. 三层阅读与权威正文

同一方案支持三个递进阅读入口：

| 阅读层 | 必须回答 | 权威载体 |
|---|---|---|
| 决策扫描 | 问题、选择、最大风险、是否有待裁定项 | 摘要 |
| 方案理解 | 为什么这样选、机制怎样工作、影响和上线验证 | 方案概览、详细设计导读、发布验证 |
| 深度评审/实施 | 契约、不变量、失败边界、兼容、追踪和证据 | 详细设计的实现级小节、`traceability.md` |

- 摘要是导航视图：允许压缩正文，但不得引入正文没有的新决策、条件、改动或风险。
- 详细设计按 guide → reference 展开：先建立心智模型，再给足以实施的精确设计，并回到代表性场景论证为何成立。
- "只定义一次"禁止同一事实换词重复，不禁止正确性论证综合引用多处事实形成新结论。
- `traceability.md` 保存映射、登记和证据，不承载读完正文后才知道的关键设计结论。

## 3. Profile、设计叙事与 CHG 追踪

`CHG-*` 是交付单元，回答"改哪个对象、怎么验、怎么发布/回滚"；主 profile 回答"方案为什么成立"。交付颗粒度不等于设计叙事颗粒度。

| 标识/结构 | 职责 | 出现位置 |
|---|---|---|
| 主 profile | 组织核心机制、正确性和边界 | `solution.md` 第 3 章骨架，且只能一个 |
| `DEC-*` | 记录实质技术取舍和理由 | `solution.md` 2.2 与第 4 章，作为锚点不机械分章 |
| `CHG-*` | 标识可实施、验证、发布/回滚的交付行为 | `traceability.md` 的 CHG 矩阵 |
| `AC-*` | 定义可验证成功标准 | `solution.md` 1.2 以自然语言引用；映射在 `traceability.md` |
| `RISK-*` | 标识风险、缓解和待决条件 | `solution.md` 第 7 章叙述；登记在 `traceability.md` |
| `E-*` | 证据 | `traceability.md` 证据清单；正文只引用 |

`solution.md` 正文不出现 CHG 矩阵、AC 矩阵、横切矩阵、指纹、producer refs、finding 处置和修订痕迹；正文中的 ID 首次出现跟在自然语言名称后面。禁止用 CHG、仓库、文件或配置 key 作为正文主标题。

一个 `CHG-*` 表示一个可独立追踪的交付行为：

- 能独立实施、验证或回滚的变化分别建 CHG；必须原子完成才能维持同一不变量的多处修改合并为一个 CHG。
- 动作只取 `新增` / `修改` / `删除` / `保持不变`。
- 一个文件可被多个 CHG 影响，但同一处具体修改只有一个主要归属。
- 每个 CHG 至少绑定一个 `AC-*`、已确认约束、`DEC-*` 或风险处置；没有来源的是孤儿变更。
- `保持不变` 的 CHG 不需要实施步骤，但必须说明保护原因和回归验证。

## 4. 内容唯一归属

| 内容 | 权威位置 |
|---|---|
| 依据的外部文档 | `solution.md` 头部相关文档列表 |
| 当前流程和已有事实 | `solution.md` 1.1 |
| 目标、范围、约束、假设和术语 | `solution.md` 1.2、1.3 |
| 推荐方案、主图、关键决策与成立理由 | `solution.md` 第 2 章 |
| 目标机制、契约、不变量和失败语义 | `solution.md` 第 3 章主 profile |
| 候选取舍与不选的理由 | `solution.md` 第 4 章 / `DEC-*` |
| 上下游影响、兼容和明确不变项 | `solution.md` 第 5 章 |
| 发布门禁、阶段、观测和回滚 | `solution.md` 第 6 章 |
| 残余风险和开放问题 | `solution.md` 第 7 章 |
| 身份、验收映射、CHG 矩阵、横切覆盖、风险登记、证据 | `traceability.md` |
| finding 处置与新旧版本差异 | `solution-review/rounds/round-<N>/` |
| 读者测试答案键与结果 | `solution-design/reader-test/` |
| 工时、负责人、commit 和开发批次 | `dev-build-change` 的 DEV 清单 |
| 详细测试步骤 | `dev-derive-test-cases` 的测试清单 |

需要引用其他位置时使用稳定 ID 或章节名，不换一种措辞重新定义。风险章节不得复制机制的失败设计，CHG 矩阵不得重写正文理由。

## 5. 语义覆盖与交付追踪

设计完整性和交付完整性分别验证：

- **设计完整性**：目标机制、关键契约、不变量、失败和边界足以评审及实施，由主 profile 和横切相关性承担。
- **交付完整性**：所有对象和交付单元有来源、验证与发布/回滚归属，由 `traceability.md` 的 CHG 追踪矩阵承担。

正式方案至少维护以下闭环：

- 每个 `AC-*` 至少映射一处目标设计和一个 `CHG-*`；未覆盖项标为阻塞或非目标。
- 每个 `CHG-*` 都有来源、影响对象、对应设计位置、验证入口和发布/回滚处置。
- 每个相关横切维度有唯一权威位置；`N/A` 有理由，`Unknown` 说明是否阻塞。
- 每个 `RISK-*` 绑定受影响的 `DEC-*` / 设计位置 / `CHG-*` 及缓解或待决条件。
- 目标设计不得引入 CHG 矩阵没有的实际行为变化，CHG 矩阵的每项都能指向解释它的目标设计位置；`traceability.md` 引用的章节号必须在 `solution.md` 中存在。

目标闭环为：

```text
AC → DEC/目标设计正文 → CHG → 验证信号 → 发布/回滚
```

### 5.1 全称断言必须可复现

"唯一 X""全仓 0 命中""完整枚举""除此之外没有 Y"等全称断言必须同时给出：可复跑检索命令、检索范围（含排除项）和命中计数，三者缺一即视为未附命令。

未附命令的全称断言在评审中一律按 `Unknown` 处理，不得作为 finding 的关闭依据，也不得支撑其他结论。命令与范围放 `traceability.md` 证据清单，正文只写结论并引用证据条目。

对"0 命中、无消费方、无影响"等负向断言，生成方还必须提供至少两条相互独立的检索路径；单一路径只能形成待复核项。

## 6. 可读性、篇幅与可视化

- 表达规则以 `writing-principles.md` 为准：第一屏、段落、列表与表格、标识与引用、标题与篇幅。
- 各章节的默认形态见 `dev-design-solution/references/readability-and-writing.md` 第 3 节；图的触发条件、格式与校验见 `visualization-routing.md`，主图默认存在，不画写豁免理由。
- 正文只展开变化、违反直觉、高风险、存在争议、影响正确性或会导致实现分歧的内容。
- 没有实质内容的章节删除，不保留空占位或大量 N/A。
- `solution.md` 正文约 300 行、超过约 450 行只触发结构复核：先去重、移出证据和追踪内容，不机械删除必要设计。
- 不设置统一中文字符数、句长或图表数量硬门禁，不用 prose linter 代替技术评审；`doc_metrics.py` 的输出是提示。

## 7. 结构与可读性验收

进入正式评审前必须通过：

1. 30 秒扫描：摘要能回答问题、选择、最大风险和是否有待裁定项；
2. 5 分钟理解：不读 `traceability.md` 能解释机制、主要影响以及怎样上线和证明；
3. Profile 测试：主 profile 唯一且与主要正确性问题一致，没有拼接多套骨架；
4. 标题测试：只看第 3 章标题能恢复设计推理，不是文件或 CHG 清单；
5. 双读者测试：新读者能建立心智模型，实施者能定位精确契约和边界；
6. 唯一归属测试：摘要、正文、追踪文件和图没有多个权威定义；
7. 完整性测试：相关维度有权威位置，`AC → 设计 → CHG → 验证/发布` 闭环，追踪引用的章节存在；
8. 范围隔离测试：当前方案、开放问题、未来设想、证据、修订痕迹和 DEV 执行内容没有混写；
9. 读者测试：`reader-test-protocol.md` 的 agent 读者七问全部通过。

读者测试任一问不通过，或结构缺陷导致读者无法定位机制、取舍、影响或回滚，是 Medium 级结构/可读性 finding。纯标题偏好、个人文风或不影响理解的措辞不形成 finding。
