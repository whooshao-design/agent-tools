# 技术方案结构与可读性契约

本契约供 `dev-design-solution` 生成技术方案、`dev-review-solution` 评审方案时共同使用。目标是让读者先看懂结论和本次变更，再按稳定 ID 定位依据、实现、验证与风险；不以堆满章节代替完整性。

## 1. 导航视图与权威正文

- “一页结论”和“变更地图”是导航视图：允许压缩正文，但不得引入正文没有的新决策、改动或风险。
- 详细设计是变更事实的权威正文；同一事实只**定义**一次，其他位置使用 `DEC-*`、`CHG-*`、`AC-*` 或 `RISK-*` 引用。
- “只定义一次”禁止的是同一事实换个措辞重复定义，**不禁止把多处事实综合成一个论证**。正确性论证、时序推演、失败路径推演天然要引用多处已定义的事实，它们是新增结论而非重复定义，必须允许存在。
- 附录保存长证据和治理身份，不承载阅读正文后才知道的关键结论。

## 2. 分层与正交划分

每个父章节只能选择一个划分维度；同级章节必须处于相同抽象层级，并共同覆盖父章节声明的范围：

| 层级 | 划分维度 | 禁止混排示例 |
|---|---|---|
| 一级正文 | 读者问题：为什么、做什么、怎么做、如何证明、如何上线 | 把具体类或字段与“发布方案”并列 |
| 详细设计二级 | 机制轴或变更轴，二选一（见下） | “模块改动”与“接口/数据/并发”并列 |
| 单个单元内部 | 生命周期：现状、调整、目标行为、不变项、失败路径、验证 | 把另一个独立行为塞进异常章节 |
| 横切维度 | 接口、数据、配置、并发、兼容、安全、观测等相关性矩阵 | 在多个单元中复制同一公共决策 |

横跨多个变更的公共技术决策建立唯一 `DEC-*`，各处只引用它。无法正交拆分的横切关注点用矩阵表达覆盖关系，不再创建与模块/变更混排的同级章节。

### 2.1 详细设计的两种组织轴

`CHG-*` 是**交付单元**，回答“改哪个对象、怎么验、怎么回滚”；它适合做追踪，不总是适合做叙事骨架。当一个机制横跨多个 `CHG-*` 时，按变更轴分节会把机制切碎，评审最需要判断的整体正确性反而无处陈述。因此详细设计按需二选一：

| 轴 | 选用条件 | 二级章节形态 |
|---|---|---|
| **机制轴** | 核心是一套新机制或状态机；正确性依赖多处改动协同；并发、时序、一致性是评审重点 | 按机制的组成部分与推理顺序分节，末尾必须有一节论证整体正确性 |
| **变更轴** | 各变更彼此独立、可分别实施与回滚；主要风险在交付边界而非机制本身 | 每节一个 `CHG-*`，按 §3 的六问展开 |

判据是：**把详细设计的二级标题单独列出来，读者能否看出这次要做的是一件什么事**。看不出来就说明轴选错了。

选机制轴时，`CHG-*` 不消失，只是移入追踪矩阵（正文内或附录皆可），并在机制正文中以“正文位置 → CHG”的方式建立双向可达。两种轴都必须满足 §5 的追踪闭环。

## 3. 变更单元

一个 `CHG-*` 表示一个可独立说明和验证的交付行为单元：动作是新增、修改或删除时，它代表实际变化；动作是保持不变时，它代表本次必须显式保护并回归验证的不变量边界。

- 能独立实施、验证或回滚的两个变化必须拆开。
- 必须原子完成才能维持同一不变量的多处代码修改合并为一个 CHG。
- 一个文件可被多个 CHG 影响，但同一处具体修改只能有一个主要归属。
- 每个 CHG 必须绑定至少一个 `AC-*`、已确认约束或风险处置；没有来源的是孤儿变更。

动作只取：`新增` / `修改` / `删除` / `保持不变`；纯保持不变项无需实现步骤，但必须说明保护原因与回归验证。

无论用哪种组织轴，详细设计整体必须回答完这六问；**变更轴下由每个 `CHG-*` 各自回答，机制轴下允许跨节回答，但不得遗漏**：

1. 当前行为和证据是什么；
2. 本次具体调整什么；
3. 调整后的行为与不变量是什么；
4. 哪些相邻行为明确保持不变；
5. 失败、降级、并发或兼容边界是什么；
6. 如何验证该变更成立。

第 4 问在机制轴下容易被漏掉——机制叙事天然只讲“改了什么”。必须单独设一节列出明确保持不变的相邻行为，否则评审无法判断改动边界。

## 4. 内容唯一归属

| 内容 | 权威位置 |
|---|---|
| 当前业务流程和已有行为 | 背景与现状 |
| 目标、非目标和约束 | 目标与非目标 |
| 跨变更技术决策与候选取舍 | `DEC-*` / 方案总览 |
| 新增、修改、删除和不变项 | 详细设计中对应的机制小节或 `CHG-*` 小节 |
| 整体正确性论证（并发、时序、一致性） | 详细设计末节，不拆散到各变更 |
| 预期会被质疑的问题 | 评审 FAQ（可选，问题反复出现时建立） |
| 性能目标、容量计算 | 性能与容量 |
| 验收映射和验证信号 | 验证方案 |
| 发布、灰度、观测和回滚动作 | 发布方案 |
| 原始 SQL、日志、查询结果、完整调用链和治理身份 | 附录 |

背景章节只描述现状，不提前夹带目标方案；详细设计不重新复述完整现状。需要引用其他位置时使用稳定 ID 或链接，不能换一种措辞重复定义。

## 5. 穷尽性与追踪

正式方案至少维护以下闭环：

- 每个 `AC-*` 至少映射一个 `CHG-*`，未覆盖项必须标为阻塞或非目标。
- 每个 `CHG-*` 都有来源、影响对象、验证方式和必要的发布/回滚处置。
- 接口、数据、配置、异常、并发、兼容、安全、观测等维度按相关性检查；`N/A` 必须写原因。
- 每个 `RISK-*` 绑定受影响的 `DEC-*` / `CHG-*` 及缓解或待决条件。
- 变更地图/追踪矩阵与详细设计**实际覆盖的行为**必须完全一致，不得有缺失、重复或只存在于摘要的变更。变更轴下体现为「地图的 CHG 集合 == 详细设计的章节集合」；机制轴下体现为「矩阵的每个 CHG 都能指向详细设计中解释它的位置，且详细设计不引入矩阵没有的行为变更」。

## 6. 表达与篇幅预算

- 一页结论中的“问题”和“核心方案”各控制在 3–5 句话；主要改动优先用表格表达。
- 一段只表达一个判断，先结论后依据；避免同义反复、长前置铺垫和无关历史。
- 标题最多四级；没有实质内容的章节直接删除，不保留空占位或泛化表述。
- 正文目标不超过约 300 行。超过时先去重并把长证据移入附录；超过约 450 行时将 SQL、日志、完整调用链或数据核验拆成独立证据文件。
- 主文只保留理解决策必需的短代码/协议片段；图只用于跨多个组件、状态或并发时序，且不能与相邻文字逐句重复。
- 性能与容量、备选方案、ADR 仅在实际相关时保留；不得为模板完整制造陪跑方案、虚构数据或负责人。

## 7. 结构验收

方案进入正式评审前必须能回答：

1. 读者能否从一页结论知道为什么做、怎么做、主要改动和最大风险；
2. 现有内容与新增/修改/删除/不变内容是否明确分离；
3. 同级章节是否使用同一划分维度，是否存在层级错位；
4. 是否存在重复事实源、互相矛盾的摘要与正文、孤儿变更或覆盖缺口；
5. 是否能从 `AC-*` 追踪到 `CHG-*`、验证信号及发布处置；
6. **只看详细设计的二级标题，能否看出这次要做的是一件什么事**；
7. **本方案最可能被质疑的地方，正文是否已正面回答**——涉及并发、状态机或数据一致性时，是否有一节完整论证整体正确性，而不是分散在各变更里。

第 6、7 条针对的是可读性缺陷：追踪闭环完整但机制被切碎的方案能通过 1–5 条，却无法被有效评审。
