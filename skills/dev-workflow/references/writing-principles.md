# 研发产物写作原则

`dev-workflow` 各阶段产物（需求摘要、技术方案、测试清单、开发清单、评审报告）的叙事正文共同遵循的表达规则。阶段模板只补充本阶段专属的结构，不重复这里的规则；追踪矩阵、清单表、findings 表和评审报告的评审对象绑定表按阶段模板的列与字段，模板与本文冲突时以模板为准。目标读者是第一次打开文件、没有会话上下文的人。

## 1. 第一屏

- 头部只有一行：状态、版本、日期，以及本阶段最多两个专属字段。指纹、producer refs、审批引用不放叙事正文，它们属于 handoff、追踪文件或评审报告的绑定表。
- 头部之下是相关文档列表：不超过 8 条，每条写类型、名称、路径或 URL。路径直接写出而不是藏在链接文字里，上传飞书后相对链接会失效，可见的路径仍然能用。
- 然后是摘要：一段话，不超过 150 字，说清问题、结论、最大代价或风险、当前需要谁决定什么。

## 2. 段落

- 一段只推进一个判断，首句就是这个判断；先写正常路径，再写例外。
- 用"参与者 + 动作 + 对象 + 条件或结果"的具体句子；使用代码与需求中的真实名称，一个概念只有一个名字，新术语首次出现时定义。
- 边界写成正面的行为描述，例如"缓存不可用时直接查库并记录告警"；防御式的"不得 / 严禁 / 不夸大其保证"留给确实需要禁止的动作。
- 正文不写给评审者看的辩护，不写修订痕迹，例如"关闭 F-03""v9 订正"；处置记录放评审目录，新证据放证据清单。
- 删掉没有信息增量的套话："综合考虑""通过上述方案""需要注意的是""值得一提"。

## 3. 列表与表格

- 列表只用于并列、顺序或对比项；不嵌套；不用"**标签**：内容"的连排，那是表格或段落该做的事。
- 表格只承载映射与对比：单元格不超过两句；叙事正文里的表列数不超过 6，追踪矩阵、清单表和 findings 表按阶段模板。理由、机制、失败语义、发布条件写成段落或小节。
- 加粗只用于警示读者必须注意的一处，不用于给每段开头贴标签。

## 4. 标识与引用

- 稳定 ID（AC、DEC、CHG、RISK、TC、E）首次出现时跟在自然语言名称后面，例如"本地执行方案（DEC-001）"，此后用名称。正文不出现以 ID 为主体的矩阵，矩阵放追踪文件。
- 证据用 E-* 引用，命令、检索范围、命中计数、长输出放证据清单，正文只写结论。
- 引用其他位置时用稳定 ID 或章节名，不换一种措辞重新定义。

## 5. 标题与篇幅

- 标题写技术机制、状态变化或结论，不写"其他""处理逻辑""方案项一""模块改动"；同级标题保持同一抽象层级；最多四级标题。
- 篇幅以读者时间为准。只展开本次变化、违反直觉、高风险、有争议、缺细节会导致不同实现的内容；系统历史、完整对象清单、长 SQL、日志、调用链、逐文件动作压缩、引用或移出正文。

## 6. 交付前自检

- 第一屏能回答：问题是什么、结论是什么、最大风险是什么、现在需要谁决定什么？
- 每段的首句删掉后，读者会失去一个判断吗？不会就删掉这一段。
- 文中有没有"**X**："连排、嵌套列表、超过两句的单元格、没有名称的裸 ID？
- 有没有防御句、修订痕迹、面向评审者的辩护？
