# 研发产物写作原则

`dev-workflow` 各阶段产物（需求摘要、技术方案、测试清单、开发清单、评审报告、调研报告、commit 与 MR 说明）的叙事正文共同遵循的表达规则；第 2.1 节同时适用于终端汇报。阶段模板只补充本阶段专属的结构，不重复这里的规则；追踪矩阵、清单表、findings 表和评审报告的评审对象绑定表按阶段模板的列与字段，模板与本文冲突时以模板为准。目标读者是第一次打开文件、没有会话上下文的人。

## 1. 第一屏

- 头部只有一行：状态、版本、日期，以及本阶段最多两个专属字段。指纹、producer refs、审批引用不放叙事正文，它们属于 handoff、追踪文件或评审报告的绑定表。
- 头部之下是相关文档列表：不超过 8 条，每条写类型、名称、路径或 URL。路径直接写出而不是藏在链接文字里，上传飞书后相对链接会失效，可见的路径仍然能用。
- 然后是摘要：一段话，不超过 150 字，说清问题、结论、最大代价或风险、当前需要谁决定什么。

## 2. 段落

- 一段只推进一个判断，首句就是这个判断；先写正常路径，再写例外。
- 用"参与者 + 动作 + 对象 + 条件或结果"的具体句子；一个概念只有一个名字，新术语首次出现时定义。
- 段落只写理由、取舍和失败语义；能用图、表或示例表达的结构性内容不写成段落（见第 3 节）。单段超过约 200 字时先检查是否混入了流程、对比或清单。
- 边界写成正面的行为描述，例如"缓存不可用时直接查库并记录告警"；防御式的"不得 / 严禁 / 不夸大其保证"留给确实需要禁止的动作。
- 正文不写给评审者看的辩护，不写修订痕迹，例如"关闭 F-03""v9 订正"；处置记录放评审目录，新证据放证据清单。
- 删掉没有信息增量的套话："综合考虑""通过上述方案""需要注意的是""值得一提"。

### 2.1 名称与准确

全局规则 Naming & Precision 的展开，每条都能逐项检查：

| 规则 | 检查方法 | 反例 → 正例 |
|---|---|---|
| 用真实名称：代码名、协议原词、数据结构原词（Map、key、value、entry、list） | 每个名词能指到一个代码对象、外部术语或已定义的业务概念 | "取候选 field"（实际返回整个 Map）→ "调用 `getSnapshot()` 取得 `BypassCacheSnapshot` 对象，遍历其中 `nodeModeCaches` 的 key" |
| 只在没有现成名称且后文引用两次以上时造新词，首次出现处用类型、位置、内容定义它 | 新词首次出现的句子里有定义 | "整表读取" → "`HGETALL`" |
| 一个概念一个名字，一个名字一个概念 | 全文搜索该词，每处指同一个东西 | "快照"同时指 Redis 转储和进程内对象 → 进程内对象写 `BypassCacheSnapshot`，Redis 转储写"Redis 导出文件" |
| 动作写出谁、对什么、做什么、得到什么；数据结构写到整个 Map、key、value 还是 entry | 句子里有动作主体、对象和结果 | "来源变化" → "field 集合由 `HKEYS` 返回值改为 `nodeModeCaches.keySet()`" |
| "相同""全部""没有""唯一"只在逐项核对全集后使用，否则写实际检查的范围 | 能给出逐项核对的表或检索命令 | "乐包模式结构相同" → 逐个方法列步骤，写明乐包模式不排序、不选节点 |
| 数字、单位、条件、否定、时间范围与来源一致；不为篇幅删掉 | 与来源逐项对照 | "失败后重试" → "失败后一个有效期（默认 10 秒）内不再加载" |
| 示例本身符合它所说明的规则 | 写下示例前按本表检查一遍 | 规则禁止自造名词，示例却写"改成取快照" |

## 3. 按内容选表达形式

先判断内容属于哪一类，再选形式；同一事实只用一种主形式表达：

| 内容 | 首选形式 | 不要用 |
|---|---|---|
| 流程、调用顺序、分支、状态转换 | 图（时序图、流程图、状态图），触发条件见各阶段的图规则 | 编号段落叙述多参与者交互 |
| 精确映射、对比、决策清单、阶段门禁、风险清单 | 表格 | 段落里逐项罗列 |
| 数据、脚本、报文、配置在变化前后的样子 | 具体示例：前后对照的代码块或对照表 | 只用文字描述"把 A 改成 B"，或画成图 |
| 理由、取舍、失败语义、为什么成立 | 短段落 | 塞进表格单元格 |

正文提到代码对象（类、方法、属性、配置 key）时直接写代码名并用代码格式；本项目已有公认中文名的业务概念（乐包、节点、主库）用中文名。不为代码对象另起中文概括名：读者要能把每个名字直接对应到代码。术语对照表只收录本项目业务概念与代码名的对应，以及需要解释的外部术语。

外部技术的通用术语（如 Redis 的 Hash、field、key、`HGETALL`，Java 的 volatile、CAS）没有公认的准确中文时直接用英文原词，不自行翻译。用中文词前先确认它不与项目或领域里已有的术语重名，例如 Hawk 里“字段”指特征字段，就不能拿来称呼 Redis Hash 的 field；拿不准时用英文。


- 列表只用于并列、顺序或对比项；不嵌套；不用"**标签**：内容"的连排，那是表格或段落该做的事。
- 表格单元格一般不超过两句，写不下对象、条件和结果时允许更长，或拆成多行；叙事正文里的表列数不超过 6，追踪矩阵、清单表和 findings 表按阶段模板。单元格里放结论和条件，推理过程写成表格后的段落。
- 加粗只用于警示读者必须注意的一处，不用于给每段开头贴标签。

## 4. 标识与引用

- 稳定 ID（AC、DEC、CHG、RISK、TC、E）首次出现时跟在自然语言名称后面，例如"本地执行方案（DEC-001）"，此后用名称。正文不出现以 ID 为主体的矩阵，矩阵放追踪文件。
- 证据用 E-* 引用，命令、检索范围、命中计数、长输出放证据清单，正文只写结论。
- 引用其他位置时用稳定 ID 或章节名，不换一种措辞重新定义。

## 5. 标题与篇幅

- 标题写技术机制、状态变化或结论，不写"其他""处理逻辑""方案项一""模块改动"；同级标题保持同一抽象层级；最多四级标题。
- 篇幅以读者时间为准。只展开本次变化、违反直觉、高风险、有争议、缺细节会导致不同实现的内容；系统历史、完整对象清单、长 SQL、日志、调用链、逐文件动作压缩、引用或移出正文。

## 6. 交付前自检

- 第一屏能回答：问题是什么、结论是什么、最大风险是什么、现在需要谁决定什么？
- 每段的首句删掉后，读者会失去一个判断吗？不会就删掉这一段。
- 文中有没有"**X**："连排、嵌套列表、超过两句的单元格、没有名称的裸 ID？
- 有没有本该是图、表或示例却写成了段落的内容？有没有自创的译名与项目已有术语撞名、或丢了原意？
- 按 2.1 节逐条检查：每个名字能对应到一个真实对象吗？有没有一个名字指两样东西？每个动作有主体、对象、结果吗？每个"相同/全部/没有"有逐项核对吗？数字和条件与来源一致吗？示例符合规则吗？
- 有没有防御句、修订痕迹、面向评审者的辩护？
