# 技术方案模板体系优化方案

> 状态：Implemented<br>
> 方案版本：v1<br>
> 设计对象：`dev-design-solution`、`dev-review-solution` 及技术方案模板体系<br>
> 基础模板：`legacy-tech-spec-solution-design-template.md`<br>
> 单一事实源：`/home/joney/projects/ai/agent-tools`

## 0. 一页结论

### 0.1 要解决的问题

当前 `dev-design-solution` 虽然允许按“机制轴”或“变更轴”组织详细设计，但正式模板仍把两套骨架放在同一文件中，由模型自由判断；Codex 入口提示又要求“按 DEC/CHG 组织权威正文”，与机制轴规则冲突。对于跨仓整改、配置迁移等“多个交付单元复用少量技术机制”的需求，模型容易因为各项可以独立提交和回滚而误选变更轴，最终把技术方案写成逐文件开发清单。

`tech-spec-solution-design-template.md` 的优点是把架构、流程、接口、数据、异常和观测放在正文，但它过度假设“挂载、触发、入口白名单”场景，并固定列出 Redis、MySQL、本地缓存和三个方案项，不适合作为通用模板直接使用。

### 0.2 核心方案

采用“**统一核心模板 + 四类场景 profile + 一套横切维度检查表**”的模板体系。所有正式技术方案共享结论、范围、决策、影响、发布、验证、风险和追踪结构；只有“目标技术设计”章节按主要正确性问题选择一个 profile。接口、数据、并发、安全、性能和观测不再作为固定并列大章，而是在相关机制内展开，并通过横切矩阵检查覆盖。

`CHG-*` 默认只承担交付追踪，不作为正文叙事骨架。只有少量、真正独立、没有共享机制与顺序约束的变更，才允许使用紧凑的逐变更写法；路径已经明确且不存在实质技术取舍的简单改动，不生成正式技术方案，直接转 `dev-build-change`。

信息组织采用“**三层阅读入口 + guide/reference 双层设计 + 风险驱动展开**”：一页结论服务快速决策扫描，方案总览和机制导读服务方案理解，实现级契约、边界与证据服务深度评审。完整性由 profile、横切维度和追踪矩阵保证，不靠把所有检查项扩写为正文；篇幅只作为结构复核信号，不作为可读性结论。

### 0.3 预期结果

- 技术方案正文优先回答“为什么这样设计、运行时如何成立、失败时怎样表现”。
- 批量整改和跨仓迁移不再退化成逐文件任务清单。
- 不同场景复用同一治理、评审和追踪结构，避免多份完整模板漂移。
- 读者可以按“决策扫描、方案理解、深度评审”逐层阅读，不必从实现明细反推方案主线。
- `SKILL.md`、入口提示、模板、结构契约、reviewer 和测试保持一致。

### 0.4 最大风险与阻塞项

- 最大风险：profile 路由仍由模型执行，如果只有描述性规则而没有反例和场景验收，仍可能误选。
- 当前阻塞项：无；可以先完成模板体系改造，再用硬编码整改方案做试点。

## 1. 现状与根因

### 1.1 当前生成链路

当前正式方案固定加载一个 `solution-template.md`，模板内部同时提供机制轴和变更轴，由模型删除不采用的一套。选择依据主要是：

- 新机制、状态机、多处协同、时序或一致性重要时选机制轴；
- 各变更可独立实施和回滚、风险主要在交付边界时选变更轴。

该判据没有覆盖“批量整改/迁移”这一常见形态：代码改动可以逐仓提交，但设计正确性依赖统一分类规则、目标配置机制、迁移顺序和退出门禁。

### 1.2 已确认缺陷

| ID | 缺陷 | 影响 |
|---|---|---|
| GAP-001 | `agents/openai.yaml` 仍要求“按 DEC/CHG 组织权威正文” | 入口提示把模型推向逐 CHG 叙事 |
| GAP-002 | 一个模板内并列两套完整骨架 | 选择依赖模型临场判断，容易保留错误骨架 |
| GAP-003 | 路由只区分“新机制”和“独立变更” | 批量整改、跨仓迁移、契约演进、数据状态变更缺少明确入口 |
| GAP-004 | `CHG-*` 同时承担追踪与叙事职责 | 交付颗粒度反向控制方案可读性 |
| GAP-005 | 缺少“是否需要正式技术方案”的前置门禁 | 简单改动也可能被套成重型方案 |
| GAP-006 | 当前契约测试保留旧断言，且不检查入口提示一致性 | 模板重构不完整仍可能合入 |
| GAP-007 | reviewer 以逐 CHG 覆盖为主，但未明确区分“覆盖追踪”与“正文叙事” | 生成方容易为了评审覆盖把 CHG 全部搬进正文 |
| GAP-008 | 详细设计没有稳定区分“先建立理解”和“再提供实现精度” | 读者在形成心智模型前被迫理解组件、字段和异常分支 |
| GAP-009 | 篇幅预算和“3–5 句话”主要约束形式，缺少分层阅读和信息密度验收 | 文档可能形式上短，但仍空泛、重复或遗漏关键边界 |

### 1.3 基础模板可复用与不可复用部分

保留以下思想：

- 总体架构、核心流程和关键设计点是正文中心；
- 候选方案与推荐方案必须给出取舍；
- 接口失败语义、数据一致性、异常、日志、指标和告警按相关性设计；
- 实施顺序、灰度和回滚需要明确。

不直接保留以下固定结构：

- “挂载位置、触发时机、入口白名单”作为所有方案必填项；
- 固定三个“方案项”；
- 固定 Redis、MySQL、本地缓存章节；
- 把接口、数据、异常、监控作为与机制并列的重复事实源；
- 把灰度与回滚归入异常处理章节。

## 2. 目标、非目标与验收标准

### 2.1 目标

1. 建立适用于多数后端技术方案的统一核心结构。
2. 为不同主要正确性问题提供可组合但不重复的详细设计 profile。
3. 明确正式方案、轻量方案和开发清单之间的路由边界。
4. 保留 `R/S/B`、`AC/DEC/CHG/RISK` 治理与独立评审能力。
5. 通过静态契约测试和典型场景验收防止再次清单化。

### 2.2 非目标

- 不为 Java、MySQL、Redis、MQ、Hippo 等具体技术各建一份完整模板。
- 不在技术方案模板中生成详细测试用例；详细用例继续由 `dev-derive-test-cases` 负责。
- 不在技术方案模板中生成 `DEV-*` 工时、负责人、commit 拆分等开发执行内容。
- 不修改既有不可变审批记录，也不让新模板追溯性改变历史方案身份。
- 本方案阶段不直接重写硬编码整改 `solution.md`。

### 2.3 验收标准

| AC | 可验证结果 |
|---|---|
| AC-TPL-001 | 所有正式方案只使用一个统一核心壳，详细设计只加载一个主 profile |
| AC-TPL-002 | 至少支持机制/架构、迁移/整改、契约演进、数据/状态四类场景 |
| AC-TPL-003 | 简单、路径明确且无实质取舍的改动能够路由到 `dev-build-change`，不强制生成正式方案 |
| AC-TPL-004 | `CHG-*` 默认位于追踪矩阵或附录，不作为批量方案的正文标题 |
| AC-TPL-005 | 核心模板能够追踪 `AC → 设计正文 → CHG → 验证/发布`，且不产生重复事实源 |
| AC-TPL-006 | `SKILL.md`、`openai.yaml`、模板、结构契约和 reviewer 对 profile 与 CHG 的表述一致 |
| AC-TPL-007 | 硬编码整改场景稳定选择“迁移/整改型”，正文按技术机制展开，59 处位置只进入追踪附录 |
| AC-TPL-008 | 现有及新增 workflow 契约测试全部通过，旧的失效断言被更新而非绕过 |
| AC-TPL-009 | 模板不固定要求 Redis、MySQL、缓存、挂载、触发、并发等无关章节 |
| AC-TPL-010 | 正文仍满足结论前置、内容唯一归属、篇幅预算和独立评审要求 |
| AC-TPL-011 | 一页结论、机制导读和实现级参考形成三个递进阅读入口；30 秒、5 分钟和双读者测试可由 reviewer 独立执行 |
| AC-TPL-012 | 完整性通过 profile、横切相关性和追踪矩阵证明，不要求把 N/A、逐对象明细或通用检查项扩写为正文 |

## 3. 关键设计决策

| DEC | 决策 | 核心依据 | 不采用路径 |
|---|---|---|---|
| DEC-TPL-001 | 采用“核心壳 + profile + 横切维度” | 公共治理稳定，详细设计按场景变化；组合成本低 | 单一巨型模板；按技术组件复制多份完整模板 |
| DEC-TPL-002 | 一个方案只选择一个主 profile | 保持单一叙事轴，避免拼接多份模板造成重复 | 多 profile 全量拼接 |
| DEC-TPL-003 | `CHG-*` 默认只做交付追踪 | 交付颗粒度不等于设计叙事颗粒度 | 默认每节一个 CHG |
| DEC-TPL-004 | 增加“无需正式方案”前置路由 | 路径明确的简单改动应直接进入开发清单 | 所有需求都生成完整技术方案 |
| DEC-TPL-005 | 横切维度使用相关性矩阵，内容写回对应机制 | 防止接口、数据、异常、观测成为重复事实源 | 固定并列“接口章/数据章/异常章/监控章” |
| DEC-TPL-006 | 场景选择以“本方案最需要证明什么”为准 | 比模块类型、文件数或是否可单独回滚更接近设计本质 | 仅按 CHG 是否独立判断 |
| DEC-TPL-007 | `agent-tools` 内模板为单一事实源 | 双端 skill 已通过符号链接共享仓库 | 运行时同时维护 `/home/joney/docs/template` 的完整副本 |
| DEC-TPL-008 | 可视化按评审问题路由；Mermaid 稳定子集为默认、可编辑 draw.io 为兜底 | 图应提升关系理解且图源必须可维护 | 固定图表清单；统一只用 Mermaid；统一只用 draw.io |
| DEC-TPL-009 | 采用三层阅读、guide/reference 双层设计和风险驱动展开；语义覆盖与正文叙事分离 | 简洁依赖信息分层和唯一归属，完整依赖相关性与追踪，不是统一字数或章节数量 | 另建简版/详版完整模板；固定中文字符数/句长；用更多必填章节防漏 |

## 4. 目标模板体系

### 4.1 组成关系

```text
正式技术方案
├── 统一核心模板（必选）
│   ├── 一页结论、现状、目标与范围
│   ├── 候选方案与 DEC
│   ├── 影响、发布、验证、风险
│   └── 治理身份与追踪附录
├── 主 profile（四选一）
│   ├── mechanism-architecture
│   ├── migration-remediation
│   ├── contract-evolution
│   └── data-state-consistency
└── 横切维度（按相关性选用）
    ├── 接口、数据、配置、并发/幂等
    ├── 外部依赖与可靠性、安全/权限
    └── 性能/容量、兼容性、可观测性
```

profile 只替换核心模板的“目标技术设计”章节，不复制一页结论、发布、验证、风险和治理附录。

### 4.2 统一核心模板

```text
0. 一页结论
   0.1 问题与影响
   0.2 推荐方案
   0.3 主要机制变化
   0.4 最大代价/风险与阻塞项

1. 背景与现状
   1.1 当前流程/架构
   1.2 问题与证据
   1.3 现有能力与限制

2. 目标、范围与约束
   2.1 AC 成功标准
   2.2 In Scope / Out of Scope
   2.3 已确认约束、假设与待确认输入

3. 方案选择
   3.1 设计原则与系统边界
   3.2 候选方案与权衡
   3.3 DEC 决策表
   3.4 推荐方案和按需方案视图

4. 目标技术设计
   <按主 profile 展开，不出现固定 CHG 标题>

5. 影响范围与兼容性
   5.1 影响对象和上下游
   5.2 明确保持不变的行为
   5.3 横切维度相关性矩阵

6. 发布、观测与回滚
   6.1 发布前门禁
   6.2 发布/迁移顺序
   6.3 观测信号和通过条件
   6.4 回滚触发条件与步骤

7. 方案级验证
   <AC → 设计位置 → CHG → 验证方式/预期结果/失败信号>

8. 风险与待确认事项
   <RISK → DEC/设计位置/CHG → 缓解/决策条件/状态>

附录 A：治理身份与版本历史
附录 B：证据
附录 C：CHG 变更清单与追踪矩阵
```

### 4.3 Profile A：机制/架构型

适用：新增运行时机制、跨组件流程、任务编排、插件/拦截、异步处理、状态机以外的协同机制。

正文必须回答：

1. 机制边界和参与者职责；
2. 入口、生命周期和关键时序；
3. 数据/控制流和状态传递；
4. 正常路径、失败路径与降级；
5. 并发、幂等或重复触发边界（相关时）；
6. 机制为什么不会漏处理、重复处理或提前处理；
7. 明确保持不变的相邻行为。

“挂载位置、触发时机、入口白名单”只作为该 profile 的可选维度，不进入核心模板。

### 4.4 Profile B：迁移/整改型

适用：配置迁移、凭证整改、数据搬迁、批量治理、依赖升级、跨仓统一改造、旧机制下线。

正文必须回答：

1. 对象盘点、分类规则及证据可信度；
2. 各类别的源状态、目标状态和统一处置机制；
3. 目标运行时机制如何读取、更新和失败；
4. 迁移阶段、前置门禁、切换条件和完成定义；
5. 迁移期间的新旧兼容、残留和例外；
6. 批量影响面、爆炸半径及分批策略；
7. 回滚路径、不可逆动作和安全残余风险；
8. 个别对象的文件级动作放入附录 C，不逐项占正文。

### 4.5 Profile C：契约演进型

适用：HTTP/Dubbo/API、消息事件、SDK、配置格式或跨系统协议变更。

正文必须回答：

1. 当前契约与目标契约的语义差异；
2. 生产方、消费方和版本边界；
3. 请求、响应、事件、错误码与失败语义；
4. 向前/向后兼容策略和兼容矩阵；
5. 双版本窗口、调用方迁移和废弃条件；
6. 超时、重试、幂等、安全和限流（相关时）；
7. 发布顺序与契约回滚限制。

### 4.6 Profile D：数据/状态型

适用：表结构、状态模型、事务边界、缓存一致性、索引、历史数据回填和状态机改造。

正文必须回答：

1. 当前与目标数据/状态模型；
2. 核心不变量和状态转换；
3. 事务、一致性、并发与幂等；
4. 读写路径及失败恢复；
5. 历史数据迁移、回填、校验和对账；
6. 索引、容量和性能依据（相关时）；
7. 灰度、双写/双读、切换和不可逆边界。

### 4.7 横切维度相关性矩阵

每个方案必须完成相关性判断，但只有相关项进入正文。`N/A` 只在矩阵中说明原因，不创建空章节。

| 维度 | 判断问题 | 正文归属 |
|---|---|---|
| 接口/契约 | 是否改变调用方可见行为或错误语义 | 对应机制或契约小节 |
| 数据/存储 | 是否改变模型、读写、事务或一致性 | 对应机制或数据状态小节 |
| 配置/开关 | 是否新增配置、动态更新、默认值或权限边界 | 对应机制和发布门禁 |
| 并发/幂等 | 是否存在重复、乱序、竞态或重入 | 对应机制正确性论证 |
| 外部依赖 | 是否涉及超时、重试、熔断、降级 | 对应失败路径 |
| 兼容性 | 是否存在跨版本、跨环境或历史数据兼容 | 影响范围与迁移小节 |
| 安全/权限 | 是否涉及凭证、鉴权、敏感数据或审计 | 对应机制和风险小节 |
| 性能/容量 | 是否改变请求量、延迟、存储或资源上限 | 对应机制；必要时增加专项小节 |
| 可观测性 | 如何发现方案未生效、降级或错误 | 发布观测与风险小节 |

### 4.8 可视化路由

图表不是固定章节或数量门禁。仅当关系、顺序、分支、状态、层级或部署映射用文字/表格难以快速理解时使用图，并先明确图要回答的评审问题。

- 默认使用 GitHub 兼容的 Mermaid 稳定语法；复杂布局才使用保留可编辑源的 draw.io PNG/SVG。
- 一张图只保留一个主视角；图前说明问题和边界，图后解释关键决策、不变量与失败分支。
- 关键失败语义、兼容约束、数值门槛和决策理由不得只存在于图中。
- 精确字段差异、对象处置、方案比较和 `AC/DEC/CHG` 追踪继续使用代码、表格或正文。
- reviewer 评估图的必要性、正确性、图文一致性、源文件和渲染兼容性；不得仅因没有图判定失败。

完整的 GitHub 实践证据、格式对比、图型路由和验收建议见 `diagram-practices-assessment.md`；运行时规则见 `../visualization-routing.md`。

### 4.9 可读性与信息密度

正式方案提供三个递进阅读入口，但不复制三份事实：

| 阅读层 | 目标 | 主要内容 |
|---|---|---|
| 决策扫描 | 快速判断问题、选择、主要变化、最大风险和是否阻塞 | 一页结论 |
| 方案理解 | 理解为什么这样选、机制如何工作、影响和上线验证路径 | 方案选择、机制导读、代表性场景/主视图、发布验证 |
| 深度评审 | 查找契约、不变量、失败边界、兼容、追踪和证据 | 实现级设计、矩阵和附录 |

各 profile 的第 4 章统一采用“guide → reference”顺序：先用机制导读和代表性场景建立心智模型，再展开足够他人实施的契约、状态、失败、不变量和边界，并回到代表性场景说明设计为何成立。

正文只详细展开本次发生变化、违反直觉、高风险、存在争议、影响正确性或缺少细节会导致不同实现的内容。完整性由七个读者问题、横切相关性矩阵和 `AC → 设计 → CHG → 验证/发布` 追踪保证；不相关章节删除，`N/A` 只在矩阵中说明。

表达遵循以下共同规则：

- 标题使用技术机制、状态变化或关键结论，不使用“方案项”“处理逻辑”“其他”等空标题；
- 一段只推进一个判断，首句先给结论或主题，先写正常路径再写异常和例外；
- 正文解释理由和语义，表格承载精确映射，图表达关系和时序，附录保存长证据；
- 同一事实只有一个权威位置，摘要、图和矩阵不引入新的条件或结论；
- 约 300/450 行仅触发结构复核，不能据此直接判定方案可读或不可读。

完整的 GitHub 项目评估、生成规则、反例、reviewer 测试和自动化边界见 `readability-practices-assessment.md`；运行时规则见 `../readability-and-writing.md`。

## 5. 路由规则

### 5.1 第一道门：是否需要正式技术方案

满足以下全部条件时，不生成正式方案，转 `dev-build-change`：

- 需求边界明确；
- 只有一个显而易见的最小实现路径；
- 不改变外部契约、数据模型或关键运行时机制；
- 不存在跨模块迁移、并发、一致性、安全或发布顺序风险；
- 验证方式可以直接从完成标准得出。

任一条件不满足，进入正式方案路由。

### 5.2 第二道门：选择主 profile

选择问题不是“改什么组件”，而是“本方案最需要证明什么”：

| 主要需要证明 | 主 profile |
|---|---|
| 多个运行时参与者协作后机制仍正确 | 机制/架构型 |
| 能从现状安全切换到目标状态且不遗漏、不误切 | 迁移/整改型 |
| 新旧生产方和消费方在版本窗口内不会互相破坏 | 契约演进型 |
| 数据、状态和事务在并发及失败下保持不变量 | 数据/状态型 |

多个条件同时命中时，只选择风险最高、最影响正确性结论的一项作为主 profile；其他内容通过横切维度或主 profile 内的补充小节处理，不拼接另一份完整 profile。

### 5.3 防止误选变更轴的强制复核条件

满足任一条件时，禁止直接把 `CHG-*` 作为详细设计标题，必须优先按 profile 组织：

- 三个及以上 CHG 共享同一个 DEC 或同一处置模式；
- 存在跨 CHG 的前置顺序、共同不变量、共享状态或统一退出门禁；
- CHG 数量超过 8 个；
- 详细设计标题中以仓库名、文件名或配置 key 为主；
- 移除 CHG 编号后，标题无法表达技术机制。

只有同时满足以下条件，才允许使用紧凑的逐变更正文：

- CHG 数量不超过 5 个；
- 各项没有共享机制、共享状态、共同顺序或跨项不变量；
- 每项可以独立实施、验证、发布和回滚；
- 每项都包含独立的技术判断，而不是同一模式在多个对象上的复制。

### 5.4 输出前自检

1. 只看第 4 章标题，能否知道方案如何工作，而不只是改哪些文件？
2. 正文是否出现工时、负责人、commit 拆分或逐文件命令？若有，应移入 DEV 清单或附录。
3. 同一失败语义是否同时定义在机制、接口、异常和风险多个位置？若有，只保留一个权威位置。
4. 是否保留了与当前场景无关的 Redis、MySQL、挂载、触发、并发等空章节？若有，删除。
5. 是否存在尚未收敛的“方案 A 或方案 B”？若会改变实现路径，标记为阻塞而不是同时写入推荐方案。
6. 只读一页结论，能否说出问题、选择、主要变化、最大风险和是否阻塞？
7. 不读附录，能否在约 5 分钟内理解机制如何工作、主要影响以及怎样上线和证明？
8. 第 4 章是否先建立心智模型，再提供实现级契约和边界，而不是直接罗列组件、字段或文件？
9. 每一段是否增加事实、理由、约束、边界或证据？没有信息增量的套话和重复内容应删除。
10. 当前方案、开放问题、未来可能性、证据和 DEV 执行内容是否已经隔离？

## 6. 追踪与内容归属

### 6.1 稳定标识职责

| 标识 | 职责 | 是否作为正文骨架 |
|---|---|---|
| `AC-*` | 定义可验证成功标准 | 否 |
| `DEC-*` | 记录实质技术取舍及依据 | 可作为方案选择小节的锚点，但不按编号机械分章 |
| `CHG-*` | 标识可实施、验证和回滚的交付单元 | 默认否，放附录 C |
| `RISK-*` | 标识风险、缓解和待决条件 | 否 |

### 6.2 追踪闭环

目标闭环调整为：

```text
AC → DEC/目标设计正文 → CHG → 验证信号 → 发布/回滚
```

附录 C 至少包含：

| CHG | 动作 | 对象 | 调整摘要 | 对应正文位置 | 来源 AC/DEC | 验证入口 | 发布/回滚 |
|---|---|---|---|---|---|---|---|

评审者仍需覆盖全部 CHG，但应通过矩阵确认交付完整性，不要求生成方把每个 CHG 写成正文章节。

### 6.3 内容唯一归属

| 内容 | 权威位置 |
|---|---|

| 候选取舍和推荐结论 | 方案选择 / DEC |
| 目标运行机制及正确性 | 第 4 章主 profile |
| 上下游影响与不变项 | 影响范围与兼容性 |
| 发布门禁、观测和回滚 | 发布章节 |
| 方案级验证 | 验证章节 |
| 风险和开放问题 | 风险章节 |
| 文件、行号、完整清单、长调用链 | 附录 |

### 9.1 静态契约测试

至少增加以下断言：

1. `solution-template.md` 只包含一个“目标技术设计”占位，不同时包含两套完整骨架。

3. `SKILL.md`、routing、template、contract 和 reviewer 均包含相同的四个 profile 名称。
4. 核心模板包含一页结论、DEC、AC、发布/观测/回滚、风险和附录追踪。
5. 核心模板不固定出现 Redis、MySQL、本地缓存、挂载位置、入口白名单。
6. 结构契约明确 `CHG-*` 默认不作为正文骨架。
7. reviewer 明确“逐 CHG 覆盖不要求逐 CHG 正文”。
8. 核心模板和入口提示不强制固定图表数量；图表规则明确按评审问题选择。
9. reviewer 同时检查缺少必要视图和存在无效图，但不把“无图”直接当失败。
10. 非文本图必须保留可编辑源，关键语义不得只存在于图中。
11. 核心模板包含机制导读和实现级设计的递进占位，各 profile 不直接以文件或 CHG 清单开篇。
12. 一页结论不包含完整 CHG 清单，只约束问题、选择、主要变化、最大风险和阻塞状态。
13. `SKILL.md`、readability 参考和 reviewer 使用一致的 30 秒、5 分钟、标题、双读者和唯一归属测试。
14. 篇幅阈值被描述为结构复核信号，而不是自动通过或失败条件。
15. 第一阶段不新增 Vale/textlint 运行时依赖；自动化只对确定性的结构、ID、占位和术语一致性设置硬门禁。

| RISK-TPL-005 | 历史方案与新模板不兼容 | 不追改历史审批；只有新版本方案使用新模板并重新评审 |

- 模板和 skill 改造应作为单一逻辑变更提交，避免新模板配旧 reviewer。
- 若试点发现 profile 路由不可用，可整体 `git revert` 模板体系提交，历史方案和审批记录不受影响。
- 已生成的旧方案继续按其绑定版本和审批记录解释，不要求迁移。
- 新模板生效后，正在 Reviewing 的旧结构方案若内容未变，可继续原轮次；一旦按新模板重写权威正文，必须形成新 `S` 并重新评审。

## 12. 交付物清单

实施完成后应交付：

1. 重写后的统一核心模板；
2. 四类 profile；
3. 路由规则和横切维度检查表；
4. 更新后的 `dev-design-solution` 与 Codex 入口提示；
5. 更新后的结构契约和 solution reviewer；
6. 修复及新增的 workflow 契约测试；
7. 更新后的人类模板指南；
8. 图表路由、格式降级、图文质量与校验规则；
9. 可读性与写作规则、分层阅读验收和结构检查边界；
10. 作为试点的硬编码整改 v4 及新的完整评审记录。

## 13. 推荐实施结论

建议按 P0 → P4 先完成模板体系改造并验证，再单独执行 P5 重构硬编码整改方案。不要先手工修当前 `solution.md`，否则会在旧模板和旧入口提示下重复产生同类问题。
